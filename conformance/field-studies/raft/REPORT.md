**Target:** local clone of `hashicorp/raft` (`C:\Users\jjdub\code\osssm\raft`, HEAD
`dd30865` @ 2026-07-20). Not a real GitHub fork — a local clone, per your call.
**Scope:** the Raft node's role/state machine (`Follower / Candidate / Leader /
Shutdown`) driven by `raft.go`'s `run()`/`runFollower()`/`runCandidate()`/
`runLeader()` loops and the RPC handlers that call `setState()`.
**Tool:** polygraph plugin v6.0.0, v2 SAM strict-profile artifact (default).

## What was built

- `contract.json` — 2-key state (`role`, `term`), 5 actions
  (`ElectionTimeout`, `ElectionWon`, `NewerTermSeen`, `QuorumLost`,
  `ShutdownRequested`), 5 special rules, `dataDomain` for `NewerTermSeen.term`.
- `traces/` — **67 real windows** across 24 chained NDJSON files, captured by
  driving an actual 3-node in-memory Raft cluster (`raft/trace_capture_test.go`,
  instrumentation added to the clone, not upstream) through 4 scenario
  families: plain elections, leader isolation + reconnect, leadership
  transfer, and explicit shutdown. Captured via a real `Observer` on
  `RaftState` (event-driven, not polling — a polling-based first attempt
  silently missed every Candidate state because elections on an in-memory
  transport resolve inside a couple of milliseconds).
- `specs/reference.js` + `invariants.mjs` — hand-written positive control,
  read directly from `raft.go`.
- `specs_broken/reference.js` — negative control (one deliberately wrong line).
- `out_generated/` — the real Step 4 run: 5 independent specs generated by
  `opus-4.8` directly from `raft.go`, replayed against the same corpus, plus
  invariant model-checking (2001 states explored, capped).

Two real bugs were found and fixed **in my own hand-written control** while
getting it to a clean run — worth recording since this is exactly what Step 3
is for:
1. `NewerTermSeen` didn't reject when the node was already `Shutdown`,
   letting the model checker "revive" a shut-down node. Fixed with an
   explicit guard.
2. My own invariant `election-won-cannot-skip-candidate` was written wrong —
   it fired on a Leader-stays-Leader no-op (any rejected action replayed as
   identity), not just on an illegal *arrival* at Leader. Fixed to gate on
   the role actually changing.

## The one real subtlety this run surfaced

13/67 windows (≈19%) in the final control, and a similar proportion in the
real generated run, disagree on whether **term increments at the exact
instant `ElectionTimeout` flips a node to `Candidate`**. This is not a bug in
the contract or the traces — it's genuine non-atomicity in the real code:

- `runFollower()`'s heartbeat-timeout case calls `r.setState(Candidate)`
  (raft.go:245) with **no term change**.
- By default (pre-vote enabled, the modern default), that Candidate then runs
  `preElectSelf()` (raft.go:2073), which explicitly computes the next term
  **"without actually changing our state"** — a comment in the source itself.
- The term is only actually persisted, via `setCurrentTerm`, inside
  `electSelf()` (raft.go:1999-2006), which fires later, after a successful
  pre-vote round.

So a node observed via `RaftState` at the moment it becomes `Candidate` can
legitimately be caught **either side** of that later term bump, depending on
real scheduling/network timing — even on an in-memory transport. I confirmed
this is the correct read, not an instrumentation bug, three ways:
1. I tried removing the 3ms settle-delay in the capture code (hypothesizing
   it let unrelated concurrent updates leak in) — conformance got **worse**
   (23/67 mismatches, not better), meaning the delay was letting a real,
   causally-linked update land, not introducing noise.
2. 4 of the 5 independently-generated specs (never shown my contract's
   framing or my reference) modeled `term = model.term + 1` on
   `ElectionTimeout`; exactly 1 modeled `term unchanged`. The *split itself*
   reproduces the real ambiguity — independent readings of the same source
   land on both sides of it.
3. Reading `electSelf`/`preElectSelf` directly confirms the design: pre-vote
   is deliberately non-mutating ("without actually changing our state") so a
   partitioned node's failed pre-vote round never disrupts the cluster with a
   spurious term bump — this is intentional Raft pre-vote-extension design,
   not an oversight.

**Practical takeaway:** a contract that observes `(role, term)` only at
`RaftState`-transition instants cannot deterministically pin down term at
the `Follower→Candidate` edge. A follow-up contract could add an explicit
`ElectionTimeoutStarted` / `ElectionTimeoutTermPersisted` split (hooking
`electSelf`/`preElectSelf` directly) if this edge matters to a consumer.

## Invariant model-checking (Step 4b)

Both the control (500-state bound) and the real generated run (2001-state
bound, 5/5 specs checked) came back with the same single reachable
violation, present in the control before the fix above and in **1 of 5**
independently generated specs:

> `shutdown-is-a-true-terminal-state`: `init → ShutdownRequested({}) →
> NewerTermSeen({"term":1})`

**Investigated by hand against the real code — not reproducible.** `run()`
(raft.go:136-156) is the only place that ever calls `processRPC` (via
`runFollower`/`runCandidate`/`runLeader`); its top-of-loop `select` checks
`r.shutdownCh` *before* the `switch r.getState()`, and that switch has no
`case Shutdown`. The instant `Shutdown()` closes `shutdownCh`, the very next
loop iteration returns — nothing is left listening on `r.rpcCh`, so no RPC
can ever again drive `setState(Follower)`. This is a **modeling gap** (an
easy acceptor omission, reproduced independently by an LLM reading the same
source), not a defect in hashicorp/raft. Good example of the intended
workflow: the checker raises a lead, hand investigation resolves it either
way.

## Bottom line

- The role/state machine hashicorp/raft actually implements matches an
  independent reading of its source on every point that matters:
  `ElectionTimeout` only fires from `Follower`, `ElectionWon` only from
  `Candidate`, `QuorumLost` only demotes a `Leader`, any role can be
  overtaken by a strictly newer term, and `Shutdown` is genuinely terminal
  once the run loop notices it.
- The only residual disagreement (term at the exact Candidate-entry instant)
  is real, understood, attributable to an intentional design choice
  (deferred term bump behind pre-vote), and not something either the hand
  control or 4/5 independent LLM reads got wrong about the code's *intent* —
  only about what a synchronous external observer sees mid-flight.
- The one invariant violation the model checker raised does not reproduce in
  the real code once you trace where `rpcCh` stops being read.
