| p2 | S552: fan-out to K observation slots with a handle invariant | Explicit refs `o1 … oK` in `Session` (there is no group broadcast). A configuration of one `Session`, K `Observation`s and K `Archive`s, 3 requests, with `handled-resolves` and `twice-then-handle` as configuration invariants (both hold, neither vacuous): **K=1, 52 global states; K=2, 898; K=3, 17,984** (8 s, and `PL5301 TRANSIT_BOUND_HIT` at the bound K·R+2); **K=4 did not finish in 230 s** and gave no verdict. The two completions (the decision's and the host's) may arrive in either order, and the checker explores both; `Session` takes the next step only when it has both.
- **S552, replaced.** The 1-slot configuration with the projection argument, in place of K slots. The README states the argument.
- **S558, confirmed** as the checker's own policy stage; no host check.
- **S555, confirmed**, on the existing journal reader.
- **S561, new.** A compaction must shrink the context and may fail; failure ends the trial with the overflow reason after one attempt. Both are properties of the harness module (HF3.8), not core changes.

## S552, the projection: ruled with conditions, written and evidenced (owner, 2026-10-11)

Ruled: the projection is accepted if the PS13 paragraph carries three conditions (per-slot properties; identical messages from the session; nothing the session does depends on how many slots exist or which answered), says that where the session waits for or aggregates slots the projection does not apply and K stays a bound, and is backed by a seeded per-slot violation agreeing at K = 1, 2 and 3 with the clean module clean at all three.

Written as **PS13.8a** in `docs/04-semantics.md`, after PS13.8 (spec text only; no code or checker change; the checker does not apply the projection, the author writes the one-slot configuration).

Evidence (`experiments/e3-probes/p2/gen.mjs`; the machines are service machines, the transit bound is K·R + 2K, R = 3; this replaces the E3.0 figures, which had `PL5402 STUCK` and `PL5301` findings of the probe's own making):

| K | clean module | seeded module (a slot is handled after 2 sends, not 3) |
|---|---|---|
| 1 | CLEAN, 52 global states | FINDINGS: `PL5401 twice-then-handle-1`, 7-step witness |
| 2 | CLEAN, 898 | FINDINGS: `PL5401` on slots 1 and 2, slot 1's witness the same 7 steps |
| 3 | CLEAN, 17,992 | FINDINGS: `PL5401` on slots 1, 2 and 3, slot 1's witness the same 7 steps |

The 7 steps are `Req@s`, `Req@s`, `Put@o1`, `Store(o1) -> a1`, `Stored() -> o1`, `Sent() -> o1`, `Sent() -> o1`. The other slots' witnesses have the same shape on their own slot. A condition of the harness, to be stated in its README: the real `Session` sends each observation the same `Sent` per request and reads nothing from the slots, so (1) to (3) hold for the handle and twice-sent properties; the budget and the context size are properties of `Session` alone and are not projected.

**What E3.2 found, and did about it.**

1. **One machine does not fit.** The first `Session` of 18 fields ran the checker out of memory twice (3.7 GB, then 3.0 GB after the number domains were cut to 0..6). A node out-of-memory is a crash, not a verdict, so no result was ever mistaken for clean. The loop is now three machines by concern, which coordinate by messages: `Turn` (a model call and its tool), `Context` (the window and its compactions) and `Trial` (the plan, the stage checks, the caps, the end). Each rule reads the fields of one concern, so each is checked on its own machine. The 3 s run that followed is the evidence. This is the plan's risk 8, "state space", realised; the split was not in the plan. The cross-machine messages (`Turn` to `Trial`, `Trial` to `Context`, `Context` to `Trial`) are checked as intents and not yet as a joint configuration; a configuration of the three is E3.4's check once the host drives it, and if it is too large the messages are checked in pairs.
2. **A `never` over a rejecting `require` is vacuous.** The checker counts a `never emit k while P` as tested only if some accepted step takes an action that can emit `k` from a state where `P` holds. A guard written as a `require` that rejects those states leaves no such step, and the rule is reported vacuous. So every gate is an `if` that is always taken and decides whether to emit: the typed gate of HT2 ("a typed decision over measured numbers"), journaled in both outcomes. This is the design HAC5 wants (every compaction decision replayed) and it came from the checker's discipline, not from the proposal.
3. **A `never` cannot name a decision** (`PL1001`: the machine declares no effect `summarise`). The compaction rule is on a new effect `startCompaction`, emitted by the gate in the same step as the summary decision; the summary's own application, `compact`, follows the summary.
4. **S561 as built.** `Overflowed` starts one compaction (`attempts` 0 to 1). If the window is still over the limit after it, whether the compaction failed or did not shrink enough, the next `Overflowed` ends the trial with `stopOverflow` and tells `Trial`. A compaction that succeeds sets the window to the summary's size (two buckets), so a compaction always shrinks. There is no `forced` flag and no `Failed` state: the first draft had both and they were redundant.
5. **A completion cannot repeat an effect.** `PL4002` refused `Summarised`, `Open` and `Receipted`, which emitted and changed nothing, so a duplicate completion would repeat the effect. Each now changes a field (`summarised`, a `Reading` and a `Checking` state of `Receipt`).
6. **`PL7001`, the credential-egress region.** A model call carries private code to a provider, so the checker finds the region reached with no gate crossed. The policy's `model-calls` obligation names `decision.agent`, `decision.summarise` and `decision.read`, and so crosses it. The budget check runs before any rule (PS18.4); the obligation allows.
7. **A policy checks the names it uses.** `effect.kind == "tool.none"` is `PL1001` ("not one of the program's values here"). The HF3.10 variant therefore points the deny rule at another real kind (`tool.stage-check`), the realistic fault of a wrong target.

**Changes to the replacement lines of E3.1 (as the owner's ruling asks them recorded).** The test header holds the new table. In short: the modules are `Turn`, `Context`, `Trial` and `Receipt`, not `Session`; every variant replaces an `if` or a `prices` line, not a `require` line, for the reason in finding 2; HF3.1 keeps the range guard (`if compactions < 2 && saving > rewrite {`), or it also breaks the counter's range (`PL3102`); HF3.4's variant is `if plan is Fusable || plan is Separate {`; HF3.5's `if scanned {`; HF3.7's `if stop is Tool && reprompts < 1 {`; HF3.8's `if attempts == 1 {`; HF3.9's `emit stopCap()`; HF3.10's `when proposal.kind == "effect" && effect.kind == "tool.stage-check"`. Two expectations changed: HF3.6 is `REFUSED` with `PL6845` (a static refusal, not `FINDINGS`), and HF3.10 gives `PL6503` and `PL7001`, since removing the deny rule also removes the gate that crossed the region. HF3.11's thresholds file is `editable/thresholds.json`.

**What the module proves and what it trusts (for the certificate and the README, E3.10).**

- The rules hold for the host's facts as given: the stop reason (`Metered`), the token measurements (buckets), the classifier's, the scan's and the verifier's verdicts, the stage check's result, and the order in which the host dispatches `Go`, `StoreLog`, `Measured`, `Overflowed`, `CapReached`, `Close`, `Show`. A `require` rejects an action out of turn; the host's failure to dispatch one is a stuck run, not a broken rule.

- The observation slot is checked as one slot (PS13.8a); `Ledger` sends each slot the same `Sent` and reads nothing back.

## Rulings after E3.2 (owner, 2026-10-11)

E3.2 accepted, with its contract changes (the Turn, Context, Trial and Receipt modules; HF3.1, HF3.6 and HF3.10 as changed). Findings 4, 5 and 6 accepted (S561 as built, `PL7001` for a model call with the `model-calls` obligation, the checked kind strings). Rulings:

1. **The three-machine split: accepted, with a gate.** Checking Turn, Context and Trial as one joint configuration is an E3.4 gate item, not an option. Until it passes, the rules hold for each machine alone, and the certificate says so. Held in `examples/harness/assumptions.json` as the open entry `joint-configuration`; `test/e3-assumptions.test.mjs` fails if it reads `discharged` before the module has a configuration of the three.
2. **Always-taken ifs: accepted, with a condition.** Both outcomes of each gate must be reachable in the checked state space. `test/e3-gates.test.mjs` adds, for each of the 13 branches (Context.Measured taken and declined; Context.Overflowed first and ending; Turn.Go waiting for a reprompt, fusing and running apart; Turn.StoreLog clean and redacted; Receipt.Show receipt and original; Trial.Close by cap and by another reason), an invariant saying the branch's signature state is unreachable, and requires the checker to violate it with a witness. 13 of 13 pass, so no gate has a branch that is vacuous in substance.
3. **S563 (a core diagnostic issue, for a later release; E3 makes no core change).** A `never emit k while P` whose guard is a `require` that rejects the states where `P` holds is reported vacuous, since no accepted step takes an emitting action from such a state. The report is right about the rule (it was never exercised) and silent about why the author wrote it that way: a guard written as a `require` is the natural way to enforce a rule, and the diagnostic pushes the author to an always-taken `if`. A later release could say, on the vacuous report, that the guard's rejecting `require` is the usual cause and what the always-taken form looks like.
4. **S564 (a limit).** A `never` cannot name a decision (`PL1001`: the machine declares no effect of that name). A rule over when a model call may start has to sit on a sibling effect emitted in the same step. `startCompaction` is accepted. `test/e3-gates.test.mjs` holds that the handlers which emit `startCompaction` are exactly those which `decide summarise`, in the same branch of the gate, and that a variant splitting the pair across two steps is caught. It is a source lint, as S562's is. A path property `count(start) == count(summarise)` would say it to the checker, but a path property must be prefix closed (`PL1701`), and an equality is not.
5. **HF3.1 asserts both.** `test/e3-hac1.test.mjs` has HF3.1 (the range guard kept: `PL3002`, and the finding is on the rule `compact-at-step-end-or-limit` itself) and HF3.1b (the counter guard dropped too: `PL3002` on that rule and `PL3102` beside it). Every test of HF3.1 checks the property name, so a `PL3102` alone cannot pass.
6. **The host's facts are named assumptions, each discharged or open (S463's way).** `examples/harness/assumptions.json`: stop reason, token buckets, classifier verdict, scan verdict, verifier verdict, stage-check verdict, compaction size, dispatch order and the joint configuration are open; the one-slot projection is discharged (PS13.8a). Each open entry says what tests it. **A limit (S565).** The poly certificate (`poly.assumptions`) lists only the assumptions poly's own checks name, so an application cannot add entries to it without a core change. E3 lists them in this file, which the harness certificate (E3.10) hashes, and the README quotes it. The owner may rule a core field for application assumptions into a later release.
7. **Placeholder prices.** `host/price-gate.mjs` refuses a price table whose source is `example.com` (or any placeholder host), whose model is a placeholder, whose date is missing, in the future or over 90 days old, or whose prices are not positive integers; `test/e3-prices.test.mjs` holds it on tables it writes. `node examples/harness/host/price-gate.mjs` is the live-run launcher's first step and exits 1 today for both committed tables. The live run (E3.9) does not start until it passes.
8. **Machine load.** M7 is running the full suite: single checks only, no builds, no full suite until M7 reports its suite line. The gate-reach test ran 13 checks at about 14 s each against a loaded machine (3 minutes in all).

## E3.3: the certified handlers (2026-10-11)

`examples/harness/host/handlers/`: `verify.mjs` (the receipt verifier), `scan.mjs` (the credential scan and the redaction), `classify.mjs` (the fusion classifier), `archive.mjs` (the archive store and the handle text), `compact.mjs` (the application of a compaction) and `intake.mjs` (what a tool output becomes: scan, redact, archive, reader input, journal record). All deterministic, no model, no import but `node:crypto`. `test/e3-handlers.test.mjs`: **22 of 22 pass**; with the other E3 light tests (lint, prices, assumptions) 32 of 32; `npm run check:boundaries` passes. No build, no suite, no check at K above 1 ran (M7's suite is running).

**HAC4, S553: the verifier.** It checks, on one tagged line each, the source hash, every quote byte for byte, the status against the exit status, and the size; all checks run and every failure is named. A suite of 14 cases (a good receipt of a failing and of a passing run; a hash of another log and of one digit off; a quote with another case, other whitespace, absent, one byte off; a status the wrong way in both directions; a receipt longer than a tiny log; not JSON; no hash; an empty quote) and a generated comparison with an independent oracle (`Buffer.includes`) on 300 logs and receipts, quotes altered or not, with multi-byte text. **The four seeded mutant verifiers are each caught:** one that skips the hash, one that accepts a quote equal to the log's only up to case and spacing, one that ignores the exit status, one that accepts a receipt longer than the log. A rejection through the handler is a permanent failure with the reasons named, which the runtime completes as the effect's failed outcome without a retry; that mapping is checked against the runtime in E3.4 (open evidence in `assumptions.json`).

**S554, HF3.5: the scan and the canary.** Seven credential shapes (AWS access key, private key block, bearer token, `sk-` key, GitHub token, JWT, a name assigned a value) and every secret the host knows in the four encodings the standing canary test knows (plain, base64, base64url, URL-encoded). A secret under 12 characters is refused, or the scan would flag ordinary text. Benign build and test output is not flagged (8 samples, including git and sha256 hashes, "tokenizer" and a `sha256:` image digest). On 200 generated outputs a redacted text holds no encoding of the token and no pattern, and scans clean. The handler writes the redacted copy only and never the unredacted bytes. **The canary:** a token in all four encodings and an AWS key in a large output reaches none of the intake's sinks (the context, the handle form, the archived copy, the archive store, the reader's input and the journal record); the reader gets nothing for a flagged output. **Seeded control:** an intake that archives the unredacted output is found by the same scan, in the archived copy and the archive store. **What this does not cover, stated:** the journal here is the record the intake makes, not the runtime's journal. The standing M9 scan over the store's tables (AC18) is run over the harness's real runs in E3.4 and E3.5, and the entry `scan-verdict` stays open until then.

**S559, HF3.4: the classifier.** An edit then a declared runner (a test, build or lint command of the table), as one plain command: no pipe, redirect, substitution, list, newline or backslash. 12 positive and 12 negative commands, plus the shapes of calls (order, count, JSON). The table is the trust; additions to it are outside the editable surface (`editable/` holds prompts, skills and thresholds only), which is stricter than S559's "only for additions a test shows the classifier handles", and is recorded here as the way it was built.

**HF3.3, HF2.4, S561: the archive and the compaction.** `ArchiveStore`: 100 generated buffers, any range exact, a reference per holder, gone at the last release and not before, a release or a retain past that refused. The handle text carries the handle, the size and a head-and-tail excerpt and names the omission. `applyCompaction`: pinned messages kept, the last few kept, the result smaller or refused (and nothing released when it is refused), and a handle released only when the new transcript no longer mentions it (a handle named in the summary stays).

**PT6.5.** The six handler files pass `poly lint handlers`; a handler importing `node:fs` is `PL6401` (the control).

**Not here, and where it goes.** `stageCheck` needs the tasks and their checks: E3.7. `saveWork` needs the sandbox and the scratch folders: E3.4. The effects' labels, targets and payloads in `harness.poly` (they are payload-free now: `scan()`, `classify(calls)`, `verify(receipt)`; the handlers read the turn's output, log and archive through a store capability keyed by the instance) are made to match the capabilities the runtime grants when the handlers first run under it, in E3.4. If that changes the module, the HAC1 tests and the gate-reach tests run again.

## Step 2: the pay-gate with the paper's structure (2026-10-12)

The host measures the paper's three ingredients (`host/loop.mjs`, `measuredNumbers`): the requests still to come, estimated from the observed rate (requests per completed step times the steps left) and capped by the requests that would fill the window at the observed growth; the saving over those requests; and the rewrite, the summary and the messages after the first dropped one, times the cache write/read price ratio less one (the pinned head stays cached; the summary call is not priced). `gain` is the ratio of saving to rewrite in halves, rounded down, 0 to 8. A later compaction needs a larger margin: the saving must exceed (compactions + 1) times the rewrite. The price tables now carry the two cache classes (`cache_write`, `cache_read`; placeholders at the usual 1.25 and 0.1 times the input price, a ratio of 12.5), the price gate requires both, and the loop takes the ratio from the main tier's table. HAC1's HF3.1 variants are `if compactions < 3 && gain > 2 * (compactions + 1) {` and, for HF3.1b, `if gain > 0 {` (the margin and the counter guard dropped): with the margin kept, the counter cannot escape its range, since a gain above 8 is not possible, so the old variant of HF3.1b no longer gave `PL3102`.

## E3.8: the paired acceptance (2026-10-12)

`examples/harness/host/paired.mjs` and `test/e3/e3-paired.test.mjs` (15 of 15, run alone; unit tests on synthetic pairs and tables, no admission, no checker, no model). The rule follows the proposal's VERA reading, as ruled:

1. A change outside the editable surface is REFUSE before any statistic (HF3.11, S557, `change-gate.mjs`).
2. Any stage that passed in the base and does not pass in the candidate, in any task, is a regression, and any regression is REFUSE, whatever else improved (HF2.8, HAC8, Q-E3-6).
3. A candidate that completes fewer tasks than the base is REFUSE, however much cheaper (HAC3). Costs are reported beside the verdict, never in it.
4. A significantly worse candidate (exact one-sided McNemar, the other way) is REFUSE.
5. A significant gain (exact one-sided McNemar on the discordant pairs, alpha 0.05) with no regression is ACCEPT, unless a measured noise floor is at least as large as the gain (then INCONCLUSIVE: within the rerun spread).
6. Anything else is INCONCLUSIVE and says why: too few discordant pairs for any outcome to reach alpha (fewer than 5), or a gain that is not significant. It is never reported as "no difference".

A task is completed when every stage passed in every rerun ("reached the end of the plan"); a stage counts as passed when it passed in every rerun. **Consequence, found while writing the tests:** a pair that goes against the candidate (completed in the base, not in the candidate) always contains a regressed stage, so rules 3 and 4 can be reached only together with rule 2; they are kept as stated checks, and a loss makes 6 of 7 a REFUSE rather than an INCONCLUSIVE. The statistic itself still gives 0.0625 for 6 of 7, which the live report states (tested at the function).

**The noise floor.** It is the share of tasks (and of stages) whose outcome differs between reruns of one configuration with the model frozen. ## S571: a live run must give the harness the real clock (owner, 2026-10-13)

**The defect.** The live launchers (`runStaged`, `runPilot`) loaded the harness through the test loader, which gives it a fixed test clock (2026-09-21). Poly's month budget was therefore keyed `budget:task:scope:harness:month:2026-09` in a run made in October. The cap held across the whole plan (`spent: 4313767` of `cap: 25000000`, the driver's total) but its period was wrong: a second plan in October would have found a fresh budget, and a cap meant to last a month would not have. **The order, as ruled:** the spec line first (HF2.10, amendment A2, `5b03724a`); then a test written by a separate writer, which failed first for the stated reason (a one-trial staged run left a budget instance keyed to 2026-09; the launchers' `loaded()` calls passed no `now`), commit `b3adcd53`; then the fix (`d7d4b64a`: both launchers pass `now: () => Date.now()`). The test now passes (`e3-live-clock` 3 of 3), and `e3-live` 12 of 12, `e3-staged` 8 of 8 and `e3-pilot` 5 of 5 pass, run alone. Recorded runs, which spend nothing, keep their fixed clock. **S571, for a later release:** the loader of the test helpers should not be the way a live run is loaded; a clock is a parameter the live path states, not a default it inherits. The report (`docs/e3/live-run-report.md`, section 5) carries one sentence saying it is fixed, with the commit.
