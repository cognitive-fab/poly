# Proposals for v2.0

Proposals that come from writing the ten new examples (P1 to P3 from batch 1, P4 to P7 from batch 2, P8 to P10 from batch 3 and its follow-up, P11 from batch 4). Each is a request for a ruling, not a ruling. The evidence for each is in `docs/examples/language-findings.md`; the numbers there are the entry numbers. None changes a requirement until the owner accepts it.

## P1. A way to declare a decision gated

- **Problem.** A decision that sends private text to a model is a credential-egress region. The check accepts it only when a policy rule names `decision.<name>`, so a rule is written to satisfy the check (`PL7001`, finding 1). The rule's content is arbitrary.
- **Proposal.** `gated by <policy>` on a decision, or a policy form `gate decision.<name> ...`, so the declaration, not a rule written for its side effect, is what the region reads. A declared gate that no policy of the scope backs is a diagnostic of its own.
- **Cost.** A grammar item, a lowering to the same `security.json` entry, and a read-back by poly-ref.

## P2. A check-time diagnostic when a decision lacks an audience

- **Problem.** A decision over a `Content` the host stored fails closed at run time with "no taint record (S302)" when the program declares no `audience`. The check is `CLEAN` (finding 2).
- **Proposal.** A diagnostic at check time when a decision's parameter is a `Content` and the program has no audience, naming the fix (`audience { public < x }`). It is a finding for the author, not a refusal.
- **Cost.** One rule in the validate stage; no lowering change.

## P3. The cut-point reduction for stored values compared with constants

- **Problem.** S458 cuts a range parameter at the constants it is compared with. A value a handler stores is explored whole, so a `0..500` amount compared with two thresholds exhausted memory (finding 3).
- **Proposal.** Extend the reduction to a state field that handlers only copy from a cut parameter and compare with constants, so the field is explored at the representatives of its classes. The lowered module is compared with the semantics at the greatest value of each class in every reached state, as S458 already requires for parameters, so the premise is checked and not assumed.
- **Cost.** An analysis over the handlers (the flow of PT3.4a already computes how a parameter reaches a field), an instance line that prints the field as cut, and a new entry in the toolchain faults for the broken lowering that misses a class.

## P4. The fail-safe direction of an effect (language findings 8)

- **Problem.** `PL6201` requires a decision's irreversible effect to be gated by its confidence, and it reads "page when unsure" as ungated, since the effect is emitted at every confidence. For an alarm, acting on an unsure answer is the safe direction, and the program has no way to say so; the example moved the unsure case to a person, who then pages.
- **Proposal.** A declaration on an effect (`safe when unsure`, or `failsafe`) that states acting without a confident answer is the safe direction. `PL6201` then accepts an emission at every confidence for that effect only, the declaration is listed in the certificate as an accepted exception that a person signs (PT12.5), and a policy can read it (`effect.failsafe`). Without the declaration the rule is unchanged.
- **Cost.** A grammar item on an effect, a certificate entry, and a test that an irreversible effect without it is still `PL6201`.

## P5. One confidence scale (language findings 12)

- **Problem.** Source compares `conf >= 0.8`; witnesses, reports and the host types carry `800`; a dispatch of `0.95` is refused as outside `0..1000`.
- **Proposal.** Witnesses and reports print a `Conf` as the decimal the source writes (`0.8`, `0.95`), and the host types say in a comment that a `Conf` is a number of thousandths on the wire. The wire form does not change.
- **Cost.** The witness and report printers, and the examples' expected text that quotes a witness.

## P6. A step-by-step settle in the test API (language findings 11)

- **Problem.** `settle` runs the worker until nothing is due, so a test cannot observe the middle of a chain of effects. Three independent test writers asserted intermediate states a run never rests in.
- **Proposal.** `rt.worker.tick({ step: true })` or `rt.settleOne()`, which takes one due item (an effect, a timer, a delivery) and returns what it was, and a helper that folds the journal into the states a run passed through.
- **Cost.** A small addition to the host API and its documentation (PT15); the worker already takes items one at a time.

## P7. An ignored completion (language findings 13)

- **Problem.** A late completion that should change nothing has no spelling that passes `PL2201`, so the example writes a field it never reads.
- **Proposal.** An `ignore` statement for a handler path that deliberately does nothing, journaled as an accepted step, and accepted by `PL2201` only where the path is a completion handler or a guard on the status.
- **Cost.** A statement in the grammar, a lowering to the existing no-write step, and a test that `PL2201` still fires for a silent handler elsewhere.

## P8. A static check that a workflow's orders fit its run cap (language findings 15)

- **Problem.** An order spends its order cap whatever it reports, so a run cap below the sum of the orders on the program's longest path is a review that cannot finish; nothing says so before it runs.
- **Proposal.** A check-time finding, from the machine's graph, when the greatest sum of order caps along a path exceeds the run cap, with the path as its witness. A path through a loop makes the finding inconclusive.
- **Cost.** A longest-path computation over the explored graph (poly-ref already has it) and one diagnostic.

## P9. An audience ceiling on a decision (language findings 17)

- **Problem.** A decision has no declared audience. What a decision may be given is a policy rule over `effect.taint.class`, written by hand for each decision, and nothing ties the rule to the decision it protects.
- **Proposal.** `audience customer` on a decision, its ceiling. It is certified, read back by poly-ref, and a policy reads it (`effect.audience`), so a rule can say "a decision is denied when its taint is above its own ceiling" once, for every decision. A decision with no declaration has the lowest class.
- **Cost.** A grammar item (the decision grammar already has the `audience` keyword for effects), a manifest field, and a broken lowering in the toolchain faults.

## P10. The check follows taint from a source into a decision's inputs (language findings 17)

- **Problem.** The flow rule excludes decisions (PS17.3), so the static check follows a taint only to where data leaves. The owner's notes given to an external decision are `CLEAN` at check time and denied only by the gate; support-drafts' defect checks `CLEAN` beside its own policy.
- **Proposal.** The flow rule applies to a decision's inputs: on every accepted step that issues `decide d(…)`, the declared audience of `d` (P9) may read the taint of every `Content` and `Items` argument, with the same pending-taint exploration the rule already has for completions. A violation is `PL6831 AUDIENCE_LEAK`, with the path to the step as its witness. It is the static counterpart of the gate's audience rule, and it needs no policy: the program alone is a finding.
- **Cost.** A change to PS17.3 and PT10k (decisions leave the exclusion), the rule's exploration over each decision's intent (the taints are already tracked), a decision-table row for each ceiling, and a seeded defect for the toolchain faults that drops the check. `support-drafts-defect.poly` becomes a finding of the program beside its own policy; its test, which now asserts `CLEAN` there, is the one that changes.

## P11. An unknown usage key is a failed call, not a charge at the highest price (language findings 21)

- **Problem.** A provider's usage report with a key the price table does not name (`inputTokens` for `input`) is charged at the table's highest price, as a fail-safe. One call then overran its reservation by three times (808 against 208 micro-dollars), spent a shared budget of 1,000, and every later call was denied `budget` with no line saying why.
- **Proposal.** `chargeOf` treats an unpriced key as it treats a missing or non-whole report: a `ProviderError`, the decision's `failed` outcome, and a line in the journal (`usage-unpriced: inputTokens`) naming the key and the table. The reservation is released as for any failed call, so one bad provider does not exhaust a budget. The charge at the highest price stays available only as an explicit table option (`unpriced charge top`) for a provider that adds classes the table has not caught up with.
- **Cost.** One more violation in `chargeOf` beside `usage-missing` and `usage-invalid`, a journal line, a table option, and a test that a call with an unknown key fails and leaves the budget as it was. The recorded providers of the examples already use the table's keys.

## Conclusion

P1 and P2 remove an arbitrary rule and a silent failure. P3 removes the largest cost the examples met. P4 and P7 make two correct designs expressible, P5 makes a reading easier, and P6 is a test convenience. Each is small against what it saves, and each has its check in the existing read-back and fault-list discipline.

## Glossary

- **Cut point:** a constant a parameter is compared with; the check explores each side of it (S458).
- **Region:** a set of effects behind a gate; `PL7001` reports one reached with no gate crossed.
- **Taint record:** what the runtime keeps about the audience of a stored body (PS17.4).
