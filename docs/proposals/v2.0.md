# poly v2.0: the proposals so far

This document holds every proposal that the work up to v1.3.1 has raised for a later major release. It is a list for the owner to order, not a plan. Each proposal has a problem, the evidence that exists today (with the file or the commit that holds it), a sketch, what it touches, and the questions that stay open. A proposal that rests on no evidence gathered in this repository says so.

The list: 1 per-order identity, 2 contracts on handlers, 3 retry safety as an effect type, 4 the out-of-range outcome, 5 signed invariants, 6 migration of running instances, 7 a published metamodel and megamodel, 8 calibration, 9 a fair Act 1 baseline and a harder benchmark, 10 the room page's event stream, 11 related work, 12 taint per recipient, 13 a reply after an unapproved escalation, 14 the model imprecision of the checker's witnesses, 15 the robustness of the Docker replay test, 16 a way to declare a decision gated, 17 a check-time diagnostic when a decision lacks an audience, 18 the cut-point reduction for stored values compared with constants.

Proposals that come from writing the ten new examples. Each is a request for a ruling, not a ruling. The evidence for each is in `docs/examples/language-findings.md`; the numbers there are the entry numbers. None changes a requirement until the owner accepts it.

## 1. Per-order identity: a conceptual data layer

**Problem.** A machine cannot say which order it acts on. `Items` is opaque (PS1.4b): it is not stored, not compared and not matched, and its owners, class and age are the runtime's. So the concierge's refund ledger is per Desk, that is per customer thread (DF19), and a guest with two orders cannot refund the second until the first is resolved. A program that wants "at most one refund for each order" cannot state it.

**Evidence.** The review of the v1.3 pages (Q1) and the commit `b28f8b7f`. The Desk reaches `Amounted` with an item set of count 1 and nothing else about it. `Key` (PS1.4c) is a value that names items of a source and can be stored and compared, but a Desk has no way to read the key of a cited item. In `poly-kept` the ticket is one machine for each order (`ticket:<order>`), so the same property is per order there, by the shape of the host.

**Sketch.** A conceptual data layer: a source declares its entities and their keys, and a cited item set can be asked for the key of its one item (`cites.key(charge)` for a set of count 1, a `Key` otherwise `none`). The Desk stores a set of keys (a `map<Key, Ledger>` or a bounded list), and the path property reads it: `never emit refund(order: o) while ledger[key(o)] != None`. The taint of the key is the item's, and a key leaves the program only as a token (PS19.4).

**Touches.** PS1.4b and PS1.4c (a new read of `Items`), PS17 (the key of a cited item is data of the item's class and owners, so the flow rule must see it), PT23 and the source declaration, the front end and the lowering of a `Key` in a map, poly-ref (representatives of keys, PS4.1g, now inside a map), the certificate, the diagrams (the projection onto a field).

**Open questions.** Whether a key read from an item is a declassification point (S325 already says a count is). How a map of keys is bounded for the check. Whether the layer is the source's schema or a separate declaration. How a forget (PS17.7) removes a key from a stored ledger.

## 2. Contracts on handlers

**Problem.** A handler is JavaScript that the check does not read. What it does is the program's last word on the outside world, and none of it is a property of the program. The amount of a refund, the bound "no more than was paid and not yet refunded", the owner check: all are code.

**Evidence.** Observation A1 of Act 1: both kept builds refunded an amount other than the one asked (`ts-kept` the whole order, `poly-kept` the blender), and the checker said nothing, because the amount is computed in a handler outside the machine (`docs/demo/act1-script.md`, part 1). `examples/concierge/host/refund.mjs` holds the bound against `amount_refunded` as code; v1.3.1 states that the ledger does not depend on it (release notes, known limits). The 409 of DF20 was a handler fault that opened the double refund the ledger closes.

**Sketch.** An effect declares a contract on its handler: a precondition over the payload and the items it reads (`requires amount <= order.paid - order.refunded`) and a postcondition over what it sent (`ensures request.amount == payload.amount`). The runtime checks both at the capability, on every call, and a violation is a permanent error with an audit row. The check proves nothing about the code but makes a breach an event, and a test can generate calls from the contract.

**Touches.** The effect grammar (PT6), the capability (`caps.api`, `caps.egress`), the manifest and its read-back by poly-ref (an artefact, so it needs its round-trip check and a broken variant in the list of toolchain faults), the audit, the worker (a contract breach is `permanent`, S138).

**Open questions.** What language the contract is written in, and whether it can name the request body (a form string). Whether a contract on a read of a charge is a contract on a Stripe answer, which poly cannot know (K17 is of that kind). The cost of reading the body of a request.

## 3. Retry safety as an effect type

**Problem.** PS23 is a rule over effect declarations: an irreversible effect with more than one attempt must be keyed or idempotent by nature (`PL4003`). It is not a type. The program can still re-emit the effect (S527), and the rule does not see the second intent. In v1.3.1 the ledger and the property `no-reissue` are written by hand for one effect.

**Evidence.** PT33.11 (the limits), the commit `b28f8b7f`, Act 1 part 4 (the shipped properties of `poly-kept` stay CLEAN on mutation (c)), and `docs/demo/part4/`.

**Sketch.** An irreversible effect has a type, `Once<E>`, whose values are a pending intent, an issued one and an unknown one, and a machine can emit `E` only through a handle that the type system tracks: emitting while a handle of the same effect and the same key is pending or unknown is a type error. The ledger and `no-reissue` become what the compiler generates from the declaration, and `Resolve` becomes the one operation on an unknown handle.

**Touches.** The type system and the front end, PS23 and PT33, lowering (generated state and action), poly-ref (the generated property and its non-vacuity), the report, the diagrams. It overlaps proposal 1: the key of the handle needs the identity of the order.

**Open questions.** Whether the handle is per machine instance or per key. How a type deals with `compensable` effects. Whether a person's `Resolve` is a language construct or a library.

## 4. The out-of-range outcome

**Problem.** An amount outside its domain (`refund me 5,000`, `Amount = { value: 0..500 }`) is refused at dispatch (AC30, S140), journaled, and the Desk replies `Unsure`. The guest is told too little ("looking into it"), and the program cannot say more because its failure action carries no reason.

**Evidence.** `docs/demo/proposal-out-of-domain-outcome.md` (options A, B, C and the table of what each touches), DF17, and the decision of the owner for v1.3 (option C: no change). The terminal line already says `outside its domain (0 to 500)`.

**Sketch.** Option A of that proposal: the runtime gives the failed hook the reason `outside-type` for a refusal under S140, the Desk's `Unextracted` takes a `reason`, a handler branches on it, and `Outcome` gains `OutOfRange`. With the machinery of v1.3.1 (the ledger is a field read by a branch) the Desk grows by one value and one branch.

**Touches.** `poly-runtime` and its documentation of the reason of a failed hook (PS, PT), the example and the demo copy, the recorded fixture, the end-to-end tests, the instance of the Desk (now 5762 states, so the check is longer still), the runbook table and the row of DS2.

**Open questions.** Whether the reason is a closed enumeration of the runtime or open. Whether the wording for the guest belongs in the program or in the reply decision.

## 5. Signed invariants

**Problem.** A property of a program can be removed by an edit and the verdict stays CLEAN. The shipped properties of `poly-kept` did not notice mutation (c); the property that does is an addition, and an edit that deletes it is invisible to the verdict. A finding can be accepted by a person's signed record (G3), but a property cannot be required by one.

**Evidence.** Act 1 part 4 and `docs/demo/part4/` (the same machine, CLEAN without the property and four witnesses with it). `poly accept` and `poly admit` (PT12.5) sign findings, and the certificate lists the properties it checked.

**Sketch.** A project declares a set of required properties by name and digest, signed by a person in the `people` ring. Admission refuses a build whose certificate lacks a required property, or lists it as vacuous, or lists a different text for the digest. A change of the set is a signed record that only moves forward (S210).

**Touches.** The certificate and its verification, admission, `poly check` reporting (a required property that was not run is `INCONCLUSIVE`, PT12.3), the records module of `poly-core` (a new kind), the runtime's load.

**Open questions.** Whether the digest is of the text or of the lowered artefact. How a property that must change (because the program changed) is re-signed without being silently weakened. Who may sign.

## 6. Migration of running instances

**Problem.** v1.3.1 adds a field to the Desk (`refund`), an action and a claims type. A running Desk of v1.3.0 has a state without the field, and nothing in the release says how it is carried over. The demo has no running instance between shows, so the gap did not show.

**Evidence.** The change of state shape in `b28f8b7f`; the `polyvers` engine and its lanes of compatibility are in the Poly stack (the agent `polygraph:polyvers`); `docs/03-technical-spec.md` mentions migration in its tables. No migration of the concierge was written or run in this release.

**Sketch.** `poly check` classifies a change between two builds of a machine into a lane (same shape, additive, breaking), generates the migration of an additive change (a default for the new field: `refund = None` is right only if no refund is in flight, which is a fact about the instance), and replays the stimuli of the old journal on the new build to prove the old runs fold the same.

**Touches.** The release flow and the certificate (a migration is an artefact), `polyvers`, the runtime's load of a build over existing instances, the journal's replay (PS11.4) across versions.

**Open questions.** What the default of a ledger is for an instance with an intent in flight. Whether a migration is signed by a person. How a rollback is done.

## 7. A published metamodel and megamodel

**Problem.** poly has a language, a lowering, a semantics and a set of models (the machine, the generated conversations, the runtime's outbox model, the policy table), and no published description of how they relate. A reader of the diagrams of v1.3.1 sees projections of one machine, not the program.

**Evidence.** None gathered here beyond the diagrams (`docs/demo/diagrams/`, DF25) and the architecture's table of layers (`docs/02-architecture.md`). This proposal comes from the owner's list.

**Sketch.** A metamodel of the language (the AST and the semantic domains of 04-semantics, as a machine-readable schema) and a megamodel of a checked program: its machines, the models derived from them (conversation, outbox, route, budget, grant), the artefacts lowered from each, and the properties and verdicts attached to each, as one graph. The diagrams, the report and the certificate become views of it.

**Touches.** `docs/02-architecture.md` and 04-semantics (a schema), `poly-core` (the AST types are the start), the report (`poly check --json`), the certificate, the diagram script (it already reads the explored graph).

**Open questions.** The format (JSON schema, a modelling language, Mermaid for the human view). How versions of the schema are pinned. Whether it is generated from the source of the packages or written.

## 8. Calibration

**Problem.** The route's calibration maps are stand-ins: `PL6842` refuses a tier whose map is fitted for another model than its price table's, so a live launch needs the maps relabelled by hand, which says nothing about the model in the room.

**Evidence.** `docs/demo/calibration-for-release.md` (two ways to a release: a calibration run plus `poly journal fit`, or named stand-ins), step 2.6 of the runbook (the relabel block), and the measured latencies of the live rehearsal (small median 1550 ms, large 2840 ms).

**Sketch.** One labelled run of the live providers on a corpus of messages, fitted with `poly journal fit` and committed with the model and the date. The copy script writes the maps from the price tables' `model` only when a fitted map exists for it; otherwise the launcher prints that the confidence is not calibrated to the model.

**Touches.** The copy script, the maps and their digests, the launcher's printed diff, the runbook, the corpus and its provenance, the cost of the run (it is a live call).

**Open questions.** The corpus. Whether a fit older than a date is refused. Whether the route's thresholds (`conf < 0.8 or margin < 0.1`) are fitted too.

## 9. A fair Act 1 baseline and a harder benchmark

**Problem.** The experiment of Act 1 is one prompt, one agent, one run for each arm. Both kept builds refunded once under the lost answer (O2), so the experiment showed no difference in behaviour, and the difference had to be shown by mutation and by a chosen scenario. In v1.3.1 the TypeScript build turned out to hold a ledger of refunds in code, which makes the lint's blind spot a statement about a fixture, not about the arm.

**Evidence.** `docs/demo/act1-script.md` (parts 1 and 4), `docs/demo/baseline-known-limits.md` (the guard's false positives, the pilot verdict), DB8 (what the protocol does not claim), and `docs/demo/step10-replay/`.

**Sketch.** Several tasks that need the property the experiment is about (an irreversible effect whose request can be repeated, with a customer who asks twice), several runs for each arm, the same prompt rewritten, a pre-registered score that counts double refunds under the asked-twice scenario, not only under the lost answer, and a task in which re-planning is the hazard. The audit and the guard stay as they are.

**Touches.** `demo/baseline/` (the pre-registration, the prompt, the replay driver's scenarios), the budget of the runs (the baseline has its own caps), the report of outcomes (O1 to O3 gain a fourth: a second intent).

**Open questions.** The number of runs that the budget allows. Whether the benchmark is public. How to keep the poly arm from being shown the answer (the arm's reference is pinned by a digest, DB16.3).

## 10. The room page's event stream

**Problem.** Each room tab holds an event stream to the host, a browser allows about six connections to one address, and stale tabs keep theirs, so a new tab's `Send` queues behind them and the page says nothing. DF18 gave the page a "Sending..." state and a timeout; the causes are not removed.

**Evidence.** `docs/demo/rehearsal.md` ("The room page, for v1.3": items 3 to 6 are not built), the rehearsal findings, and the eight failures listed in the release notes of v1.3.0 (the connection limit that queued Send behind stale tabs).

**Sketch.** The state of the stream on the page (`Reconnecting...`), one stream for each session (a new stream closes the older one after a `superseded` event, which the page shows), the connection of a hidden page freed on `pagehide`, and a heavy test with six held connections.

**Touches.** `demo/host/page.mjs` and `demo/host/server.mjs`, the room's subscriptions, two tests, the runbook (it can drop the rule about tabs).

**Open questions.** Whether the stream should be a long poll to fit proxies. How a presenter's second window is told from a stale tab.

## 11. Related work

**Problem.** The claims of poly (a check of the program, not of an agent; retry safety as a rule; translation validation against a semantics) are read against other systems by every reviewer, and the answers are scattered.

**Evidence.** `docs/research/landscape-2026-09.md` (state-machine and model-checkable languages, verification-aware languages used with LLMs, languages for agents, durable execution and governance runtimes), and the review `docs/reviews/review-2026-10-08-article-lamport.md`.

**Sketch.** A section for the pages and the release notes of each version, kept up to date: for each neighbouring system, what it checks that poly does not, what poly checks that it does not, and what the demo can and cannot say against it. The v1.3.1 lint is a worked case: the lint sees a line, the check sees a path.

**Touches.** Documentation only: the landscape document, the glossary of the pages, the README.

**Open questions.** Which systems to name, and who dates the comparisons.

## 12. Taint per recipient

**Problem.** The taint of a body is kept by its digest and joined with the owners of every customer it was made for (PS17.4, S319). A text that two customers receive is a body with two owners, and the send to the second is denied `audience`. A live model can write the same sentence for two guests, and the stub model always does, so replies can be dropped without any attack.

**Evidence.** The room scenarios of v1.3.1: the same `Already` text for three guests was sent to the first and denied to the others (`channel.support.send` dead, `denied: audience`), found by `test/after/demo-ledger-e2e.test.mjs`. The fixture now gives each message a text of its own (`57331668`). `packages/poly-runtime/src/memory.ts` (`taint` joins by digest).

**Sketch.** Key the taint by the digest and the instance that made the body (or by a nonce the decision adds), so that two customers' identical texts are two bodies. The flow rule still sees the owners of what the decision read, and a body copied across instances is still refused.

**Touches.** `memory.ts` and the `poly_taint` table, PS17.4 and S319 (the join), the erasure (PS17.7: a forget drops the records of a subject's bodies, and a body with one record per instance needs a list), poly-ref's flow model (its taint is by value, so it may already be right), and the tests of the flow rule.

**Open questions.** Whether the digest should include the recipient. What a body shared on purpose looks like (the acknowledgement text is fixed for everyone). The cost of one record for each send.

## 13. A reply after an unapproved escalation

**Problem.** A refund above 100 waits for a person for 24 hours. If nobody approves, the escalation is denied (`escalation-timeout`), the Desk is told `RefundFailed` and replies `Declined`, but the guest's last message is then 24 hours old, WhatsApp's window has closed, and the send is refused (`SendRejected`, AC15). The ledger is clear and the guest hears nothing.

**Evidence.** Scenario (1) of `test/after/demo-ledger-e2e.test.mjs`: `RefundFailed` delivered, `SendRejected` accepted, no reply heard, no refund. It is the behaviour of v1.3.0.

**Sketch.** One of: an escalation timeout shorter than the window (23 hours), so the reply is sent; the template retry that v1 leaves out (a message allowed outside the window, `std.channels.whatsapp`), used for this one case; or a notice to the staff that a guest was not answered.

**Touches.** The worker's escalation timeout (a default of 24 h), the WhatsApp library (templates, PS15 and AC15), the example and the demo copy, the recorded fixture and the runbook.

**Open questions.** Which of the three. Whether the timeout is a policy parameter. What template text is approved.

## 14. The model imprecision of the checker's witnesses

**Problem.** The witnesses of the Desk's path properties pass through `Found({count:0})` and then `Amounted(..., {count:1})`: the retrieval gave no item and the amount cites one. PS17.6 refuses that pair at run time (a citation is a subset of what the decision was given), so the witness shows that the text allows the path, not that a run can take it. A reader who replays it finds a step that cannot happen.

**Evidence.** The 10-step witness of the Desk on v1.3.0 with a ghost field (`docs/demo/ledger/v1.3.0-witness.check.txt`), and the 10-step witness of the variant of DF19 item 6; both have the pair. The release notes say so.

**Sketch.** Relate the two counts in the abstraction: the item set a decision cites has a count no larger than the item set it was given, so `Amounted.cites.count <= Found.items.count` for the pair of a citing decision and its retrieval. The checker explores the pairs that PS17.6 allows. A witness then replays.

**Touches.** poly-ref's exploration of `Items` (PS4.1, its representation by count `0..L`) and the dependence between a decision's `cites` and the items it received (PS17.6), the lowering's contract data domain, translation validation (the compared domain), the counts of every instance (they would fall), the witnesses' confirmation (`confirmWitness`).

**Open questions.** Whether the relation is an assumption of the model, printed beside K11 and K17, or a constraint of the step. How an instance with two retrievals in one Desk is related.

## 15. The robustness of the Docker replay test

**Problem.** A replay in Docker answered O3 (the build did not start in time) in the full run, while the machine was busy, and passed alone. A flake in the parallel group stops `npm test` before the serial group runs, so one release needed a split run.

**Evidence.** `test/demo-driver-hygiene.test.mjs` `(c3)`: `'O3' !== 'O2'` in the full run of 2026-10-20, 15 of 15 on its own; rehearsal finding F1 (poly starts over 15 s in the container); the sizes of the runs (`docs/demo/rehearsal-start-times.md`).

**Sketch.** A readiness probe in place of a fixed wait, a retry of a replay once when it ends O3 with the reason `did not listen`, a limit on how many container tests run at once, and a start timeout set from the measured start times with a margin. The test states in its message when it retried.

**Touches.** `demo/driver/replay.mjs` and the container's entry, the tests under `test/demo-driver-*.test.mjs`, the suite's concurrency for those files, the runbook.

**Open questions.** Whether a retry hides a real slow start (the retry is recorded as a count in the result). Whether the Docker tests belong in the serial group.

## 16. A way to declare a decision gated

- **Problem.** A decision that sends private text to a model is a credential-egress region. The check accepts it only when a policy rule names `decision.<name>`, so a rule is written to satisfy the check (`PL7001`, finding 1). The rule's content is arbitrary.
- **Proposal.** `gated by <policy>` on a decision, or a policy form `gate decision.<name> ...`, so the declaration, not a rule written for its side effect, is what the region reads. A declared gate that no policy of the scope backs is a diagnostic of its own.
- **Cost.** A grammar item, a lowering to the same `security.json` entry, and a read-back by poly-ref.

## 17. A check-time diagnostic when a decision lacks an audience

- **Problem.** A decision over a `Content` the host stored fails closed at run time with "no taint record (S302)" when the program declares no `audience`. The check is `CLEAN` (finding 2).
- **Proposal.** A diagnostic at check time when a decision's parameter is a `Content` and the program has no audience, naming the fix (`audience { public < x }`). It is a finding for the author, not a refusal.
- **Cost.** One rule in the validate stage; no lowering change.

## 18. The cut-point reduction for stored values compared with constants

- **Problem.** S458 cuts a range parameter at the constants it is compared with. A value a handler stores is explored whole, so a `0..500` amount compared with two thresholds exhausted memory (finding 3).
- **Proposal.** Extend the reduction to a state field that handlers only copy from a cut parameter and compare with constants, so the field is explored at the representatives of its classes. The lowered module is compared with the semantics at the greatest value of each class in every reached state, as S458 already requires for parameters, so the premise is checked and not assumed.
- **Cost.** An analysis over the handlers (the flow of PT3.4a already computes how a parameter reaches a field), an instance line that prints the field as cut, and a new entry in the toolchain faults for the broken lowering that misses a class.

## Conclusion

Fifteen proposals, three families. Five make the checker see more: per-order identity, retry safety as a type, the out-of-range outcome, the imprecision of the witnesses and signed invariants. Four make what the checker cannot see into events or contracts: contracts on handlers, taint per recipient, a reply after an unapproved escalation, and migration. Six are about the evidence around the checker: the baseline and the benchmark, calibration, the metamodel, related work, the room page and the replay test. The first and the fourteenth were found by the same finding in v1.3.1, and the twelfth and thirteenth by running its scenarios. None is started.

Proposals 16 and 17 remove an arbitrary rule and a silent failure. Proposal 18 removes the largest cost the examples met. Each is small against what it saves, and each has its check in the existing read-back and fault-list discipline.

## Glossary

- **Conceptual data layer:** a declaration of the entities of a source and their keys, so that a machine can read the key of a cited item.
- **Contract (on a handler):** a precondition and a postcondition that the runtime checks at the capability, on every call.
- **Cut point:** a constant a parameter is compared with; the check explores each side of it (S458).
- **Ledger:** the Desk's record of its refunds on a thread: `None`, `Unknown`, `Issued`.
- **Megamodel:** a graph of the models of a program and of how they relate.
- **Metamodel:** a machine-readable description of the language and its semantic domains.
- **Path property:** a property of the sequences of steps of a machine.
- **Region:** a set of effects behind a gate; `PL7001` reports one reached with no gate crossed.
- **Taint:** the class and owners of a body, kept by its digest (PS17.4).
- **Taint record:** what the runtime keeps about the audience of a stored body (PS17.4).
- **Window (WhatsApp):** the 24 hours after a customer's message in which a free-form reply may be sent (AC15).
- **Witness:** the steps by which the checker's model breaks a property; it may pass through a pair the run-time rules refuse.
