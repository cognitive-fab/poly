`# M7.5 · Work orders with budgets (S359): the proposed spec text and the choices the plan does not cover
`
`Status: **proposed, for the reviewer's ruling before anything is built.** It applies S522 as ruled (the budget sits on the workflow; amounts are currency micro-units from a price table the participant declares; the reservation is the cap) and the ruling of 2026-10-12 (self-reported usage never protects the budget; it is recorded and reconciled, and the reservation alone bounds the spend; a stop is trusted only when it is host-measured). Once ruled, the text moves into PS18, PT10 and PT24.6, and the tests are written from it.
`
`## What exists
`
`A workflow's effect kinds are work orders: the worker proposes each to the gate, issues it on an allow (`worker.ts` `issue`), and an agent's `workflow_report` settles it (S173). A workflow's tool map has no cost field (`ast.ts` `WorkflowTool`). Decisions have budgets: a `budget b` declaration with caps per run, scope or period, instances `budget:b:...` that the runtime dispatches `Reserve`, `Settle` and `Release` to, and `verdict {stage:'budget'}` events, with the reservation taken in the allow's transaction after the memory check and before the grant check (PS18.4, PT10k). K15 says a provider's usage report is the usage it bills; a work order has no provider.
`
`## The proposed text
`
`**PS18.7 Work-order budgets (S359, S522, S523).** A workflow may name a budget with `budget b prices "f" order cap <amount>`, written once, after its tools. `b` is a `budget` declaration of the module (`PL1001` otherwise); `f` is a price table the participant declares, read beside the source, in the currency of `b`'s caps (`PL6844`), with a source and a date (`PL6843`); the **order cap** is the most one order may cost, in that currency. The amount of a work order is in currency micro-units (PS18.3).
`- **The reservation is the cap.** When the worker would issue a work order, the budget check runs where a tier's call is checked: the order cap is the reservation against every cap of `b` that applies (the run's, the scope's, the period's), in the allow's transaction. An order whose cap does not fit what remains of any cap is denied with the reason `budget`, or escalated when `b` says `on exhausted escalate`, exactly as a decision's call is, and no order is issued: the effect's failure completion is delivered.
`- **Spend is the reservation.** An order settles for its cap, whatever the participant reports: the reservation alone bounds the spend. A usage report (an optional `usage` of `workflow_report`: classes of the price table to whole numbers) is recorded on the run in the `verdict {stage:'budget'}` event of the settle, priced with the participant's table, and **reconciled** against the reservation: `reconciled: "under" | "equal" | "over"`. An over-report is an overrun, recorded and never hidden; an under-report is not credited back. A report whose usage is not whole numbers of classes of the table is recorded as not priceable (S361) and changes nothing.
`- **A stop is host-measured.** The budget's refusal is made by the runtime from its own count of reservations. Nothing a participant says reduces a reservation or raises a remaining amount.
`- **The certificate** lists each workflow budget as `{ workflow, budget, prices, orderCap, usage: "self-reported", bound: "reservation" }`, so a reader sees that the usage figures are the participant's word and that the bound does not rest on them. `poly cost` sums a work order's settled reservation by run, scope and period and shows the reported usage and its reconciliation beside it.
`
`## The choices for the reviewer
`
`1. **Where the cap is written.** I propose the clause on the workflow (`budget b prices "f" order cap usd 0.05`), reusing the module's `budget` declaration for the run, scope and period caps. The alternative is one cap per tool (`tool "k" -> t … cap usd 0.05`), for workflows whose orders differ a lot in what they may cost. Recommended: the workflow clause; per-tool caps are a later refinement.
`2. **A failed order.** The plan's acceptance says a reservation is released on a failed order. Under the new rule, what an agent reports as a failure is self-reported, and a lapsed deadline does not tell the host that no work was done, so neither is a host-measured stop. Options: **(a)** never release: every issued attempt spends its cap, a re-issued attempt reserves again, and the acceptance becomes "an order the gate does not issue spends nothing" (host-measured by construction); **(b)** release on an agent-reported failure (weaker: an agent that fails and has spent is unprotected); **(c)** release a lapsed order only when the runtime recorded no claim of it (polycrew's `workflow_claim`), which needs the claim recorded as an event. Recommended: **(a)**. The plan's wording "released on a failed order" would then be amended in the record.
`3. **The participant's price table.** I propose reusing the model price table's shape (`perMillionTokens: { <class>: <micro-units> }`), so the same checks (`PL6843`, `PL1201`) and `costOf` serve, with the classes the participant names (for an agent, `input` and `output`; for a tool, a class such as `step`). The alternative is a new table kind with a per-unit field.
`4. **A kernel assumption.** K15 is about a provider's bill and is listed exactly when a route exists. I propose a new assumption, **K16**: *a work order's reported usage is the participant's own word and is never what bounds the budget*. It is listed in a certificate exactly when a workflow names a budget, and the broken variant that lets a report reduce the reservation is in the explicit list of toolchain faults.
`5. **The artefact rule (S524).** The workflow descriptor gains `budget: { budget, prices: { path, digest, currency, perMillionTokens }, orderCap }`; poly-ref reads it back from the source in `artefacts.ts` (the workflow row), and the faults `workflow-budget-dropped` and `workflow-order-cap-raised` join `test/toolchain-faults.mjs`. Load checks the descriptor's budget against the certificate, as it does for a decision.
`6. **What I will not build in M7.5:** a cap per tool, a lookup of an agent's real spend, and any release on a report.
`
`## Acceptance (as ruled in the plan, amended by choice 2)
`
`- A workflow whose orders together exceed the budget has the next order denied at the gate with the reason `budget`, with no order issued and the failure completion delivered (host-measured).
`- An order the participant reports as using less than its cap still spends the cap; one reporting more is recorded as an overrun; neither changes what remains.
`- The certificate lists the budget as self-reported with the bound the reservation, and `poly cost` shows the reconciliation.
`- The broken lowering that drops the budget, the one that raises the cap, and the one that lets a report reduce the reservation are each caught.
