# Review: identity and lineage proposal (PD5)

*Review of `docs/proposals/pd5-identity-lineage.md` (v0.1, not ruled), done as the PD review was: against the spec, with an independent script for the open question it asks to be settled by evidence. 30 September 2026. Nothing in PD5 or the spec is edited here; the S-numbers are for ruling.*

## Verdict

**The design principle holds; the text assumes more of the spec than the spec says.** Taking identity as a finite typed input, verified outside and explored inside, is PD1's move applied to a new input, and the script below supports its central technical claim: with principals compared only for equality, a small number of representatives decides the refund example exactly, and an order comparison breaks the symmetry the reduction relies on. But twelve places assume a rule, a field or a section the spec does not have (S101 to S112). Three matter most: claims are not part of a step's label, so neither the rejection row of PS3.2 nor the theorem of PS4.1b covers them yet (S101, S102); a `Tri` claim cannot be read by a handler under PS8.0 (S103); and lineage carried on messages breaks the multiset quotient of a configuration's state unless it is abstracted (S105). None of the four items needs a change to polyrun's kernel for checking; PD5.2's runtime lineage and PD5.4's workload signatures need engine changes, listed for JJ.

## 1. Consistency with the spec

Each reference PD5 makes was read where the spec defines it. Where PD5 assumes something the spec does not say, it is numbered.

| Reference | What the spec says | Finding |
|---|---|---|
| PT9.3 | The gate evaluates a proposal against the post-state of the emitting step. | Claims are not state, so they are not in that snapshot (S104). |
| PT9.9 | A cross-scope send is proposed with kind, target machine and scope, action and payload digest; a deny delivers `SendDenied`. | No lineage field in the proposal (S105). |
| PS3.2 | Five rows; row 2 is `rejected("outside-check-domain")` for data outside a `strict` domain. | PD5's `claims-unverified` is not row 2 (S101). |
| PS4.1b | "Checked is running" for inputs in `D(a)`, by strict rejection before the handler. | Claims and principals are outside `D(a)` as defined (S102). |
| PS8.7 | Cross-scope sends are proposed; the gate's decision is an environment choice in the checked configuration. | Agreed in principle; see S105 for what the checked state must hold. |
| PT8.5 | Obligation consistency: every mandate dischargeable (PS8.6). | PD5.3.3a cites it for a denial property it does not state (S106). |
| PT12 | Diagnostics, verdicts, witnesses, signed acceptances (PT12.5). | Not the certificate (S108). |
| PL6401 | A lint over the imports of the handler files `poly.json` names. | PD5 §0 overstates it (S111). |
| PD2 | `decision` events in the ledger, M4 with K10. | PD5.4 records claims at M4 that exist only from M5 (S112). |
| PD4 | Mode machines; the gate reads a mode by `machine("…").field`; per-mode dischargeability (PD4.4b). | `mode(…)` and "liveness" are not PD4's (S106); person attestation overlaps PD4.2a (S107). |

- **S101. The claims rejection is not a row of PS3.2.** PD5.1.2c says **run** rejects missing, malformed or out-of-domain claims "before the handler, and journals the rejection (PS3.2 row 2)", with reason `claims-unverified`. Row 2 is `rejected("outside-check-domain")`, and it applies to `d ∈ T(a)`; claims are not part of `d`, and a label is `(a, d, v)`. *Needs:* a label that carries claims, `(a, d, c, v)`; a new row before the handler, `c` missing or outside the claims type gives `rejected("claims-unverified")`; and PS9.1a's list of rows the runtime applies before the module extended to it.
- **S102. PS4.1b does not cover claims or principals.** The theorem rests on **check** offering every input in `D(a)` and **run** rejecting anything outside a strict `D(a)`. PD5.1.3 calls itself "PS4.1b applied to a new kind of input", but the claims domain is not in `D(a)`, and a `Principal` has no finite domain at all: **check** offers representatives, **run** sees real identities. *Needs:* the claims type in the check domain of the action, and a data-independence lemma (a handler that uses principals only by equality, storage and passing behaves the same under any injective renaming of principals) so the theorem extends from representatives to every principal. The script in section 3 supports the lemma on the example and shows where it fails.
- **S103. A `Tri` claim cannot be read by a handler.** PD5.1.2a allows `Tri` claim fields. PS8.0 says machine fields are never optional and every machine expression is `Bool`; a `require` demands `Bool`, and a `Tri` there is `PL1203`. `caller.attested` in a handler is therefore a type error, or the claims record is an optional input, which PS8.0 reserves for policies. *Needs:* a rule: either claims are total (a missing claim is S101's rejection, so `attested` is `Bool` or an enum), or handlers must test a `Tri` claim explicitly (`== T`), as PS8.0 does for policies.
- **S104. Policies cannot read claims.** PD5.1.2d has the gate read `step.caller.kind` "under the snapshot rule of PT9.3". The inputs a policy reads are the proposal, labels, `machine(…)` fields and history (PS8.0); the proposal (PT9.1) has no claims, and PT9.3's snapshot is a post-state, which holds no claims. *Needs:* the proposal to carry the emitting step's claims (or their digest and a reader), and `step` added to the policy inputs of PS8 with its optional type.
- **S105. Lineage on messages breaks the configuration's state.** PD5.2.2a gives every delivered message the lineage of the step it follows, with the digest of the previous hop. PS13.2a keeps μ as a multiset of message values `(target, action, data)`, exact because two copies are indistinguishable; a per-message lineage makes copies distinct, and a hop digest is unbounded, so the configuration is no longer finite. PD5.2.3's claim that "the checker knows which origin classes can lead to" each effect needs lineage in the checked state. And PT9.9's proposal carries no lineage token. *Needs:* lineage in **check** abstracted to its origin class (kind, and principal by representative), with the digest chain a runtime-only field outside the checked state; and the token added to PT9.9's proposal.
- **S106. Three PD5.3 references point at the wrong rule.** (a) PD5.3.3a cites PT8.5 for "in `Halted` no compensable or irreversible effect is admitted"; PT8.5 is obligation consistency (dischargeability), and the property PD5 wants is a denial over a region, which is polycheck's (PT8) and should be named as such. (b) PD5.3.3b calls PD4.4b "PD4's liveness obligation"; PD4.4b is a possibility property (PS8.6), and the difference matters: PD5 claims a halt "never strands work", which possibility does not prove. (c) PD5.3.2's `mode("Trust").level` is not a policy accessor; PD4.2b reads a mode as `machine("ops.OpsMode").mode` (PS8.5).
- **S107. PD5.3.2's example is not poly, and duplicates PD4.2a.** The `Trust` machine writes `state level: enum { … } = Normal` (no inline enum in the state grammar), `and` (poly has `&&`), and typed parameters in `on CredentialRevoked(p: Principal)` (parameter types are declared on `action`). The example in PD5.1.2 reads a `requester` field it never declares. Separately, PD4.2a already says a mode change needs a person's signature (PT12.5); PD5.3.3c makes leaving `Halted` need person *claims*. Two mechanisms for "a person did this" need one rule about which one governs a mode machine.
- **S108. Certificates are not PT12, and heads are ed25519.** PD5.4b cites PT12 for certificates; PT12 is diagnostics. The certificate is written and signed by `poly admit` (PT14), and the ledger's signed heads (PT16) are `{ …, alg: "ed25519", sig }`. X.509 SVIDs are commonly ECDSA P-256 or RSA, so signing heads with a workload's SVID needs PT16's head format to name other algorithms, and the verifier (Polyaxion's signature check, polysec's notary, which is ed25519 only) to accept them.
- **S109. `PL6702` is in the wrong range.** PT12.2 gives `PL6xxx` to policy admission, labels and capabilities, and `PL1xxx` to names, types and domains. `PRINCIPAL_NOT_OPAQUE` is a typing rule; `PL1206` is free and fits beside `PL1201` to `PL1205`. `PL6701 UNATTRIBUTED_EFFECT` is a policy finding and fits `PL67xx`.
- **S110. K11 assumes K10 is in PS10.** PS10 lists K1 to K9; K10 enters "when PD2 is built" (decisions-m1, M4). PD5 numbers its assumption K11 and proposes PD5.4 for M4 and the rest for M5, so K11 can only follow K10 if PD2 lands first. *Needs:* the rule that K-numbers are assigned when an assumption enters PS10, or PD5's dependency on PD2 stated.
- **S111. PD5 §0 overstates `PL6401`.** "Handlers hold no ambient authority (`PL6401`)": the lint rejects imports of named ambient modules in the handler files `poly.json` lists, and is listed as not run without that field (PT6.5, S72). It is a lint, not a capability boundary; the talking points should say so.
- **S112. PD5.4 is M4 but records what exists only from M5.** PD5.4a puts the claims that admitted a step and its lineage digest into the ledger's `step` record (PT16) at M4; claims are PD5.1 and lineage PD5.2, both M5. *Needs:* PD5.4a at M5 with PD5.1 and PD5.2, or the `step` record's fields reserved at M4 and filled from M5.

## 2. Codes

- `PL6701` and `PL6702` are unused: no occurrence in the spec, the other proposals, the decisions, the code under `packages/`, the vendored engines, the tests or the conformance sources. Only PD5 and the handoff name them.
- `K11` is unused anywhere; `K10` is named (PD2.3, PT18's M4 row) but not yet in PS10 (S110).
- The rejection reason `claims-unverified` does not collide. The reasons the semantics fixes are `terminal` and `outside-check-domain` (PS3.2); `unhandled` is a verdict, not a reason; every other reason is a program's own `reject` string, and none in the repository is `claims-unverified`. A program could still write `reject "claims-unverified"` itself; PS3.2 does not reserve the runtime's reasons, which is worth a sentence when S101 is ruled.
- `SendDenied` with reason `lineage` is new; PS8.7 leaves the reason to the gate, so it is consistent.

## 3. Open question 1: how many principals

`docs/reviews/evidence/principal_symmetry.py` models the PD5.1 refund example independently of the compiler and poly-ref: `Request(amount)` by a caller (an amount above the limit awaits an approval, one at or below it is refunded at once), and `Approve` by a caller with `kind`, `assurance` and `principal`, requiring a person, assurance at least 2 and a principal other than the requester, storing the approver and emitting the refund. The module has two `Principal` fields (requester, approver), so PD5's conjecture is three representatives. The property: no refund is emitted after an accepted approval whose principal is the requester. Every claim value is offered in every state. Guards are written as data, so the script sees every operation applied to a principal. Each run reports the reachable states, the states up to renaming principals (orbits), whether an approval is reachable at all, and whether the reachable set is closed under every renaming of the representatives.

| Model | n = 1 | n = 2 | n = 3 | n = 4 | Stable from |
|---|---|---|---|---|---|
| reference | 3 states, CLEAN, *vacuous* (no approval reachable) | 7 states, 4 orbits, CLEAN | 13 states, 4 orbits, CLEAN | 21 states, 4 orbits, CLEAN | n = 2 |
| mutant, no self-approval `require` | 4 states, VIOLATED | 9 states, VIOLATED | 16 states, VIOLATED | 25 states, VIOLATED | n = 1 |
| mutant, principals compared by order | flagged outside the rule | 6 states, not closed under renaming | 10 states, not closed | 15 states, not closed | (not trusted) |

The mutant without the self-approval `require` is violated at every n with the witness `Request(2) by p0`, `Approve by Person/2/p0`. The order mutant is flagged before its numbers are read (`lt` on a principal, which PD5.1.2b would refuse as `PL6702`), and its reachable states are not closed under renaming from n = 2, which is the failure of symmetry itself. A bound below the reachable states (at most 5 states at n = 4) gives `INCONCLUSIVE`, never `CLEAN`.

**What it shows.** On the example, the verdict stops changing at n = 2, and the orbit count is constant from n = 2 (4 for the reference, 5 for the first mutant), as data independence predicts. n = 1 is not enough even though its verdict is `CLEAN`: no approval is reachable when the only principal is the requester, so the verdict is vacuous. PD5's "fields plus one" (three) is sufficient here but not tight: the stored approver never meets a third principal in a guard, so what matters is how many principals a guard or property relates at once (here two: the requester and the caller). A rule stated that way, "the most principals any one guard, property or input relates, plus one", would be tighter and is what the lemma of S102 should prove; until then, fields plus one is a safe bound, and a vacuity check (is the guarded step reachable at all) should be part of the verdict.

## 4. Feasibility

Engines are vendored and never forked; a change an engine needs is listed for JJ and made in the engine's repository.

- **PD5.1 Verified claims.** *poly (compiler, poly-lang, poly-core):* the `claims` declaration, `by` on handlers, the `Principal` type and its opacity check, claims in the check domain (S101, S102). *poly-ref:* claims in the label and the explored inputs, principal representatives and the vacuity check (section 3); written from 04-semantics once S101 and S102 are ruled. *Lowering and polyrun:* claims can be lowered as extra fields of the action's data with their domains in `dataDomain`, so the module's strict schema already refuses out-of-domain values; but a *missing or malformed* claim with the reason `claims-unverified` must be refused before dispatch, which belongs in poly's host (`poly-runtime`, M4) with the verifier adapter, not in the kernel. **No kernel change**, if the host refuses and journals through polyrun's existing entry for a rejected step; if polyrun has no such entry for a reason the host chooses, that is one change for JJ's list (a host-supplied rejection journaled as a step). *Polyaxion:* reads claims only through the proposal (S104), which is poly-runtime's to fill.
- **PD5.2 Lineage.** *polyrun:* lineage computed at commit and carried on each outbox row (effects and messages) needs the kernel to record the emitting step's lineage on the row and the receiving step to inherit it: **an engine change** (JJ's list), in the same place as M3-2's `sendTo`. *Polyaxion:* a gate input for the lineage token on cross-scope sends (PT9.9), and token verification, which PD5.5 gives to the host's verifier: the gate needs the verified origin as a proposal field, not the token. *poly-ref:* origin classes in the configuration's state, abstracted (S105). `PL6701` is a poly-ref and polycheck finding.
- **PD5.3 Revocation.** Everything here is PD4 (mode machines, per-mode checks, M5) plus PD5.1's claims on `Restore`. **No new engine change** beyond PD4's; the denial in `Halted` is a polycheck region property over existing labels (S106).
- **PD5.4 Attributed provenance.** *poly-runtime (M4):* claims and lineage digest in the ledger's `step` record (PT16), poly's own code. *Polyaxion and polysec:* signing ledger heads and certificates with a workload SVID needs polysec's notary and Polyaxion's signature check to accept algorithms other than ed25519: **an engine change** (JJ's list, S108). RATS appraisal (PD5.4c) stays the host's.

**JJ's list from this review:** (1) polyrun: lineage recorded on outbox rows and inherited by the receiving step (PD5.2); (2) polysec and Polyaxion: signature algorithms beyond ed25519 for SVID-signed heads (PD5.4b); (3) possibly polyrun: a host-supplied rejection journaled as a step, if the existing entry cannot carry `claims-unverified` (PD5.1).

## Conclusion

PD5's principle is sound and its open question 1 has a clear answer on the example: equality-only principals make a small, exact representative set, two representatives decide the refund example, three is safe, one is vacuous, and an order comparison breaks the symmetry visibly. The proposal is not yet consistent with the spec. Claims need a place in the step's label, the rejection rows and the "checked is running" theorem (S101, S102); `Tri` claims and policy access to claims need a rule (S103, S104); lineage needs an abstraction before it can enter a checked configuration (S105); and seven smaller references are wrong or premature (S106 to S112). Two engine changes follow from PD5.2 and PD5.4 and go to JJ's list; PD5.1 and PD5.3 need none in the kernel.
