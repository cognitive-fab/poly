## 6. Spec issues

- **S23. `check-effects` does not accept an `unchanged` step (blocks the engine step).** Decision M1-1 says polyrun already treats every classification other than `rejected` and `unhandled` as accepted. The kernel and `check-product` do; `check-effects` lists `mutated` and `identity-by-mutation` explicitly (`check-effects.mjs:198`), so after 2.3.0 it would treat an emit-only step as a rejection and never count its effects. That silently weakens every path property over such a step. *Proposal:* in polygraph, change that line to "any classification other than `rejected` and `unhandled`", matching the kernel, with the polyrun test the handoff asks for. It is an engine change, so I wait for your approval.
- **S24. The OMS corpus cannot replay at 100%, and tests almost nothing (blocks AC1's replay).** All 81 windows of `machines/order/traces` have `post == pre`: every trace starts in `pending` and never leaves it, although the contract moves `SUBMIT` from `pending` to `fraudCheck`. The hand-written module passes 53/81, exactly the windows whose action it rejects in `pending`. The corpus appears to predate the module's migration to next-state semantics (polygraph commit `22c676f`), when acceptor writes were lost. No module that follows the contract passes all 81. *Proposal:* (a) keep the copied corpus and gate it as S1 did for raft, window-by-window identity with the hand-written module (53/81); and (b) add a second, meaningful corpus, produced by running the hand-written OMS artefacts through polyrun's own kernel along the sixteen scenarios the file names describe and exporting the journal with `polyrun export-traces`, copied with provenance that says how it was made. Gate the poly order at 100% on (b). Alternatively, the corpus is regenerated upstream in polygraph, which is your change to make.
- **S25. Action data that is an object without a tag (blocks the OMS rewrite).** polyrun delivers a child's completion as `{ childKey, childState }`, where `childState` is the child's terminal state object, such as `{ shipState: "delivered" }`. poly has no type for an untagged record: a union value always carries its constructor. *Proposal:* record types, `type ChildState = { shipState: ShipState }` (PT2 `TypeDecl`, PT3.1), finite when their fields are, lowered as a plain JSON object, compared field by field, and usable as a parameter type. PS1.4 already speaks of records as the payload of a constructor; this names them as a type.
- **S26. When does `after` emit `cancelTimer` first?** PT6.3 says arming a key that "may already be armed" emits `cancelTimer` then `timer`. Timers are not state (PS1.2), so the compiler cannot know whether a key may be armed. *Proposal:* every `after` emits `cancelTimer` then `timer`, as the literal rule reads. The OMS hand-written mapper emits `timer` alone, so the AC1 comparison of `check-effects` results must not count `cancelTimer` intents; I confirm first that polyrun accepts a `cancelTimer` for an unarmed key without poisoning.
- **S27. `check-product` needs invariants the OMS example does not have.** polyrun refuses a product check with no cross-machine invariants, and the OMS example ships none. *Proposal:* write the product invariants once, as `compose invariant`s in the poly source (for example: a completed order has as many delivered shipments as fulfillments; no shipment is spawned before the order is charged), hand-write the same predicates as an `invariants.compose.mjs` for the hand-written run, and compare the two `check-product` results.
- **S28. Machine ids.** polyrun names machines by a `machineId` (`order`, `shipment` in the OMS config); poly names them `module.Machine`. *Proposal:* the lowering uses `<module>.<Machine>` as the machine id (the PT1.5 build directory name), and the AC1 comparison maps ids before comparing. No spec change unless you want PT1.5 to say so.
- **S29. A send to `none`.** PS1.6 makes `none` the empty address, and PT7a's order starts with `inv: Ref<Inventory> = none`. Nothing says what `send none <- A()` means. *Proposal:* in a configuration it is a finding, `PL5404 SEND_TO_NONE`, with its path; in a single-machine check it is an ordinary intent, completed by the environment. This needs a new code.
- **S30. What a single-machine check does with `send`.** PS13.3 defines sends inside a configuration; a machine checked alone (PS4) has no receivers. *Proposal:* a send is an intent in `E` like an effect; a machine checked alone treats it as the environment treats any intent (PS4.4), and its receiver's replies are ordinary actions offered in every state. No spec change: this is how I read PS4.4 and PS13.3 together. Stated here so it is agreed rather than assumed.
- **S31. `InputRef` has no production.** PT2's `Inputs = "inputs" "{" InputRef { "," InputRef } "}"` never defines `InputRef`, and PT7a writes `order[*].Place`. *Proposal:* `InputRef = Ident [ "[" ( Int | "*" ) "]" ] "." Ident`.
- **S32. How a configuration property names an instance's field.** PT7a writes `count(order[*] is Done)`, `init(inv.onHand)` and `order[i] is Asked`. That is, `order[*]` or `order[i]` stands for the instance's control field, and `inv.onHand` for a field. *Proposal:* in a configuration property, `g[i].f` and `x.f` name field `f` of an instance; `g[i]` alone, and `g[*]` inside an aggregate, stands for its control field, so `is` applies to it. A field access on an instance is legal only here, never inside a machine (PS1.6: nothing reads another instance's state).

- **S49. Shipments spawned in a loop.** The hand-written OMS mapper spawns one shipment per fulfillment, keyed `f0`, `f1`, …, in a loop; poly has no loop and no computed key. *Proposal, in the direction of the ruling:*
  - A child key may be indexed: `spawn Shipment as f[i] -> Start(…)` lowers to the key `f<i>` (`f0`, `f1`, …). `i` has an integer range type, so a family `f` has finitely many keys, the checker knows them all, and `signal f[i] -> A()` names one of them the same way.
  - A bounded loop, `for i in 0..n { … }`, is unrolled at compile time. `n` is an integer literal, or a field or parameter whose type is a range `0..K`: the body is then unrolled for `i` in `0..K`, each copy guarded by `if i <= n`. No unbounded loop, and no key built from a string at runtime.
  - Inside the body, `i` is a `let`-like binding of type `0..K`; the checker's per-path rules (PL2102, PL2301, PL5101) see the unrolled copies, so two copies that spawn one key are PL5101 as before.
  - A compose invariant reaches a family through the configuration forms S32 already defines: `forall i in f: f[i] spawned implies children.f[i].ship != Pending`, and `count(children.f[*].ship == Delivered)`, with `f[i] spawned` narrowing `children.f[i]` (S48).

- **S56. Liveness in a configuration.** PT7a writes `liveness settle: forall i in order: order[i] is Asked leads to order[i] is Done | Refused`, with no `under fair` clause and with a quantifier over the whole `leads to`. PT2's `Liveness` production requires `under fair { … }` and has no quantifier prefix. PS13.6 already says the quantifier scopes over the `leads to`, and PS14.2 makes delivery fairness automatic. *Proposal:* in a configuration, a liveness property takes an optional prefix `forall i in g:` over the whole `leads to`, and an optional `under fair { … }`; delivery is fair by PS14.2, and an input is not assumed fair unless the clause names it. In a machine the clause stays required. M1 lists every liveness property as not run, so no M1 result depends on this.
- **S57. The domain of `Ref<M>` in a single-machine check.** M0 read PS1.6 as `{ none }` for a machine checked alone (`types.ts`, `model.ts`). PS1.6 gives the domain only inside a configuration. With `{ none }` alone the check is unsound as soon as a handler compares addresses: `require from == owner` is explored only where both are `none`. *Proposal:* alone, a `Ref<M>` field or parameter ranges over `none` and `n` addresses `M#1 … M#n`, where `n` is the number of `Ref<M>` fields of the machine plus the largest number of `Ref<M>` parameters of one action. An address is only compared with `==` or passed on (PS1.6), and a state and one step's data hold at most `n` addresses of `M`, so every pattern of equalities among them is realised: the check is sound, and it adds no behaviour a real run cannot have. In a configuration PS1.6's domain applies unchanged.
- **S58. `send` and `self` at runtime.** PT7a lowers `send` to a built-in intent `sendTo { target, action, data }`, and architecture §2a lists it as a polyrun change. polyrun does not have it yet: the kernel poisons on an intent kind it does not know (`kernel.mjs`, "effect mapper emitted undeclared kind"), and `check-effects` reports it as `mapper-defect:undeclared-kind`. The mapper also has no instance id, so it cannot write `self`. *Proposal:* lower `send r <- A(d)` to `{ kind: "sendTo", target, action: "A", data }` as PT7a says, an address as the target instance's id and `none` as `null`. `self` is legal only as a whole argument of a `send` (M1), and lowers to the marker `{ "$ref": "self" }`, which the kernel replaces with the sender's instance id when it writes the outbox row. Until polyrun has `sendTo`, stage 3 of a machine that sends is poly-ref's alone and says so, and a module that sends does not run under polyrun. `send … as n` names nothing in PS or PT, so it is refused (`PL0901`) until it does. The polyrun change joins the owner's list.
- **S59. `SendDenied` needs trust scopes (blocks `SendDenied`).** PS8.7 delivers `SendDenied(to, action, reason)` only for a send that crosses trust scopes, and a trust scope is the scope of a module's policy (PT8, PT9.9), which M3 builds. In M1 no send crosses a scope, so no `SendDenied` is ever delivered, and no M1 check can observe one. *Proposal:* M1 does not build `SendDenied`; it arrives with the gate in M3, with the environment's choice among allow, deny and escalate. In M1 an action named `SendDenied` is an ordinary action.
- **S60. `spawn detached` (blocks detached children).** PT6.4 says `as pay` binds a `Ref`, but not where: a field, or a name local to the handler. A handler is pure, so the new address must be known before the kernel creates the instance. PS13.3 creates instances "with fresh addresses", without saying which group of the configuration they join (for `forall` and `count`), in which state they start, or what `N` counts. polyrun has no detached spawn: `spawnChild` always makes an attached child. *Proposal:* the new instance's address is `<parent address>/<k>`, so it is known in the handler; `k` is a local of type `Ref<M>` that the handler may store; the instance starts at `M`'s initial state and takes its creation action (S43) as its first message; in a configuration, instances spawned from `M` form the group `M`, and `N` counts every instance; polyrun gains a `createInstance` intent. Until ruled, `spawn detached` stays `PL0901`.
- **S61. The other intents of an instance in a configuration.** PS13.3 says an accepted step's "other effects are completed by the environment, as in PS4.4". In a configuration the environment's moves are the declared `inputs`, so a completion action not listed there is never offered, and a completion listed there is offered in every state (PS4.4). *Proposal:* that reading, stated in PS13.3: effects and timers of an instance are completed only through declared inputs. An instance whose machine spawns attached children would need its joint machine (PS7) inside the configuration, a third `System`; M1 refuses it with `PL0901`.
- **S62. A configuration without bounds.** PT2's `Configuration` production makes `bounds` optional, and PS13.1 says a configuration declares `B`. Without `B` the exploration need not end. *Proposal:* `bounds { transit n }` is required (`PL1201` at the configuration); `instances n` is required only when a machine of the configuration spawns detached children (S60).
- **S63. PT7a's inventory reports `PL4002` alone.** S33 makes an accepted step that emits and leaves the state unchanged `PL4002`, whatever the intent. PT7a's `Inventory` answers `Query` with a `send` and no write, and `Take` with `onHand = 0` answers `OutOfStock` the same way. So each is `PL4002` when the module is checked, although PT7a calls both machines "safe on their own". A reply is what a service does once per request; in a configuration each request is one message, which takes one step (PS13.3, PS14.3), so the repetition S33 describes needs another request. *Proposal:* S33 counts effects, timers and child intents, and not `send`: the consequences of a repeated send are checked where its receiver is, in a configuration. *Until ruled:* S33 applies as written, so `poly check` on the checkout module reports `PL4002` on `Inventory.Query` and `Inventory.Take`, and the file's verdict is `FINDINGS` while its configuration is clean.
- **S64. PT9.8's `in-order` also breaks when M1 steps twice.** PT9.8 states `invariant in-order: steps[M2] == 1 implies steps[M1] == 1`, and `delivery_check.py` checks "M2 has stepped and M1 has not" (`steps[M2] == 1 and steps[M1] == 0`). - **S65. How a union with payloads lowers below the top of a field.** Step 10 lowers what M0 refused: maps whose values are unions with payloads, a payload that is itself such a union, and action parameters of such a type. PS9.1b flattens a union only where it is a state field, into a tag and one nullable field per payload name, because the sealed model shape is flat. It says nothing of a union inside a map, a payload or a parameter, where no flat key exists for it. *Proposal:* there it lowers to one JSON object, `{ "$": "C", p: v, … }`, the constructor under `$` and exactly its own payloads, each lowered by the same rule; a union with no payload anywhere stays its constructor's name (PT3.1). This is the value the generated handlers already build (`{ $: "C", … }`), so only the edges change: a flat payload field or a map value holds such an object, and a parameter's schema says `object`. α reads the object back, and translation validation compares the flat values exactly, so a stray key is a `PL2501`. Effect parameters and a child's `childState` are left as they are: polyrun passes a child's flat snapshot, and an intent's payload carries no type from which poly-ref could rebuild the object; both stay `PL0901`, now "after M1".
