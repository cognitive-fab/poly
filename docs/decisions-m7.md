## M7.1 · `poly export traces`

### M7.1 spec text (PS19, PT29)

Committed alone, before any test or code (rule 7a).

- **A correction of the inventory, affecting S503.** The M7.0 inventory said it was open whether a poly effect declares reversibility. It does: an effect's `class` is `none | reversible | compensable | irreversible` (grammar `Class`, PT6.1, the manifest, the gate). The ruling for S503 asked for an optional `consequence` declaration with those four words. Adding a second declaration of the same thing would be a duplicate, so the spec text makes the consequence of an effect its `class`, and an effect with no `class` exports as `unknown` (PT29.6). This is the ruling's intent with no grammar change. Reviewer to confirm.
- **A correction affecting S504.** The certificate's `domains` are text (`field ∈ 0..3`), not a form a program can read. The check domain of a parameter is read from the certified sources, which the certificate binds by digest and `replay` already reads (PT29.3). No runtime change, as ruled.
- **Run ids are tokenised.** An instance id can be built from a message id or a key, so the episode id is a salted token (PS19.1, PS19.4). No time of day is exported.
- **Command shape.** `poly export traces` takes `--db --build --certificate --trust --out`, refuses an existing file, and is not served over MCP (PT29.1).
- **Accepted by the owner's reviewer, 2026-10-11:** S503 corrected (the consequence is the effect's existing class, and no class exports as unknown), S504 corrected (the domain is read from the certified sources), tokenised run ids with no time of day, and the command shape.

### M7.2 · the S508 check (read-only, before anything is built)

polyx's `synthetic` adapter (`@cognitive-fab/polyx-lens` 0.3.0, `src/ingest/synthetic.ts`) reads `{corpus, interactions:[{id, operator, team, agent, startedAt, outcome, turns:[{speaker, intent|button|event, slots, result}]}]}`. A turn with `speaker: system` and an `event` is a state event: the alphabet (`alphabet.synthetic-state.yaml`) gives its type `identity` and `state` slots, and `no-X-unless-state` reads the latest state event whose identity slot equals X's. The adapter carries `result` (`ok | failed | refused`) and an `outcome`. It reads slots as scalars. So it can carry what a poly trace has: **S508 passes, nothing is stopped, and the lens is not changed.** Limits found, to be written into the port text: slots are scalars only (a value or a token is one; a union with a payload is not, so the port flattens it as the journal does); one interaction is one episode (`expected_episodes: 1`), which is S506's "an interaction is a run"; `consequence` is declared per type in the alphabet, not per event, so the port gives each action one consequence from the effects it emits (or `unknown`).

**The suite's 2 skipped and 4 waiting tests, named (reviewer's request).** Skipped: (1) `PS15.4, E13: until the kernel can create an instance, an inbound message that would create the application is refused` is skipped because the vendored kernel now has `createInstance` (E13), so the real path is tested by the test above it; (2) `S152: enforcement through an OpenShell gateway` is skipped because no gateway is configured (`POLY_OPENSHELL_GATEWAY`), and enforcement needs one on Linux 6.2 or later. ### The inbox defect: which case held (reviewer's question of 2026-10-12; read from the sources, no job run)

**Case 2 holds: `failed` includes ambiguous outcomes, so a retry can leave two drafts.**
- The handler (`examples/inbox/host/drafts.mjs`, `createDraft`) posts once and throws on anything but a 200: a transport error, a timeout or a dropped connection after Gmail may already have made the draft throws exactly as a 500 or a 403 does. None of them is marked permanent.
- The runtime (`packages/poly-runtime/src/worker.ts`, `failed`, `boundOf`) treats a thrown, non-permanent error as `HandlerFailed` and retries the handler (bound 3 by default; `createDraft` declares no `retry`), so the retry loop itself can post a second draft before any completion is delivered. Only a permanent error is final (S138), and a crash is `lost`, never permanent.
- When the attempts are used up, `createDraft` declares no `exhausted` completion, so the runtime delivers its `failed` completion: `failed -> NotCreated()` (inbox.poly:443), which puts the Todo back to `Drafted`, and the next `Propose` posts again. Gmail drafts carry no idempotency key, so no layer can tell the second post from a first.
- So the witness's path is real in the ambiguous case, and `count("gmail.createDraft") <= 1` was not wrong as a rule; it found a defect. (The count is of effects proposed, and a definite failure followed by a retry is correct; the defect is that a definite failure and an ambiguous one are not told apart.)

**The fix, as ruled (not yet made; it needs inbox checks, which wait for JJ):** an ambiguous outcome is its own outcome. (1) `createDraft` is attempted once (`retry` with one attempt), since an irreversible effect with no idempotency key must not be retried by the runtime. (2) The handler throws a permanent error for a definite refusal (a 4xx), so that is `failed -> NotCreated()` and a retry by the Todo is correct; any other outcome (transport error, timeout, 5xx) is ambiguous and is delivered as `exhausted`. (3) `exhausted -> DraftUncertain()` takes the Todo to a new status `Uncertain`, outside `Proposed`, from which only a person's report that the draft exists (`Created`) or does not (`Drafted`) leads on. (4) Then `count("gmail.createDraft") <= 1` holds or its refined form does: the created-drafts rule (the `Created` completion reached at most once) is promoted. Order: a test from the witness, seen failing; the fix; the checks; the promotion; release notes naming the defect and that drafts are off by default (read-only mode), so no user has been exposed.
