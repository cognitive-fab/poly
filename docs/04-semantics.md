# poly · Semantics

*Cognitive Fab · September 2026 · draft v0.6 · specification only, no code*

This document defines what a poly program means. The functional (`PF`), architecture (`PA`) and technical (`PT`) specifications defer to it. Where they disagree with it, this document is right and they are wrong. Requirement ids here are `PS`.

The definitions are mathematical and short. They are written so that a reference interpreter can be built directly from them, with no code shared with the compiler (PS9).

## PS1. Machines and states

- **PS1.0** **Programs and modules (S176).** A **program** is a finite set of modules. A machine is named by its module and its name, `m.M`, and two machines are the same only when both are. `use m` makes the machines of module `m` nameable in a module as `m.M`; it adds no behaviour, no state and no message. PS1.6 to PS13 read `M` as the qualified name throughout.

  **Enums across modules (S190).** An enum is identified by its module and its name, `m.E`, and two enums are the same type only when both are: two enums with the same members in different modules are different types, and a value of one where the other is expected is `PL1201`. `use m` makes `m`'s enums nameable as `m.E`, as it does its machines, and `use m.E` makes `m.E` nameable and nothing else of `m`. A member is written `m.E.C`. A bare member `C` is allowed only where the expected type fixes the enum; elsewhere a bare member of another module's enum is refused, and so is a bare member that would name a member of more than one enum. A value of `m.E` is compared with `==` and `!=` and taken apart with `match`, which must cover every member of `m.E`, exactly as for an enum of the module itself, in handlers, guards, properties and configuration properties alike. Only payload-free enums cross modules: a record, a union with payloads, or a map of another module's types is `PL0901`. Where an enum is declared changes nothing else: `T(f)` for a field of type `m.E` is the set of `m.E`'s members (PS1.2), and check explores every one.
- **PS1.1** A machine `M` is a tuple `(F, init, A, H, G, term)`:
  - `F` is a finite, ordered set of fields. Each field `f` has a type `T(f)` and a check domain `D(f) ⊆ T(f)`. The first field is the **control field**.
  - `init` is the initial state.
  - `A` is a finite set of actions. Each action `a` has a parameter record type `T(a)` and a check domain `D(a) ⊆ T(a)`, the product of its parameters' check domains.
  - `H` maps each handled action to its handler.
  - `G` is the ordered list of guards (`guard all when … reject …`).
  - `term` is the terminal predicate.
- **PS1.2** A **state** is a function `s` from `F` to values with `s(f) ∈ T(f)` for every field. `S` is the set of states. The state contains the declared fields and nothing else: no verdict, no pending effects, no timers.
- **PS1.4** **Types.** The value types are `bool`, integer ranges, `int`, `string`, finite maps with enum keys, and **tagged unions**. A tagged union `U = C1 { p1 } | … | Cn { pn }` has constructors `Ci`, each with a record of named payload fields `pi` (possibly empty). Its values are pairs `(Ci, r)` with `r` a record of the payload types of `Ci`. An enum is a tagged union whose constructors have no payload. A union is finite when every payload field's type or check domain is finite.
- **PS1.4a** **Content (S180).** `Content` is an opaque reference to a body, identified by the SHA-256 digest of the body's bytes, or `none`. A module may store a `Content`, pass it, and compare two with `==` and `!=`; no other operation reads it, so an order, arithmetic, a comparison with a string, a map key, a record field, a `match`, a check domain or any other use is `PL1209 CONTENT_NOT_OPAQUE`. The only constant of type `Content` is `none`: a digest written in source is `PL1209`, and a body enters only at run time, through ingress or the runtime's content store. The type has no finite domain of its own; **check** explores it by representatives (PS4.1f).
- **PS1.5** **The control field may be a union.** `term` then depends only on its constructor. So `terminal intent is Done | Denied | Dead` is a predicate on the tag.
- **PS1.6** **Addresses.** `Ref<M>` is the type of addresses of instances of machine `M`. An address is a value: it can be held in state, carried in a message and compared with `==`. It cannot be dereferenced; nothing can read another instance's state. `none` is the empty address. In a configuration (PS13), the check domain of a `Ref<M>` is the set of addresses of the configuration's `M` instances plus `none`, so it is finite. In a machine checked alone, a `Ref<M>` ranges over `none` and `n` symbolic addresses `M#1 … M#n`, where `n` is the number of `Ref<M>` fields plus the largest number of `Ref<M>` parameters of one action; when `M` is the machine's own type, `self` is one more distinct address (S57), and each key of a detached spawn of `M` adds one more (S78). A detached child's address `<parent>/<k>` is absolute from the commit of the step that creates it (S78). An address is only compared with `==` or passed on, and a state and one step's data hold at most that many addresses of `M`, so every pattern of equalities among them is realised: the check is sound, and it adds no behaviour a real run cannot have.
- **PS1.7** **A machine may be a service.** `service` marks a machine that is never terminal (an inventory, a ledger). It is exempt from the per-instance deadlock check of PS5.6 and is covered by the configuration's quiescence check instead (PS13.6).
- **PS1.3** `term(s)` depends only on `s(control field)` (PT4.4a).

## PS2. Handlers denote functions

- **PS2.1** A handler for action `a` denotes a function

  ```
  h_a : S × T(a) → Verdict
  Verdict = accept(w, E) | reject(r)
  ```

  where:
  - `w` is a partial function from fields to values: the writes;
  - `E` is a finite sequence of effect intents (effects, timer sets and cancels, spawns, signals), in statement order;
  - `r` is a reason, a string literal from the handler's text.
- **PS2.2** A handler body is evaluated against the pre-state `s` and the data `d` as follows:
  0. **Names.** A bare name denotes the innermost binding: a local (`let` or a pattern binder), then a parameter of `a` (a component of `d`), then a field (a component of `s`). `pre.f` always denotes `s(f)`, so a field hidden by a parameter of the same name stays readable (S19).
  1. **Guards.** The guards in `G` are evaluated in declaration order, against `s`, `a` and `d`. A guard sees the parameters of `a` only where `action == A` narrows the action; elsewhere a bare name is a field (S19). The first guard whose condition holds yields `reject(r)` with its reason.
  2. **Body.** Statements are evaluated in order:
     - `require c else reject r` yields `reject(r)` if `c` is false and continues otherwise;
     - `reject r` yields `reject(r)`;
     - `let x = e` binds `x`;
     - `if c B1 else B2` evaluates the chosen branch;
     - `f' = e` adds `f ↦ value(e)` to `w`;
     - `f' = f with [k] = v` adds `f ↦ s(f)[k := v]` to `w`. Entry writes to one map on one path combine when their keys are distinct constants after unrolling (literals, constructors, or the index of different copies of a loop): `w(f) = s(f)[k1 := v1][k2 := v2]…` (S55);
     - `match e { C1 {x…} => B1 … _ => Bn }` evaluates `e`, binds the payload of the first arm whose constructor (and literal payload, if written) matches, and evaluates that arm's block. The compiler requires the arms to be exhaustive (`PL1501 NON_EXHAUSTIVE_MATCH`). So `match` never falls through, and handlers stay total;
     - `f' = C { q: e … }` writes a whole union value. A union field is always written as a whole value, never one payload field at a time;
     - `emit`, `after`, `cancel`, `spawn`, `signal`, `send`, `decide` and `adjudicate` append an intent to `E`. `adjudicate d as o` appends an intent of kind `outcome.d` carrying `o`; it is an effect of class `none`, so path properties count it like any other (S129). `send r <- A(d)` appends a **message** to the instance at address `r`; `self` is the sending instance's own address. An effect is also a message: `emit k(d)` sends `d` to the host actor that performs kind `k`, whose address is the handler's capability (PS1.6, PT6.5).
  3. **End.** If the body completes without a rejection, the result is `accept(w, E)`.
- **PS2.3** **Expressions read the pre-state only.** A primed field is write-only. Reading `f'` is a compile error (`PL1202 READ_OF_PRIMED_FIELD`). So the order of assignments within a handler does not change the result.
- **PS2.4** A field written twice on one control path is `PL2102 DOUBLE_WRITE`. A map is written twice when it is assigned twice, assigned and also written by entry, written twice at one constant key, or written at a key that is a field or a parameter on a path that writes another of its entries (S55). Therefore `w` is well defined.
- **PS2.5** All expressions are total (PT2.2): integer division truncates toward zero, `%` takes the sign of the dividend, and a divisor that may be 0 is rejected at compile time (`PL1204`). So `h_a` is a total function. **A machine is deterministic in its inputs**: for each state and each input there is exactly one verdict.

## PS3. Steps and the transition relation

- **PS3.1** A **label** is a triple `(a, d, v)` of an action, its data and a verdict kind:
  - `v = accepted(E)`;
  - `v = rejected(r)`;
  - `v = unhandled`.

  **Claims (PD5.1.2c, S101).** For an action whose handler is written `by c: C`, the label is `(a, d, c, v)`: the claims `c`, a value of the claims type `C` that a verifier outside poly asserts for the caller, are part of the label and the handler reads them as `c`. Every other action's label has no claims.
- **PS3.2** The transition relation `R_M ⊆ S × Label × S` contains exactly these triples `(s, (a, d, v), s')`, for every `s ∈ S`, `a ∈ A` and `d ∈ T(a)`:

  | Condition | Verdict `v` | Next state `s'` |
  |---|---|---|
  | `term(s)` | `rejected("terminal")` | `s` |
  | `d` violates a `strict` check domain of `a` (PT3.4) | `rejected("outside-check-domain")` | `s` |
  | `a ∉ dom(H)` | `unhandled` | `s` |
  | `a` requires claims of type `C`, and `c` is missing, malformed, or not a value of `C` (PD5.1.2c, S101) | `rejected("claims-unverified")` | `s` |
  | `d` holds a `Content` that names no body in the content store (S180) | `rejected("content-missing")` | `s` |
  | `h_a(s, d) = reject(r)` | `rejected(r)` | `s` |
  | `h_a(s, d) = accept(w, E)` | `accepted(E)` | `s ⊕ w` |

  `(s ⊕ w)(f) = w(f)` if `f ∈ dom(w)`, and `s(f)` otherwise. This is the **frame**: every field not written is unchanged.

  **Unhandled before data (S180 ruling).** An action with no handler is `unhandled` whatever its data: the claims and content rows apply only to a handled action. The claims row could never apply to an unhandled action, since claims are bound by a handler's `by c: C`; it moved with the content row so that the table states the rule once. The `content-missing` row was first written before `a ∉ dom(H)`, which made an unhandled action that carries a `Content` rejected when its body was missing; polyrun, which never sees an action outside the module's surface (PS9.1a), answers `unhandled`, and the table now agrees with it.

  **Data outside the type (S140).** The relation has steps only for `d ∈ T(a)`. An input outside its action's type is no label of `R_M`: the runtime refuses it before any step, with an error and an audit row and no journal row, as it refuses an outside completion (K9, K10). Replay never meets such a row.

  **Missing bodies (S180).** The `content-missing` row is applied by the runtime before it calls the module, from its content store: the step is journaled, the state is unchanged and nothing is emitted. In **check** every representative names a body, so the row never applies there; a `content-missing` step of **run** changes no state and emits nothing, so every invariant, step property and path property that holds on **check** holds on the paths of **run** that contain it, and a reject property cannot name the reason, as it cannot name `poisoned` or `archived`. **Erasure (S205).** The content store is erasable: the runtime's erasure of a body deletes it and keeps its digest, with an erasure record journaled on the runtime's own `runtime:content` run. An erased body stays erased: every later step whose `Content` names it is `content-missing`, and the same body presented again is not stored again. Only bodies and addresses (PS15.4) are erasable; the records the journal and the ledger keep by digest are not.

  **Reserved reasons (S101, S127, S180).** The reasons the runtime uses are reserved: `terminal` and `outside-check-domain` (the two rows above), `poisoned` (an instance the kernel has poisoned), `archived` (K4), `claims-unverified` (the claims row above), `content-missing` (the content row above), and `unknown-thread`, `thread-not-started` and `creation-unavailable`, with which the runtime refuses an inbound message (PS15.4). A handler's `reject` may not use them (`PL1207 RESERVED_REJECT_REASON`), so a rejection's reason always says whether the runtime or the module refused the step.
- **PS3.3** **Rejected and unhandled steps are steps.** They are transitions whose next state equals their current state, and they carry their verdict in the label, not in the state. They are journaled, they appear in traces, and properties over labels see them (PS5). Properties over states cannot distinguish them from not taking a step at all. This is the answer to the question "is a rejected step a step?": it is a labelled stuttering step.
- **PS3.4** An accepted step may leave the state unchanged (for example `Pay` in PT4.5, which only emits). It is still accepted, and its label carries its effects.

## PS4. Behaviours and the checked instance

- **PS4.1** The **environment** chooses each action and its data. A **path** is a finite sequence `s0 l0 s1 l1 … sn` with `s0 = init` and `(si, li, si+1) ∈ R_M` for every `i`. A **behaviour** is an infinite such sequence.
- **PS4.1a** **One machine, three interpretations of the environment.** The machine is the pure transition relation `R_M`. The environment is an interface with two operations:

  ```
  Env = { offer   : History → (Action × Data)          -- what happens next
          complete: Intent  → Completion               -- what the world does with an effect }
  ```

  Checking, simulation and running are three interpretations of `Env`, and nothing else:

  | Interpretation | `offer` and `complete` | What it produces | Engine |
  |---|---|---|---|
  | **check** | every action and every data value in `D(a)`, in every state; every completion | the set of all paths of `I` (nondeterminism) | polygraph, polyrun `check-effects`, poly-ref |
  | **simulate** | sampled from declared distributions and rates | a probability measure over paths (v2) | Polytrion |
  | **run** | whatever the world sends; intents go to real handlers under the effect gate | the one path that happens (IO) | the runtime |

- **PS4.1b** **Theorem (checked is running).** Every path produced by **run** whose inputs lie in the check domains is a path of **check**. *Proof:* the two interpretations apply the same `R_M` (PS2.5, and PS9 for the lowered module under K7), and **check** offers every input in `D(a)` in every state and every completion for every intent. For fields in `strict` mode, **run** cannot offer an input outside `D(a)`, because the runtime rejects it before the handler (PS3.2), so the condition holds by construction. For fields in `disclosed` mode, the theorem covers exactly the paths whose inputs stayed in the domain, and the others are journaled as drift. ∎ So every safety property that is `CLEAN` on **check** holds on every such **run** path.
- **PS4.1c** **Principals (PD5.1.3, S102).** A `Principal` is an opaque identity: a module compares it only for equality with another, stores it or passes it (`PL1206` otherwise). *Lemma (renaming invariance):* in such a module, for every bijection `π` on principals, `(s, l, s') ∈ R_M` iff `(π s, π l, π s') ∈ R_M`, since no handler, guard or property can tell two principals apart except by equality. So PS4.1b extends to claims and principals: every path of **run**, whatever principals it carries, is the renaming of a path of **check** over a finite set of representatives, provided the set is large enough. **check** offers every claims value, with every representative for each `Principal` field, in every state where the action can arrive. The number of representatives is the number of `Principal` positions in the state (a map holds one per key) plus the most principals one label carries (its parameters and its claims, at least one), and never fewer than 2; with one principal per label this is S102's rule, the positions plus one; the verdict prints it in its instance. A tighter bound enters only with the lemma's proof.
- **PS4.1f** **Content (S180).** *Lemma (renaming invariance):* in a module where `Content` is opaque (PS1.4a), for every bijection `π` on bodies, `(s, l, s') ∈ R_M` iff `(π s, π l, π s') ∈ R_M`, since no handler, guard or property can tell two bodies apart except by equality, and no constant other than `none` names one. So PS4.1b extends to `Content`: every path of **run**, whatever bodies it carries, is the renaming of a path of **check** over the representatives `none` and `c1 … cn`. `n` follows PS4.1c's rule, applied to `Content` separately: the number of `Content` positions in the state (a map holds one per key) plus the most `Content` values one label carries (at least one), and never fewer than 2. With two `Content` values compared for equality, two representatives show both outcomes, equal and different; one cannot. `Principal` and `Content` are counted apart, a body never being a principal, and the verdict prints both counts in its instance.
- **PS4.1c** A Polytrion world (v2) is a definition of **simulate** for a set of machines. The machines are unchanged. This is the formal content of the Polytrion principle "responders draw, machines decide, the kernel schedules".
- **PS4.1d** In **check**, the environment is unconstrained: every action, with every data value in its domain, may be offered in every state.
- **PS4.1e** **The bounded fragment.** Checks cover finite instances: finite domains, a finite number of instances, and a declared bound on messages in transit (PS13). The actor guarantee that a message is delivered after an unbounded but finite delay cannot be expressed in a finite instance. Liveness checks approximate it with fairness (PS6, PS14). The runtime implements the unbounded guarantee (R1, PS10).
- **PS4.2** The **checked instance** `I` restricts inputs to their check domains (every `d ∈ D(a)`) and states to theirs: a state is **in the instance** when every field `f` has `s(f) ∈ D(f)`. `Reach(I)` is the set of in-instance states on paths of `I` that stay in the instance. It is finite, because every field type in a checked machine is finite or restricted to a finite check domain (PT3.2).
- **PS4.2a** **Leaving the instance.** A transition from a state in `Reach(I)` can produce a post-state outside the instance in two ways, and they mean different things:
  - **Outside a declared type.** The post-state writes a value outside a field's declared type, such as `items: 0..3` becoming 4. The post-state is not in `S` at all. This is a program error: `PL3102 DOMAIN_ESCAPE`, a finding, with the path to the transition (PT3.5).
  - **Outside a check domain only.** The post-state stays inside the declared type (`int` or `string`) but leaves the field's check domain, such as a `term: int check 0..3` becoming 4. The post-state is a legal state that the instance does not cover. This is a **bound hit**: `PL3901 BOUND_HIT`, naming the field, with the shortest path to the boundary. The post-state is not explored, and the verdict is at best `INCONCLUSIVE`.

  Properties are still checked on every explored state, so a violation found inside the bound is still reported, and the fold of PT12.3 makes that verdict `FINDINGS`. A counter that grows without limit in the real system (a raft term, a coin count) is therefore checked up to its declared bound, and the verdict says so; it is never `CLEAN`.
- **PS4.3** **Every verdict is about `I`.** A `CLEAN` result states that a property holds on `Reach(I)` and on all paths of `I`. The instance is printed with the verdict (PT12.3a).
- **PS4.4** **Completion actions are ordinary actions.** In `I`, a completion such as `PaymentOk` can be offered in any state, whether or not a charge was emitted. So `I` over-approximates the real system: every real behaviour is a behaviour of `I`, but not every behaviour of `I` is real. For safety properties this is sound: a clean result holds for the real system. A witness may be infeasible if it uses a completion with no matching intent. Such a witness is marked `environment: unconstrained`, and the matching path property check (PS5.4) is the place to rule it out. A `send` is an intent in `E` like any other: a machine checked alone has no receivers, so the replies its receivers would send are ordinary actions the environment may offer in any state. This over-approximates too, and the configuration check (PS13) is where the receivers' actual behaviour is used (S30).

## PS5. Properties

There are five kinds of property. Each has its own keyword (PT5), and none is called an invariant unless it is one.

- **PS5.1** An **invariant** is a predicate `P` on states. `M ⊨ invariant P` iff `P(s)` holds for every `s ∈ Reach(I)`. The automatic `domain:<field>` properties (PT3.5) are invariants.
- **PS5.2** A **step property** is a predicate `Q(s, a, d, s', E)`, where `E` is the intent sequence of the step's verdict `accepted(E)` (PS3.2). It holds iff `Q` holds for every **accepted** transition from a state in `Reach(I)`. `Q` reads `d` only where `action == A` narrows the action, with the names of PS2.2 (S19). `Q` reads `E` only through `emits(k, f1: v1, …, fn: vn)`, `n ≥ 0`, which is true iff some intent of `E` is an intent of the effect named `k` (an `emit`, PS2.2), recognised by that effect's kind, whose payload field `fi` equals `vi` for every `i`. Each `vi` is a constant of its field's type: an enum constructor, an integer, a boolean, or `none`; `emits` reads no field, parameter or body. `k` is the effect's name, as `emit k(…)` writes it (PT2.2); a `send`, a timer, a spawn or a signal is not an effect, and naming one in `emits` is `PL1001` (S178). An intent, a witness and the journal carry an effect's kind and not its name, so two effects of one kind cannot be told apart: `emits` on either is `PL1201`. A rejected step emits nothing (PS3.2), so reading only accepted steps misses no intent.
- **PS5.2a** **`never emit` (S178).** `never n: emit k(f1: v1, …) while P` declares the step property `n: P(s) implies !emits(k, f1: v1, …)`, where `P` is a predicate on the pre-state alone: it names fields, and neither `post.`, a parameter nor `action`. It holds iff no accepted step from a reachable state that satisfies `P` emits the effect `k` with those field values. Without `while P`, `P` is `true`. `k` must name an effect the machine declares and each `fi` be a payload field of `k` (`PL1001`); a value outside its field's type is `PL1201`. A violation is a finding whose witness is the path to the pre-state and the step that emits. `P` reads the pre-state: a step that sends from a state where `P` holds is a violation whatever it writes, and a step from a state where `P` does not hold is not, whatever it writes. By PS4.4, `I` over-approximates every environment the machine runs in, a configuration included, so a `never` that holds on `I` holds for every instance of the machine in every configuration. A witness that uses a completion or a message nothing sent is marked `environment: unconstrained` (PS4.4); the configuration check evaluates the machine's `never` statements on that instance's global steps, which confirms such a witness or rules it out. A machine's `never` is not a policy's `never` (S149): the policy's is proved over the gate's decision table, and the machine's over `R_M`, before any gate. **Tested, or vacuous (ruled on M8 plan step 10).** A `never` is *tested* where it is judged (the machine's reachable graph, or a configuration's) when some reachable accepted step of the machine, or of its instance, takes an action whose handler can emit `k` (an `emit k` on some path of its body), from a pre-state where `P` holds. A `never` that is not tested holds for no reason the program gives: it is vacuous there, listed with the `never`, the machine or instance, and the reason (`P` holds in no reachable state, or it holds and no action that can emit `k` is taken from such a state), and the verdict is at best `INCONCLUSIVE` (PT12.3, S113), never `CLEAN`.
- **PS5.3** A **reject property** is a predicate `J(s, a, d, v)`. It holds iff `J` holds for **every** transition from a state in `Reach(I)`, whatever its verdict. `rejected(r)` in `J` is true iff `v = rejected(r)`. `J` reads `d` only where `action == A` narrows the action; elsewhere a bare name is a field of `s` (PS2.2, S19).
- **PS5.4** A **path property** is a predicate `Φ(π)` on finite paths. It is evaluated through `emitted(π)`, the concatenation of the intent sequences of the accepted labels of `π`, and `actions(π)`, the sequence of actions. It holds iff `Φ(π)` holds for every path `π` of `I`. Path properties must be **prefix-closed**: if `Φ` holds of a path, it holds of every prefix. The compiler accepts only forms that are prefix-closed by construction: `count(k) <= n`, `count(k) < n` (read as `count(k) <= n - 1`), `before(k1, k2)`, and their conjunctions. `count(k)` is the number of intents of kind `k` in `emitted(π)`, and `before(k1, k2)` holds iff every intent of kind `k2` in `emitted(π)` is preceded by an intent of kind `k1` (S37). Any other form is `PL1701 NOT_PREFIX_CLOSED`. So a path property is a safety property and has a finite witness.
- **PS5.5** A **liveness property** has one of two forms:
  - `eventually P`: every fair behaviour of `I` reaches a state satisfying `P`;
  - `P leads to Q`: in every fair behaviour, every state satisfying `P` is followed by a state satisfying `Q`.

  Fairness is defined in PS6. A liveness property is not a safety property and has no finite witness. Its counterexample is a **lasso**: a path to a cycle that can repeat forever.
- **PS5.6** **Deadlock.** A state `s ∈ Reach(I)` is a **deadlock** iff `¬term(s)` and no action accepts in `s`: for every `a` and every `d ∈ D(a)`, the verdict is not `accepted`. Deadlock freedom is checked for every machine, whether or not it declares a liveness property (`PL3201 DEADLOCK`, with the path to the state).

## PS6. Fairness

- **PS6.1** An action group `g` is a set of actions (written `A | B`). `g` is **enabled** in `s` iff some `a ∈ g` and some `d ∈ D(a)` give an accepted transition from `s`. `A(*)` in a fairness list stands for one group per data value: `{A(d)}` for each `d ∈ D(A)`. So `Send(*)` is fair to each message separately, and a sender that keeps sending one value cannot starve another.
- **PS6.2** A behaviour is **weakly fair for `g`**, written `WF(g)`, iff `g` is not enabled continuously from some point on without an accepted step of `g` being taken infinitely often. In words: an action group that stays enabled is eventually taken.
- **PS6.3** A liveness property is always stated with its fairness assumption: `liveness n: eventually P under fair { g1, g2, … }`. It is checked only over behaviours that are weakly fair for every listed group. Actions not listed carry no assumption: the environment may never offer them. A person's approval, for example, is not listed.
- **PS6.3a** Liveness under fairness is a game. The environment is an adversary that chooses inputs, constrained only by the stated fairness. A liveness property holds when the adversary has no strategy that avoids `P` forever. The lasso of PS6.4 is the adversary's winning strategy.
- **PS6.4** **Check.** Over the finite graph of `Reach(I)`, `eventually P` fails iff there is a strongly connected component `C`, of the states reachable from the initial state through states where `P` does not hold, with all of the following properties (S82):
  1. `C` contains no `P`-state.
  2. `C` contains at least one edge, where rejected and unhandled steps count as edges.
  3. For every listed group `g`, either some edge of `C` is an accepted step of `g`, or `g` is disabled in some state of `C`.

  This is the standard component test for weak fairness on a finite graph. `P leads to Q` is checked by the same test on the graph restricted to the part after a `P`-state, until `Q`. The counterexample is the path to `C` followed by a cycle through `C` that visits every edge the third condition names.

## PS7. Composition

Children come in two kinds. The author chooses, and the verdict says which semantics was checked.

- **PS7.1** **Attached children** (the default) form a **joint machine** with their parent. Its state is `(s_P, {k ↦ s_k})`, over the children spawned so far, and with each instance's status (active or terminal) and each child's wiring (its completion and cancel actions). The joint label is the **stimulus** `(target, a, d)`, where the target is the parent or a child key. The stimuli are offered as the kernel delivers them (S45): a terminal instance is offered nothing, and an action wired as the completion of a child is offered to the parent only once that child is terminal, because until then only the kernel delivers it, in the cascade. Inside a cascade, a delivery to a terminal instance is rejected and changes nothing. This rests on kernel assumption K9.
- **PS7.2** A joint step of attached children is the **cascade** of a stimulus: the stimulus's own transition, followed by every transition it causes, applied in order. These are completions to the parent, parent-terminal actions to children and signals, up to depth 8. The joint step is accepted iff the stimulus transition is accepted. A cascade that exceeds depth 8 is `PL5201 CASCADE_DEPTH`.
- **PS7.3** A **compose invariant** is an invariant (PS5.1) of the joint machine.
- **PS7.4** **Attached means co-located.** The cascade semantics is a model of the runtime only under K1 to K3, and K3 (one transaction per cascade) holds only if the parent and all its attached descendants are served by one kernel shard. The runtime shards by the root of each attached tree and refuses to place an attached child elsewhere (`PL5202 ATTACHED_ACROSS_SHARDS`). Every composition guarantee cites K1 to K3 and this rule.
- **PS7.5** **Detached children** (`spawn detached …`) are separate actors. `spawn` creates the instance and returns its address to the parent. From then on, parent and child communicate only by messages (`send`), which may arrive in any order. Their composition is checked as a configuration (PS13), not as a cascade.

## PS8. Policies

- **PS8.0** **Two truth types.** `Bool = {T, F}`. `Tri = {T, F, U}`, which is `Bool` lifted into an option type, with Kleene's rules for the missing case. The inputs a policy reads (the proposal, the action's labels, `machine(…)` fields, history) have **optional types**: any of them may be missing. A comparison or boolean operator applied to an optional operand has type `Tri`. Machine fields are never optional, so every machine expression has type `Bool`. `unknown(x)` has type `Bool`. A machine `require` demands `Bool`. A policy `when` or `require` accepts `Tri` and is evaluated by PS8.2. A `Tri` where a `Bool` is expected is a type error (`PL1203 TRI_WHERE_BOOL_EXPECTED`). The two logics are separated by type. One set of operators (`==`, `!=`, `&&`, `||`, `!`) serves both, and its meaning follows the operand types.
- **PS8.1** Policy expressions take values in `{T, F, U}`, where `U` is unknown.
  - `not`, `and` and `or` follow Kleene's strong three-valued logic: `not U = U`; `F and U = F`; `T and U = U`; `T or U = T`; `F or U = U`.
  - A comparison with an unknown operand is `U`.
  - `unknown(x)` is `T` or `F`, never `U`.
- **PS8.2** A `rule` obligation `when W require Q else s on unknown u` is evaluated for a proposal as follows. The severity `s` is `deny`, `warn` or `escalate`. The unknown handling `u` is `escalate`, `deny` or `skip`.

  | `W` | `Q` | Outcome |
  |---|---|---|
  | `F` | any | not applicable |
  | `T` | `T` | satisfied |
  | `T` | `F` or `U` | `s` (an unknown value never satisfies a requirement) |
  | `U` | any | `u` |

  **The default for `u`:**
  - For `s = deny`, the default is `escalate`. A deny rule whose condition cannot be evaluated never passes silently.
  - For `s = warn`, the default is `warn`.
  - `skip` must be written explicitly. It is listed in the certificate under `skippedOnUnknown`.
- **PS8.3** **Combination.** The gate's decision for a proposal is:
  - `deny` if any obligation's outcome is `deny`;
  - otherwise `escalate` if any outcome is `escalate`;
  - otherwise `allow`.

  Warnings are recorded with an `allow`.
- **PS8.4** **Labels.** In a scope where any obligation mentions `effects`, `labels` or `class`, an effect or tool with no labels is **refused at admission** (`PL6302 UNLABELLED_IN_LABELLED_SCOPE`, verdict `REFUSED`). An unlabelled effect cannot make a label-based rule's `when` unknown at runtime.
- **PS8.5** `machine("<module>.<Machine>").f` is the value of `f` in the post-state of the step that emitted the effect under decision (PT9.3). It is `U` for a proposal that is not an effect of that machine.
- **PS8.6** **Consistency of obligations.** Obligations in one scope come from several sources: declared policies, promoted Polyx rules, recalled text and native kernels. Each decision is resolved by PS8.3, but the obligations may still contradict each other as a whole. A mandate `m` is **dischargeable** under a set of obligations `O` iff some path over the scope's **tool alphabet** reaches a discharge state of `m` with no `deny` outcome on the way. The tool alphabet is the set of actions the scope's tools can perform, with their labels. The declared action alphabet is used only when the scope has no tool catalogue, and the certificate records which alphabet was used. This is Polyaxion's admission condition m2, "lawfully dischargeable".
  - **A possibility property.** Dischargeability says that a good path *exists*. Every other property in this document constrains *all* behaviours. It is not a property of behaviours: a system whose behaviours all satisfy every PS5 property may fail it, and the converse. It is checked as reachability on the explored graph of the scope's policy machines, not with the machinery of PS5 and PS6, and diagnostics name it as a possibility property.
  - If `m` is not dischargeable, the finding (`PL6501 UNDISCHARGEABLE_MANDATE`) names **a minimal conflicting subset** `O' ⊆ O`: `m` is not dischargeable under `O'`, and it is dischargeable under `O' \ {o}` for every `o ∈ O'`. It is minimal, not necessarily smallest. Different deletion orders can find different minimal subsets, so the order is fixed for reproducibility: obligations are tried for removal in declaration order, then promoted rules in promotion order.
  - The check runs at admission and again on **every promotion** of a mined rule, because promotion is when rules written from different evidence first meet.

- **PS8.7** **Which messages cross the gate.** Every instance has a **trust scope**: the scope of its module's policy, or the scope its configuration assigns to it.
  - A `send` whose sender and receiver are in **different** trust scopes is proposed to the gate, exactly like an effect. A send within one scope is not.
  - Effects to capability addresses are always proposed, as before (PT9).
  - **A denied send** is not delivered. Instead, the message `SendDenied(to, action, reason)` is delivered to the sender itself, as an ordinary message. The sender may handle it; if it has no handler, it is an unhandled step, journaled like any other. A denied send is therefore visible in the sender's behaviour and in the checked configuration, where the gate's decision is an environment choice among allow, deny and escalate (PS4.4).
  - Governance thus sees every message that leaves a trust scope. "One mechanism" holds for control as well as for execution.
- **PS8.8** **The age of claims (PD6.1, S195, S196, ruled for M9).** The verifier adapter may give, beside a step's claims, the time it checked the presentation (`verifiedAt`) and the time of the status information it used (`statusAt`); they are kept with the step and bound into its ledger event. A policy reads `age(step.claims)` and `statusAge(step.claims)`, integers in milliseconds: the decision time minus `verifiedAt`, and minus `statusAt`. The decision time is the runtime's clock when the gate decides, and the ages it gave are recorded in the `verdict` event, so replay uses the recorded ages and never reads a clock (PS11). An age is unknown (`U`) when its time is missing, or lies after the decision time; it is never taken as fresh, and `on unknown` decides (PS8.2).
  - **Checking.** Each age is explored by the intervals the policies' thresholds cut (PT20.3): for a scope whose rules compare an age with thresholds `t1 < … < tn`, the values `0`, each `ti` and `ti + 1`, and unknown. The decision-table check (S149) covers them, so a `never` over ages is proved or refuted with a witness like any other.
  - **Stale claims are denied, never refreshed (S198, as amended by the owner's ruling).** A rule over an age denies: its severity is `deny`, and a rule over an age written `escalate` or `warn` is refused (`PL1201`); an escalation may still be raised on other grounds, and an unknown age follows `on unknown`. A proposal a rule over an age denies is denied with the reason `stale-claims`, journaled. The runtime does not refresh the claims: the host dispatches the action again with a fresh presentation, which is a new step and a new intent, checked by the gate like any other, and is bounded by the host's own logic.
- **PS8.9** **Mandates that only narrow (PD6.2, S195, S197, ruled for M9).** A **mandate** is evidence the verifier adapter may give beside a step's claims: `{ id, delegator, delegate, scope, expires }`, with its chain of parent mandates, outermost first. A **scope** is a conjunction of: a finite set of allowed actions (effect kinds); per payload field, a finite set of allowed values or an upper bound on an integer; and the expiry. `scope(c) ⊆ scope(p)` iff each constraint of `p` is present in `c` and at least as tight: every allowed action of `c` is allowed by `p`, every allowed value of a field in `c` is allowed by `p` for that field, every upper bound of `c` is at most `p`'s, and `expires(c) ≤ expires(p)`. Subset is decided field by field.
  - **The narrowing rule (K12).** For each hop of a chain, the child's scope is within its parent's (`⊆`), and the child's delegator is the parent's delegate. A chain that widens anywhere, or that holds a revoked mandate, is refused before any step: the dispatch is refused `mandate-widened` (or `mandate-revoked`), written to the audit log, and no instance changes, as an input outside its type is (S140).
  - **Every action, not the first.** Each proposal for an effect of a step that carries a mandate is checked against the innermost mandate's scope at the decision time: its kind among the allowed actions, each constrained payload field within its values or bound, and the decision time before the expiry. Otherwise the proposal is denied `outside-mandate` before any policy runs (S199), on the tenth action as on the first. Policies read `step.claims` for the principal and `step.mandate.delegate` and `step.mandate.delegator` for the agent and the person it acts for; the agent is never the delegator.
  - **Revocation.** Revoking a mandate revokes every mandate beneath it: a chain that holds it is refused at the next dispatch, and a proposal from a step whose chain holds it is denied `outside-mandate`.

## PS9. Lowering correctness

- **PS9.1** Let `L(M)` be the lowered module. Let `R_L` be its transition relation under the SAM v2 strict profile. For each `(s, a, d)`:
  - an acceptor rejecting with `r` gives `rejected(r)`;
  - writes to `next`, with the declared `unchanged`, give the next state;
  - the effects mapper applied to the step gives `E`.
- **PS9.1a** Rows 1, 2, 4 and 5 of the table in PS3.2 (terminal states, strict check domains, claims and content) are applied by the runtime before it calls the module: the lowered module's first acceptors apply them, before any guard. `R_L` is therefore the module's relation with those rules applied first, exactly as the runtime applies them. An action with no handler is not in the module's action surface (S35), so the runtime answers it without calling the module: row 1, `rejected("terminal")`, in a terminal state, and row 3, `unhandled`, elsewhere (row 2 never applies: a parameter is `strict` by default only when a handler lets it flow into an effect, and an explicit `strict` on a parameter of an action with no handler is `PL1302 STRICT_ON_UNHANDLED_ACTION`, S53). Those steps are part of `R_L` and are compared like any other.
- **PS9.1b** **Flattening unions.** A union field `f` lowers to a tag field `f` plus one nullable field `f_<payload>` per payload name of any constructor, because the SAM sealed shape is flat. Below the top of a field, where no flat key exists (a map's value, a payload, a parameter), a union with payloads lowers to one object `{ "$": "C", p: v, … }` with exactly its constructor's payloads, recursively, and `α` reads it back; a union with no payload is its constructor's name (S65). Constructors that share a payload name share its field, which requires the same type (`PL1601 PAYLOAD_TYPE_CONFLICT` otherwise). The abstraction function `α` maps a flat state back to a structured one. The lowering adds one automatic invariant per union field (`shape:f`): the payload fields of the current constructor are present, and all others are null. PS9.2 compares `R_M` with `R_L` through `α`.
- **PS9.2** **The lowering is correct for `M` on `I`** iff `R_L` and `R_M` agree on every `(s, a, d)` with `s ∈ Reach(I)` and `d ∈ D(a)`. They must give the same verdict kind, the same reason, the same next state and the same intent sequence. The lowered property modules must also agree with PS5 on every reachable state and transition.
- **PS9.3** **Translation validation on every check.** `poly check` runs `poly-ref`, poly's own model checker and reference interpreter, written directly from this document and sharing no code with the compiler. It explores `I` and compares every transition with the lowered module's. A difference is `PL2501 LOWERING_MISMATCH`. The verdict is `REFUSED`, and the diagnostic is addressed to the toolchain, not to the author. This makes the lowering's correctness a checked fact for each program, not a claim about the compiler.

### Runtime obligations

A kernel assumption is something the semantics relies on. A runtime obligation is something the semantics *defines*, and which the runtime must implement. When an obligation is not met, the runtime is at fault, not the program or the specification.

| Id | Obligation | How it is watched |
|---|---|---|
| R1 | **Delivery (PS14).** While the runtime is up, every message in transit is eventually delivered, every intent is eventually completed or refused, and every due timer eventually fires. | Queue-age and timer-lag monitors, with an alarm when an age exceeds its declared bound. The ledger records every delivery, so a missing one is visible after the fact. |

## PS11. The gate and replay

- **PS11.0** **The gate is an actor.** It has its own state (Σ per session), it processes one proposal or settle at a time per session, and its only inputs are messages. The order that determines its decisions is its own **arrival order**, recorded as `sseq`. No global order exists, and none is needed. It follows that:
  - a session is a serialisation point: all proposals of a session queue at one actor, and throughput is measured per session (PT9.6);
  - the gate can be sharded along sessions, and only along sessions;
  - a policy that needs state across sessions needs another actor, reached by messages. It cannot share a variable.

- **PS11.1** Each gate session has a **session sequence** `sseq`. The gate assigns it on receipt of every proposal and every settle. Each ledger event carries its `sseq` and the digest of Σ before the event.
- **PS11.2** **Replay of a session** re-applies its events in `sseq` order. It must reproduce every decision and every Σ digest. By K6, this reproduces the gate's behaviour exactly.
- **PS11.3** **Replay of a run** reproduces every post-state from the run's own chain (K1, PS2.5). It reproduces gate decisions when the sessions the run touched are replayed with it.
- **PS11.4** **Replay is a fold.** A run's state after `n` steps is `foldl δ init [l0 … ln-1]`, where `δ(s, (a, d, _))` is the next state given by `R_M`. The replay theorem is then one line: `δ` is a function (PS2.5), so the same journal gives the same fold. The runtime stores the journal, and the state is the fold's cache (the snapshot). A snapshot that disagrees with the fold is a kernel fault, not a program fault.

## PS12. Expression syntax: precedence

From tightest to loosest binding:

| Level | Operators | Associativity |
|---|---|---|
| 1 | field access, indexing `m[k]`, calls `count(…)`, `before(…)` | left |
| 2 | `!` `-` (unary) | right |
| 3 | `*` `/` `%` | left |
| 4 | `+` `-` | left |
| 5 | `<` `<=` `>` `>=` `in` | none |
| 6 | `==` `!=` | none |
| 7 | `&&` | left |
| 8 | `\|\|` | left |
| 9 | `implies` | right |

The canonical formatter inserts parentheses whenever `implies` is mixed with `&&` or `||` in one expression. So `executed implies (decisions <= 1 || approved)` is the only printed form of that invariant, and neither the author nor a reader has to remember level 9. `e is C` (constructor test, type `Bool`) binds at level 5. Policies use the same operators; their meaning follows the operand types (PS8.0).

## PS13. Configurations

- **PS13.1** A **configuration** `C` is a finite set of named instances. Each instance has a machine, an initial state (including initial addresses) and a flag telling whether the machine is a service. `C` also declares:
  - its **inputs**: the actions the environment may inject, at which instances;
  - its **bounds**: the maximum number of messages in transit `B`, and the maximum number of instances `N` (detached spawns create instances).
- **PS13.2** A **global state** is a pair `(σ, μ)`:
  - `σ` maps each instance to its state;
  - `μ` is the **set of identified messages** in transit. Each message is `(id, target, action, data)`. Its identity is `id = (sender, sender's step number, position among that step's intents)`, the model's image of the runtime's idempotency key.
- **PS13.2a** **Copies are indistinguishable to the receiver.** Two messages with the same `(target, action, data)` produce the same step at the receiver, whatever their identities. The explorer therefore keeps `μ` as a multiset of values, and a delivery of a value consumes its **oldest** copy. This quotient loses no behaviour: every delivery sequence of identified messages maps to one with the same states and labels. So it is exact for safety.
- **PS13.2b** **Fairness per identified message.** In the quotient, weak fairness of each value's delivery, together with oldest-copy delivery, implies that every identified message is eventually delivered. Proof: while a value `v` is in transit, its deliveries are enabled. Weak fairness makes them happen repeatedly. Each delivery removes the oldest copy. A given copy has at most `B - 1` copies ahead of it (PS13.5), so it is delivered after at most `B` deliveries of `v`. ∎ Liveness checks use this fairness (PS14.2).
- **PS13.3** A **global step** is one of:
  - **input**: the environment injects a declared input `(i, a, d)`;
  - **delivery**: any one message in `μ` is removed and delivered to its target.

  In either case the target takes its step by `R_M` (PS3.2). The intents of an accepted step are handled as follows:
  - its `send` messages are added to `μ`; a send to `none` adds nothing and is a finding (`PL5404 SEND_TO_NONE`, S29);
  - its detached `spawn` intents create new instances, each at the address `<parent address>/<k>`, in its machine's initial state, with its creation action as its first message; instances spawned from `M` join the group `M`, and `N` counts every instance (S60). A spawn of a key whose instance already exists creates nothing and is `PL5101 CHILDKEY_COLLISION`, checked before the instance bound (S83);
  - its other effects and its timers are completed by the environment only through the configuration's declared inputs: a completion action not listed there is never offered (S61).

  A delivery to an instance that rejects the message is a rejected step: the message is consumed and the state is unchanged.
- **PS13.4** **Arrival order is nondeterministic.** Any message in transit may be delivered next, whatever order the messages were sent in. This is the only order a configuration assumes. Two messages from one sender to one receiver are not assumed to arrive in order unless the configuration declares `fifo` for that pair.
- **PS13.5** **Bounds are reported, never silently applied.** A step that would exceed `B` messages in transit or `N` instances is not explored. The verdict is then at best `INCONCLUSIVE`, with `PL5301 TRANSIT_BOUND_HIT` or `PL5302 INSTANCE_BOUND_HIT` and the bound. It is never `CLEAN`.
- **PS13.6** **Properties of a configuration.**
  - A **configuration invariant** is a predicate on `σ`.
  - **Instance groups and quantifiers.** `g[*]` may appear only as the argument of an aggregate: `count`, `sum`, `all` or `any`. Everywhere else a group must be quantified explicitly: `forall i in g: P(g[i])` or `exists i in g: P(g[i])`. An unquantified `g[*]` outside an aggregate is `PL5403 UNQUANTIFIED_GROUP`. In a liveness property, the quantifier scopes over the whole `leads to`: `forall i in order: order[i] is Asked leads to order[i] is Done | Refused` means that each asked order is eventually settled.
  - **Instance fields (S32).** `x.f` and `g[i].f` denote field `f` of an instance in `σ`. `g[i] is C` denotes `g[i].f is C` for the one field `f` of the machine whose type has the constructor `C`; with none or several such fields it is `PL1005`. Only configuration properties read instances' fields (PS1.6).
  - **`init(e)`** is the value of `e` in the configuration's initial state. Properties refer to initial quantities through `init`, never through constants explained in comments.
  - A **quiescent** global state has `μ` empty and no declared input accepted.
  - A **stuck** state is a quiescent state in which some non-service instance is not terminal. It is reported as `PL5402 STUCK`, the configuration's form of deadlock.
  - Liveness properties (`P leads to Q`) are checked under the delivery guarantee (PS14) and any stated fairness. In a configuration the fairness clause may be left out: delivery is fair by PS14.2, and an input is fair only if the clause names it (S56).
- **PS13.7** **Interpretations.** The three interpretations of PS4.1a apply to configurations unchanged:
  - **check** explores every input and every arrival order within the bounds;
  - **simulate** samples them (a Polytrion world, v2);
  - **run** is the deployed system.

  The theorem of PS4.1b extends: every run of the deployed instances, whose inputs are in their domains and which stays within the bounds, is a path of the check interpretation, up to the choice of linearisation.
- **PS13.8** **The happens-before argument.** A deployed configuration does not execute a sequence of global steps. Instances step concurrently on different workers, and no one observes a global state. A run is a partial order of events under the causal relation `→`: a step precedes the next step of the same instance, and a send precedes the delivery of that message. The proof of PS13.7 is:
  1. **Commutation.** Every step touches one instance's state and adds messages to `μ`. So two steps of different instances that are unordered by `→` commute: applying them in either order gives the same global state.
  2. **Linear extensions.** Every linear extension of a run's partial order is therefore a sequence of global steps. It is a path of **check**, because **check** delivers any message in transit in any order (PS13.4).
  3. **Coverage.** A configuration invariant that holds on every path of **check** holds in every state of every linear extension, however the run is linearised. ∎
- **PS13.9** **Monitoring.** A configuration invariant is a statement about global states, which no participant observes. It constrains the system's behaviour, but no runtime monitor can check it directly. It is monitored either by taking a consistent snapshot of the instances (a cut closed under `→`) or offline, over the ledger, by replaying one linear extension of the recorded partial order.

## PS14. Delivery

- **PS14.1** **Every message sent is eventually received.** This is part of the meaning of `send`, not an assumption about a kernel. In a behaviour of a configuration, every message added to `μ` is eventually delivered. Every intent is eventually completed or refused. Every due timer eventually fires.
- **PS14.2** In the check interpretation, this is **weak fairness of each identified message's delivery**, realised in the explorer as weak fairness per value with oldest-copy delivery (PS13.2b). A message in transit stays deliverable until it is delivered, so weak fairness is enough. Liveness checks (PS6.4) include these fairness constraints automatically, so an author states only the fairness of the machines' own actions.
- **PS14.3** At runtime, delivery is obligation R1 (PS10). Delivery is at-least-once through the outbox, and the receiver deduplicates on the message's idempotency key (K4 with its lifetime). The claim that each message takes **exactly one step at its receiver** is a property of the delivery protocol. That protocol is modelled as the `Delivery` machine (PT9.8) and checked: at most one step per message always, at least one under fairness, and in-order delivery for the in-order worker. The runtime's conformance to that model is kernel assumption K8, checked by trace replay at M4.

## PS15. Channels

- **PS15.0** **A channel adds no step, verdict or property of its own (M8b).** `channel c: k { … }` in module `m` means the program obtained by the expansion of PS15.1 to PS15.5, and every other section reads the expanded program. `k` names the module `std.channels.k`. It declares the machine `Conversation`; its peer machine `Peer`, an interface whose actions are the messages the conversation sends to the application, with no state and no handler; and the conversation's actions `Open(app: Ref<Peer>)`, `Inbound(…)`, `Reply(…)`, `Template(…)` and `Ack()`. Of the `Peer` actions, `Delivered`, `Rejected` and `Failed` are the conversation's **receipts**; `Ack()` is the application's acknowledgement of one. The checker and poly-ref each expand a channel from this text, and neither is given the other's expansion.
- **PS15.1** **The conversation of a channel.** The channel instantiates `Conversation` as the machine `m.c.Conversation`. Its peer type becomes `Ref<A>`, `A` being the application machine the channel names. Each message it sends its peer under a name `N` is renamed to the action of `A` the channel maps `N` to, and its provider effect `send` takes the kind `channel.c.send`, one kind per channel, so a policy tells channels apart. The binding is checked: it is total, every `Peer` action mapped (`PL6813`); one-to-one, no two `Peer` actions mapped to one action of `A` (`PL6814`); and typed, each mapped action of `A` having the `Peer` action's parameters, by name and type (`PL6815`). The instance keeps the conversation's states, handlers and properties.
- **PS15.2** **The link.** The handler of the action `starts` names gains, as its last statement, `spawn detached m.c.Conversation as c -> Open(app: self)`. The child key is the channel's name, fixed by the compiler (S177), so the conversation of the application instance at address `p` is at `p/c`. `self` is legal as a whole argument of a detached spawn's creation action, as it is of a `send` (S58, S177). A key `c` used otherwise in `A` is `PL1002`.
- **PS15.3** **The rewrite.** In `A`'s handlers, `emit c.reply(args)` is `send c <- Reply(args)` and `emit c.template(args)` is `send c <- Template(args)`, `c` reading the address of the child spawned under that key (PS7.5). Only the conversation emits the provider effect `channel.c.send`. Since `c.reply` is a message after the rewrite, `never … emit c.reply` or `emits(c.reply)` in `A` is `PL1001`, and the rule is stated on the conversation (S178). Each handler of `A` bound to a receipt gains, as its last statement, `send c <- Ack()`: an accepted receipt step acknowledges the receipt, so the conversation can hold its slot until its receipt is consumed and count it in `pending`, and every message between the two is then bounded by `pending`'s bound. A rejected receipt step sends nothing (PS3.2), so its receipt stays unacknowledged. `Ack` is the expansion's alone: an author neither writes nor binds it, and it is outside the binding and its checks (PS15.1, `PL6813` to `PL6815`).
- **PS15.4** **Inbound.** A message from the provider is the action `Inbound` of the conversation at `p/c`, `p` being the application instance its thread key names. The thread key is a checked string computed from the message's fields by the channel's template (PT21.1b), and is used only to name the instance. When no instance has the key:
  - if the channel declares that inbound creates the application (`starts A.S on inbound`), the runtime creates it, takes the `starts` step with its spawn of the conversation, and then delivers the message to the conversation, in that order, each journaled. A `starts` step that is rejected refuses the message, with the reserved reason `thread-not-started`;
  - otherwise the message is refused with the reserved reason `unknown-thread`.
  - while the runtime's kernel cannot create an instance by a detached spawn (polyrun before E13), a message that would create the application is refused with the reserved reason `creation-unavailable`, before any instance is created.

  **Addresses (S191, S205).** A thread key, and each message field its template reads, is an address (a phone number, an email address, a Slack channel id). At run time no address enters the journal or the ledger: before the message is delivered, each field the template reads is replaced by its keyed digest, an HMAC under the store's own key, and `p` is `c:` followed by the keyed digest of the thread key. Each address is kept in the erasable content store under its keyed digest, and the send of `channel.c.send` reads its recipient from there; a send whose recipient was erased fails permanently, journaled, and the conversation is told as of any failed send. The sender a channel's adapter verifies (K11) is journaled by its keyed digest too. One address gives one digest in one store, so the replacement is a renaming of the field's values: a conversation that reads a thread-key field only to compare it for equality, or not at all, takes the same steps, and the conversations of `std/channels` do not read one. So PS4.1b carries over to the renamed values as it does to `Content` (PS4.1f).

  Every refusal is journaled on the runtime's own `runtime:ingress` run. An `unknown-thread` refusal creates no instance. A `thread-not-started` refusal follows the creation and its rejected `starts` step, both journaled: the application exists in its initial state with no conversation, and each later message on its thread is refused the same way: such a thread stays dead. Until its conversation is spawned, `c` names no instance, and a send to it is refused as one to an address that names no instance: dead-lettered and journaled on the sender's run (S89), and `PL5404` in a configuration, as a send to none is. The conversation sends the message to its peer, which the renaming of PS15.1 makes `A`'s mapped action. A provider's report that a rule of the conversation reads (an email bounce, a failed webhook delivery, a Slack channel found archived) reaches the conversation as a **provider event**: an `Inbound` of that event on the thread, with the action id `<channel>:<provider's id>`, or the completion of the `send` the report concerns. A report no rule reads is recorded on `runtime:ingress` and reaches no instance.
- **PS15.5** **The checked configuration.** Each channel gives the configuration `c` (PS13), named after the channel in every report so a finding can be traced to it: the instance `app: A`; its conversation, the detached child `c` that `starts` spawns; the inputs `A`'s `starts`, the conversation's `Inbound`, and the completions the conversation's provider effect is wired to (the provider's receipts); the transit bound the conversation's declared `pending` bound, `N` for its field `pending: 0..N`, plus one for each other channel `A` is bound to, `N + n - 1` for `n` channels; and the instance bound one plus the number of channels `A` is bound to: the application and every conversation its `starts` handler spawns (ruled on the review of M8b, A-F2). Another channel's conversation is an instance of `c`, and `c` offers none of its inputs, arms none of its timers and checks none of its `never` statements, which its own channel's configuration checks. Having no inputs, each of those `n - 1` conversations holds at most its creation message `Open(app)` in transit beside the `N` of `c`'s own conversation, hence the transit bound (ruled on the review of M8b, A-F2). The report lists, per configuration, the instances whose `never` statements it checked and those it left to their own configuration. **The provider's clock (ruled on M8 plan step 10).** The inputs of the configuration `c` also include the completion of each of the conversation's timers (`after d -> X() as k`), which may fire an armed timer at any time. The global state of `c` records which of the conversation's timers are armed, with the action and data each will deliver: an `after` arms its key, and an `after` on a key that is already armed re-arms it, so a key has at most one pending firing, as at run time; a `cancel` disarms it; the environment offers `X` only while `k` is armed, and the firing disarms `k` before the step it starts. Durations are not compared: any armed timer may fire before or after any other step (PS4.4). **Timers in every configuration (S206, ruled 2026-10-06).** Every configuration, generated or declared, keeps every instance's armed timers in its global state in the same way, and the environment may fire one while it is armed; a declared input on a timer's target stays an input like any other (it replaces S61's rule that a declared configuration completes timers through its declared inputs alone). Any declared configuration that includes `A` also gets the conversation of each of its instances, with the same inputs and the instance bound raised to count them. The conversation's `never` statements are checked on it alone (PS5.2a) and in these configurations; an application that leaves a message unhandled gets `PL5102` or `PL5402` with its witness, as any configuration does. Each `never` of the conversation that these configurations check is judged tested or vacuous by PS5.2a, per configuration. **The joint configuration (S207, ruled 2026-10-06).** An application `A` bound to `n > 1` channels whose handler of a message from one channel (an action the binding of channel `c` maps a `Peer` action to) sends on another channel `c'` (`emit c'.reply` or `emit c'.template`) gets, beside the configuration of each channel, one more, named after `A`: the instance `app: A`; every conversation its `starts` handler spawns, each live, with its `Inbound`, its provider's completions and its timers; the instance bound `1 + n`; and the transit bound the sum of the conversations' `pending` bounds. It is the model of the run for a reply across channels. Its exploration is capped at 10,000 global states; a check that reaches the cap is `PL3901` and `INCONCLUSIVE`, never `CLEAN`. A finding in it, as in any configuration, is the program's: in the cross-channel application of the M8b review, the email conversation refuses, `busy`, a reply that answers no waiting message while its slot is held (`PL5407`). In each of these configurations two kinds of global step are findings, reported once per action with the path to the first in breadth-first order as the witness: a delivery of a receipt that `A` rejects, `PL5406 RECEIPT_REJECTED`, since a rejected step sends no `Ack` (PS3.2) and the conversation's slot is then never freed; and a delivery of `Reply` or `Template` from `A` that the conversation rejects, `PL5407 REPLY_REFUSED`, since `A` is not told and its message is lost.

## PS16. Credentials

- **PS16.0** **A credential adds no step of its own (M9, S203, S209).** `credential c: oauth2 { … }` in module `m` declares what the vault holds by reference; an effect's `uses c { s… } for p` names it (PT10e). Its meaning is the module `m.c`: the module `std.credentials` instantiated for `c`. `std.credentials` declares the record `ScopeSet` and the machine `Grant`, whose lifecycle (requested, granted, refreshing within a bounded number of attempts, expired, revoked) is written from RFC 6749 and RFC 7009, and is checked alone with two scopes.
- **PS16.1** **The scope set of a credential.** In `m.c`, `ScopeSet` is the record with one `bool` field per scope `c` declares, in declaration order, each named by its scope with every `.` written `_`; two scopes of one credential that give one field name are `PL1002`. Every record literal of `std.credentials` whose fields are `ScopeSet`'s is read with the new fields, each `false`. Every other declaration is `std.credentials`'s, as written. So the scope sets `m.c.Grant` explores are exactly the subsets of `c`'s declared scopes (PT22.2b): a grant with fewer scopes than requested is a reachable state, and `m.c.ScopeSet` and `m.c'.ScopeSet` are different types for two credentials.
- **PS16.2** **One grant per credential and holder.** At run time each pair of a credential `c` and a holder (a `Principal`, or none for `client_credentials`) has its own instance of `m.c.Grant`, keyed by both (PT22.2a). A scope granted on one credential is a field of that credential's instance only, so it never satisfies an effect that uses another credential. The check and the runtime each instantiate `m.c` from this text; poly-ref is given the source as written, as for a channel (PS15.0).
- **PS16.3** **The grant check (PT22.4, S199).** For an intent of an effect with `uses c { s… } for p`, before any policy and before the mandate (PS8.9), the runtime reads the instance `G` of `m.c.Grant` for `c` and the value of the payload field `p` (for `client_credentials`, the one instance of `c`), as of the proposal. If there is no such instance, no vault for `c`, or `G.g` is not `Granted`, the intent is denied `credential-unavailable`; if some scope of `s` is not among `G`'s scopes, it is denied `insufficient-scope`. Both refusals are final whatever a policy says (fail closed), and are journaled with `G`'s sequence number. An intent the check passes is proposed with the field `credential`: the credential's name, `G`'s state and the scopes granted; the holder is never readable. An allow reads `G` as it reads a singleton (S147): when `G` takes a step before the intent starts, the allow is stale, and the intent is proposed again, so a grant revoked or expired before the start denies it.
- **PS16.4** **Revocation (PT22.6).** `Revoke()` reaches `G` from three sources: the provider's notice that the holder withdrew the grant, a person's signed revocation (a record of the kind `revocation`, by a key of the `people` ring, PT12.5), and a security signal on the holder (PD5.3). From the step that records `Revoked`, every intent using `G` is denied `credential-unavailable` (PS16.3). An intent already started finishes, since the provider has already accepted its request, and its step is journaled before the revocation's.

## Conclusion

A poly program denotes a deterministic, labelled transition relation over a finite checked instance. Checking, simulation and running are three interpretations of one environment interface over that same relation, and the claim that the checked program is the running program is a theorem about two of them. States may be tagged unions, so invalid states are unrepresentable rather than merely unreachable. Policy logic has its own type. Machines talk to each other only by messages sent to addresses. A configuration of machines is checked with messages arriving in any order, within declared bounds. Delivery is part of what sending means, and the runtime is obliged to implement it. Attached children are co-located, and detached children are actors like any other. Obligations from all sources are checked together for a way to discharge each mandate; that check is a possibility property, named as such. Messages have identities, so fairness is per message, and the delivery protocol that makes a message take exactly one step is itself a checked machine. Rejections are labelled stuttering steps. Properties come in five kinds with distinct meanings. Liveness is stated only with its fairness assumptions. Policies have a total three-valued evaluation in which an unknown deny condition escalates. The lowering is correct when its transition relation equals this one, and every `poly check` verifies that for the program at hand. Every guarantee about a running program names the kernel assumptions it depends on.
