# poly · Semantics

*Cognitive Fab · September 2026 · draft v0.6 · specification only, no code*

This document defines what a poly program means. The functional (`PF`), architecture (`PA`) and technical (`PT`) specifications defer to it. Where they disagree with it, this document is right and they are wrong. Requirement ids here are `PS`.

The definitions are mathematical and short. They are written so that a reference interpreter can be built directly from them, with no code shared with the compiler (PS9).

## PS1. Machines and states

- **PS1.0** **Programs and modules (S176).** A **program** is a finite set of modules. A machine is named by its module and its name, `m.M`, and two machines are the same only when both are. `use m` makes the machines of module `m` nameable in a module as `m.M`; it adds no behaviour, no state and no message. PS1.6 to PS13 read `M` as the qualified name throughout.

  **Enums across modules (S190).** An enum is identified by its module and its name, `m.E`, and two enums are the same type only when both are: two enums with the same members in different modules are different types, and a value of one where the other is expected is `PL1201`. `use m` makes `m`'s enums nameable as `m.E`, as it does its machines, and `use m.E` makes `m.E` nameable and nothing else of `m`. A member is written `m.E.C`. A bare member `C` is allowed only where the expected type fixes the enum; elsewhere a bare member of another module's enum is refused, and so is a bare member that would name a member of more than one enum. A value of `m.E` is compared with `==` and `!=` and taken apart with `match`, which must cover every member of `m.E`, exactly as for an enum of the module itself, in handlers, guards, properties and configuration properties alike. Only payload-free enums cross modules: a record, a union with payloads, or a map of another module's types is `PL0901`. Where an enum is declared changes nothing else: `T(f)` for a field of type `m.E` is the set of `m.E`'s members (PS1.2), and check explores every one.
- **PS1.1** A machine `M` is a tuple `(F, init, A, H, G, term)`:
  - `F` is a finite, ordered set of fields. Each field `f` has a type `T(f)` and a check domain `D(f) ⊆ T(f)`. The first field is the **control field**.
  - `init` is the initial state.
  - `A` is a finite set of actions. Each action `a` has a parameter record type `T(a)` and a check domain `D(a) ⊆ T(a)`, the product of its parameters' check domains.
  - `H` maps each handled action to its handler.
  - `G` is the ordered list of guards (`guard all when … reject …`).
  - `term` is the terminal predicate.
- **PS1.2** A **state** is a function `s` from `F` to values with `s(f) ∈ T(f)` for every field. `S` is the set of states. The state contains the declared fields and nothing else: no verdict, no pending effects, no timers.
- **PS1.4** **Types.** The value types are `bool`, integer ranges, `int`, `string`, finite maps with enum keys, and **tagged unions**. A tagged union `U = C1 { p1 } | … | Cn { pn }` has constructors `Ci`, each with a record of named payload fields `pi` (possibly empty). Its values are pairs `(Ci, r)` with `r` a record of the payload types of `Ci`. An enum is a tagged union whose constructors have no payload. A union is finite when every payload field's type or check domain is finite.
- **PS1.4a** **Content (S180).** `Content` is an opaque reference to a body, identified by the SHA-256 digest of the body's bytes, or `none`. A module may store a `Content`, pass it, and compare two with `==` and `!=`; no other operation reads it, so an order, arithmetic, a comparison with a string, a map key, a record field, a `match`, a check domain or any other use is `PL1209 CONTENT_NOT_OPAQUE`. The only constant of type `Content` is `none`: a digest written in source is `PL1209`, and a body enters only at run time, through ingress or the runtime's content store. The type has no finite domain of its own; **check** explores it by representatives (PS4.1f).
- **PS1.4b** **Audiences and `Items` (M10, S303, Q3).** `audience { a1 < a2 < … < ak }` declares the enum `Audience`, its members in a total order, `a1` the lowest; a program declares at most one. A module uses an `Audience` value as any enum's (in a claims field, for example); its order is read by the flow rule (PS17.3) and by policies. `Items` is an opaque reference to the items a retrieval returned (PS17.2). A module reads one thing of it, `x.count`, an integer of `0..L`, `L` being the largest `limit` among the module's retrievals, and passes it whole as an argument of a decision or an effect. It is not stored in the state, a record, a payload or a map, not compared and not matched; any such use is `PL1209`, as for `Content`. Its class, owners and age are not readable by a module: they are its taint (PS17.1), which the checker and the runtime track, and its age, which the gate reads (PS17.6). **check** explores an `Items` parameter by its count, `0..L`. *Limit (S325):* a count carries no taint. It is a declassification point: whether another principal has any items, and how many, reaches whoever the count is sent to. The certificate lists each count a handler reads of an `Items` from a retrieval whose owner predicate is not the requesting step's claimant (PS17.2).
- **PS1.4c** **Keys (S451).** `Key` is an opaque value that names items of a source by one of the keys the source declares (a message, a thread, a correspondent), or `none`. A module stores a `Key`, passes it, and compares two with `==` and `!=`; any other use (an order, arithmetic, a comparison with a string, a map key, a check domain, a literal other than `none`) is `PL1209`, as for `Content`. A `Key` enters only as data at run time, a non-empty string the host or a completion gives. The type has no finite domain of its own; **check** explores it by representatives (PS4.1g).
- **PS1.5** **The control field may be a union.** `term` then depends only on its constructor. So `terminal intent is Done | Denied | Dead` is a predicate on the tag.
- **PS1.6** **Addresses.** `Ref<M>` is the type of addresses of instances of machine `M`. An address is a value: it can be held in state, carried in a message and compared with `==`. It cannot be dereferenced; nothing can read another instance's state. `none` is the empty address. In a configuration (PS13), the check domain of a `Ref<M>` is the set of addresses of the configuration's `M` instances plus `none`, so it is finite. In a machine checked alone, a `Ref<M>` ranges over `none` and `n` symbolic addresses `M#1 … M#n`, where `n` is the number of `Ref<M>` fields plus the largest number of `Ref<M>` parameters of one action; when `M` is the machine's own type, `self` is one more distinct address (S57), and each key of a detached spawn of `M` adds one more (S78). A detached child's address `<parent>/<k>` is absolute from the commit of the step that creates it (S78). An address is only compared with `==` or passed on, and a state and one step's data hold at most that many addresses of `M`, so every pattern of equalities among them is realised: the check is sound, and it adds no behaviour a real run cannot have.
- **PS1.7** **A machine may be a service.** `service` marks a machine that is never terminal (an inventory, a ledger). It is exempt from the per-instance deadlock check of PS5.6 and is covered by the configuration's quiescence check instead (PS13.6).
- **PS1.3** `term(s)` depends only on `s(control field)` (PT4.4a).

## PS2. Handlers denote functions

- **PS2.1** A handler for action `a` denotes a function

  ```
  h_a : S × T(a) → Verdict
  Verdict = accept(w, E) | reject(r)
  ```

  where:
  - `w` is a partial function from fields to values: the writes;
  - `E` is a finite sequence of effect intents (effects, timer sets and cancels, spawns, signals), in statement order;
  - `r` is a reason, a string literal from the handler's text.
- **PS2.2** A handler body is evaluated against the pre-state `s` and the data `d` as follows:
  0. **Names.** A bare name denotes the innermost binding: a local (`let` or a pattern binder), then a parameter of `a` (a component of `d`), then a field (a component of `s`). `pre.f` always denotes `s(f)`, so a field hidden by a parameter of the same name stays readable (S19).
  1. **Guards.** The guards in `G` are evaluated in declaration order, against `s`, `a` and `d`. A guard sees the parameters of `a` only where `action == A` narrows the action; elsewhere a bare name is a field (S19). The first guard whose condition holds yields `reject(r)` with its reason.
  2. **Body.** Statements are evaluated in order:
     - `require c else reject r` yields `reject(r)` if `c` is false and continues otherwise;
     - `reject r` yields `reject(r)`;
     - `let x = e` binds `x`;
     - `if c B1 else B2` evaluates the chosen branch;
     - `f' = e` adds `f ↦ value(e)` to `w`;
     - `f' = f with [k] = v` adds `f ↦ s(f)[k := v]` to `w`. Entry writes to one map on one path combine when their keys are distinct constants after unrolling (literals, constructors, or the index of different copies of a loop): `w(f) = s(f)[k1 := v1][k2 := v2]…` (S55);
     - `match e { C1 {x…} => B1 … _ => Bn }` evaluates `e`, binds the payload of the first arm whose constructor (and literal payload, if written) matches, and evaluates that arm's block. The compiler requires the arms to be exhaustive (`PL1501 NON_EXHAUSTIVE_MATCH`). So `match` never falls through, and handlers stay total;
     - `f' = C { q: e … }` writes a whole union value. A union field is always written as a whole value, never one payload field at a time;
     - `emit`, `after`, `cancel`, `spawn`, `signal`, `send`, `decide` and `adjudicate` append an intent to `E`. `adjudicate d as o` appends an intent of kind `outcome.d` carrying `o`; it is an effect of class `none`, so path properties count it like any other (S129). `send r <- A(d)` appends a **message** to the instance at address `r`; `self` is the sending instance's own address. An effect is also a message: `emit k(d)` sends `d` to the host actor that performs kind `k`, whose address is the handler's capability (PS1.6, PT6.5).
  3. **End.** If the body completes without a rejection, the result is `accept(w, E)`.
- **PS2.3** **Expressions read the pre-state only.** A primed field is write-only. Reading `f'` is a compile error (`PL1202 READ_OF_PRIMED_FIELD`). So the order of assignments within a handler does not change the result.
- **PS2.4** A field written twice on one control path is `PL2102 DOUBLE_WRITE`. A map is written twice when it is assigned twice, assigned and also written by entry, written twice at one constant key, or written at a key that is a field or a parameter on a path that writes another of its entries (S55). Therefore `w` is well defined.
- **PS2.5** All expressions are total (PT2.2): integer division truncates toward zero, `%` takes the sign of the dividend, and a divisor that may be 0 is rejected at compile time (`PL1204`). So `h_a` is a total function. **A machine is deterministic in its inputs**: for each state and each input there is exactly one verdict.

## PS3. Steps and the transition relation

- **PS3.1** A **label** is a triple `(a, d, v)` of an action, its data and a verdict kind:
  - `v = accepted(E)`;
  - `v = rejected(r)`;
  - `v = unhandled`.

  **Claims (PD5.1.2c, S101).** For an action whose handler is written `by c: C`, the label is `(a, d, c, v)`: the claims `c`, a value of the claims type `C` that a verifier outside poly asserts for the caller, are part of the label and the handler reads them as `c`. Every other action's label has no claims.
- **PS3.2** The transition relation `R_M ⊆ S × Label × S` contains exactly these triples `(s, (a, d, v), s')`, for every `s ∈ S`, `a ∈ A` and `d ∈ T(a)`:

  | Condition | Verdict `v` | Next state `s'` |
  |---|---|---|
  | `term(s)` | `rejected("terminal")` | `s` |
  | `d` violates a `strict` check domain of `a` (PT3.4) | `rejected("outside-check-domain")` | `s` |
  | `a ∉ dom(H)` | `unhandled` | `s` |
  | `a` requires claims of type `C`, and `c` is missing, malformed, or not a value of `C` (PD5.1.2c, S101) | `rejected("claims-unverified")` | `s` |
  | `d` holds a `Content` that names no body in the content store (S180) | `rejected("content-missing")` | `s` |
  | `h_a(s, d) = reject(r)` | `rejected(r)` | `s` |
  | `h_a(s, d) = accept(w, E)` | `accepted(E)` | `s ⊕ w` |

  `(s ⊕ w)(f) = w(f)` if `f ∈ dom(w)`, and `s(f)` otherwise. This is the **frame**: every field not written is unchanged.

  **Unhandled before data (S180 ruling).** An action with no handler is `unhandled` whatever its data: the claims and content rows apply only to a handled action. The claims row could never apply to an unhandled action, since claims are bound by a handler's `by c: C`; it moved with the content row so that the table states the rule once. The `content-missing` row was first written before `a ∉ dom(H)`, which made an unhandled action that carries a `Content` rejected when its body was missing; polyrun, which never sees an action outside the module's surface (PS9.1a), answers `unhandled`, and the table now agrees with it.

  **Data outside the type (S140).** The relation has steps only for `d ∈ T(a)`. An input outside its action's type is no label of `R_M`: the runtime refuses it before any step, with an error and an audit row and no journal row, as it refuses an outside completion (K9, K10). Replay never meets such a row.

  **Missing bodies (S180).** The `content-missing` row is applied by the runtime before it calls the module, from its content store: the step is journaled, the state is unchanged and nothing is emitted. In **check** every representative names a body, so the row never applies there; a `content-missing` step of **run** changes no state and emits nothing, so every invariant, step property and path property that holds on **check** holds on the paths of **run** that contain it, and a reject property cannot name the reason, as it cannot name `poisoned` or `archived`. **Erasure (S205).** The content store is erasable: the runtime's erasure of a body deletes it and keeps its digest, with an erasure record journaled on the runtime's own `runtime:content` run. An erased body stays erased: every later step whose `Content` names it is `content-missing`, and the same body presented again is not stored again. Only bodies and addresses (PS15.4) are erasable; the records the journal and the ledger keep by digest are not.

  **Reserved reasons (S101, S127, S180, S304).** The reasons the runtime uses are reserved: `terminal` and `outside-check-domain` (the two rows above), `poisoned` (an instance the kernel has poisoned), `archived` (K4), `claims-unverified` (the claims row above), `content-missing` (the content row above), `unknown-thread`, `thread-not-started`, `creation-unavailable` and `principal-mismatch`, with which the runtime refuses an inbound message (PS15.4, S450), `uncited`, with which it refuses a decision's answer that cites an item it was not given (PS17.6), and `route-exhausted`, with which it fails a routed decision whose tiers are spent (PS18.2). A handler's `reject` may not use them (`PL1207 RESERVED_REJECT_REASON`), so a rejection's reason always says whether the runtime or the module refused the step.
- **PS3.3** **Rejected and unhandled steps are steps.** They are transitions whose next state equals their current state, and they carry their verdict in the label, not in the state. They are journaled, they appear in traces, and properties over labels see them (PS5). Properties over states cannot distinguish them from not taking a step at all. This is the answer to the question "is a rejected step a step?": it is a labelled stuttering step.
- **PS3.4** An accepted step may leave the state unchanged (for example `Pay` in PT4.5, which only emits). It is still accepted, and its label carries its effects.

## PS4. Behaviours and the checked instance

- **PS4.1** The **environment** chooses each action and its data. A **path** is a finite sequence `s0 l0 s1 l1 … sn` with `s0 = init` and `(si, li, si+1) ∈ R_M` for every `i`. A **behaviour** is an infinite such sequence.
- **PS4.1a** **One machine, three interpretations of the environment.** The machine is the pure transition relation `R_M`. The environment is an interface with two operations:

  ```
  Env = { offer   : History → (Action × Data)          -- what happens next
          complete: Intent  → Completion               -- what the world does with an effect }
  ```

  Checking, simulation and running are three interpretations of `Env`, and nothing else:

  | Interpretation | `offer` and `complete` | What it produces | Engine |
  |---|---|---|---|
  | **check** | every action and every data value in `D(a)`, in every state; every completion | the set of all paths of `I` (nondeterminism) | polygraph, polyrun `check-effects`, poly-ref |
  | **simulate** | sampled from declared distributions and rates | a probability measure over paths (v2) | Polytrion |
  | **run** | whatever the world sends; intents go to real handlers under the effect gate | the one path that happens (IO) | the runtime |

- **PS4.1b** **Theorem (checked is running).** Every path produced by **run** whose inputs lie in the check domains is a path of **check**. *Proof:* the two interpretations apply the same `R_M` (PS2.5, and PS9 for the lowered module under K7), and **check** offers every input in `D(a)` in every state and every completion for every intent. For fields in `strict` mode, **run** cannot offer an input outside `D(a)`, because the runtime rejects it before the handler (PS3.2), so the condition holds by construction. Every parameter with a check domain is `strict` unless `disclosed` is written (PT3.4a, S400). For fields in `disclosed` mode, the theorem covers exactly the paths whose inputs stayed in the domain, and the others are journaled as drift. ∎ So every safety property that is `CLEAN` on **check** holds on every such **run** path.
- **PS4.1c** **Principals (PD5.1.3, S102).** A `Principal` is an opaque identity: a module compares it only for equality with another, stores it or passes it (`PL1206` otherwise). *Lemma (renaming invariance):* in such a module, for every bijection `π` on principals, `(s, l, s') ∈ R_M` iff `(π s, π l, π s') ∈ R_M`, since no handler, guard or property can tell two principals apart except by equality. So PS4.1b extends to claims and principals: every path of **run**, whatever principals it carries, is the renaming of a path of **check** over a finite set of representatives, provided the set is large enough. **check** offers every claims value, with every representative for each `Principal` field, in every state where the action can arrive. The number of representatives is the number of `Principal` positions in the state (a map holds one per key) plus the most principals one label carries (its parameters and its claims, at least one), and never fewer than 2; with one principal per label this is S102's rule, the positions plus one; the verdict prints it in its instance. A tighter bound enters only with the lemma's proof.
- **PS4.1g** **Keys (S451).** *Lemma (renaming invariance):* in a module where `Key` is opaque (PS1.4c), for every bijection `π` on keys, `(s, l, s') ∈ R_M` iff `(π s, π l, π s') ∈ R_M`, since no handler, guard or property can tell two keys apart except by equality, and no constant other than `none` names one. So PS4.1b extends to `Key`: every path of **run** is the renaming of a path of **check** over the representatives `none` and `k1 … kn`, `n` following PS4.1c's rule applied to `Key` apart (its positions in the state plus the most keys one label carries, never fewer than 2). A retrieval compares a key only for equality, so the items it returns are renamed with it. `Key`, `Principal` and `Content` are counted apart.
- **PS4.1h** **Ranges read only against constants (S458, ruled 2026-10-09).** Let `p` be a parameter of an action `a` of a machine `M` whose type is a range, written as one or named by a type declaration (not a field of a record, a key or value of a map, or a payload of a union), with domain `D`: its check domain, or every value of the range. A **use** of `p` is an occurrence of its name in `a`'s handler, or in a guard or a step property of `M` that reads `a`'s parameters. `p` is **cut** when every use is one of these two: a comparison `p op k` or `k op p`, `op` one of `==`, `!=`, `<`, `<=`, `>`, `>=` and `k` an integer constant; or an argument of an `emit` or a `decide` of `a`'s handler written as `p` alone, so that `p` is passed unchanged into the payload of an effect or a decision. Any other use turns the reduction off for `p`: arithmetic, a comparison with anything but a constant, an argument of a `send`, a `spawn`, a `signal` or an `after`, a write to a field, a `let`, a map index, or any other expression. A write to a field turns it off because a stored value can be compared after storage, by another handler, a property or a policy (`machine("m.M").f`). The **cut points** `C` of `p` are the constants of its comparisons; the constant `v` of each `emits(k, f: v)` in a step property of `M` where `p` is passed unchanged as the payload field `f` of `k`, read as `p == v`; and each constant a policy compares a payload field with, where `p` is passed unchanged into that field. v1's policies read no payload field (PT8), so no policy gives a cut point today, and none reads `p` otherwise. Two values `v, w ∈ D` are **equivalent** when every comparison of `p` with a cut point, as written, has the same outcome on both. **check** offers `p` at the least value of each class, its **representatives**, at most `2|C| + 1` of them. The runtime still refuses a value outside `D` (PS3.2, strict by S400): the reduction narrows what is explored, never what is accepted. *Lemma (cut invariance):* let `v` and `w` be equivalent, and `d` and `d'` two data of `a` that differ only in `p = v` and `p = w`. From every state `s`, the steps `R_M(s, a, d)` and `R_M(s, a, d')` have the same verdict and the same post-state, and their intents differ only in the payload fields where `p` was passed unchanged, which hold `v` and `w`: every expression of the handler and the guards that reads `p` is a comparison with a cut point, which has one outcome on both, and no field holds `p`. Every property of `M` has one truth value on both steps: a state predicate cannot read `p`, a step property reads it only against cut points, `emits(k, f: v)` compares the payload field with a cut point, and a path property counts kinds, which are the same. A policy decides both intents alike, since it reads neither payload value, or reads it against cut points. So replacing each value of `p` by its representative maps every path of **run** whose inputs lie in `D` onto a path of **check** with the same states, verdicts, intent kinds and property values, and PS4.1b extends to cut ranges. ∎ A configuration (PS13) offers each instance's inputs and completions at the same representatives, since a message to another machine is not a use the reduction admits. The verdict prints, for each cut parameter, its domain, its cut points and its representatives (PT12.3a). poly-ref computes the reduction from the source on its own, as it computes a `Conf`'s intervals (PD1.4b).
- **PS4.1f** **Content (S180).** *Lemma (renaming invariance):* in a module where `Content` is opaque (PS1.4a), for every bijection `π` on bodies, `(s, l, s') ∈ R_M` iff `(π s, π l, π s') ∈ R_M`, since no handler, guard or property can tell two bodies apart except by equality, and no constant other than `none` names one. So PS4.1b extends to `Content`: every path of **run**, whatever bodies it carries, is the renaming of a path of **check** over the representatives `none` and `c1 … cn`. `n` follows PS4.1c's rule, applied to `Content` separately: the number of `Content` positions in the state (a map holds one per key) plus the most `Content` values one label carries (at least one), and never fewer than 2. With two `Content` values compared for equality, two representatives show both outcomes, equal and different; one cannot. `Principal` and `Content` are counted apart, a body never being a principal, and the verdict prints both counts in its instance.
- **PS4.1c** A Polytrion world (v2) is a definition of **simulate** for a set of machines. The machines are unchanged. This is the formal content of the Polytrion principle "responders draw, machines decide, the kernel schedules".
- **PS4.1d** In **check**, the environment is unconstrained: every action, with every data value in its domain, may be offered in every state.
- **PS4.1e** **The bounded fragment.** Checks cover finite instances: finite domains, a finite number of instances, and a declared bound on messages in transit (PS13). The actor guarantee that a message is delivered after an unbounded but finite delay cannot be expressed in a finite instance. Liveness checks approximate it with fairness (PS6, PS14). The runtime implements the unbounded guarantee (R1, PS10).
- **PS4.2** The **checked instance** `I` restricts inputs to their check domains (every `d ∈ D(a)`) and states to theirs: a state is **in the instance** when every field `f` has `s(f) ∈ D(f)`. `Reach(I)` is the set of in-instance states on paths of `I` that stay in the instance. It is finite, because every field type in a checked machine is finite or restricted to a finite check domain (PT3.2).
- **PS4.2a** **Leaving the instance.** A transition from a state in `Reach(I)` can produce a post-state outside the instance in two ways, and they mean different things:
  - **Outside a declared type.** The post-state writes a value outside a field's declared type, such as `items: 0..3` becoming 4. The post-state is not in `S` at all. This is a program error: `PL3102 DOMAIN_ESCAPE`, a finding, with the path to the transition (PT3.5).
  - **Outside a check domain only.** The post-state stays inside the declared type (`int` or `string`) but leaves the field's check domain, such as a `term: int check 0..3` becoming 4. The post-state is a legal state that the instance does not cover. This is a **bound hit**: `PL3901 BOUND_HIT`, naming the field, with the shortest path to the boundary. The post-state is not explored, and the verdict is at best `INCONCLUSIVE`.

  Properties are still checked on every explored state, so a violation found inside the bound is still reported, and the fold of PT12.3 makes that verdict `FINDINGS`. A counter that grows without limit in the real system (a raft term, a coin count) is therefore checked up to its declared bound, and the verdict says so; it is never `CLEAN`.
- **PS4.3** **Every verdict is about `I`.** A `CLEAN` result states that a property holds on `Reach(I)` and on all paths of `I`. The instance is printed with the verdict (PT12.3a).
- **PS4.4** **Completion actions are ordinary actions.** In `I`, a completion such as `PaymentOk` can be offered in any state, whether or not a charge was emitted. So `I` over-approximates the real system: every real behaviour is a behaviour of `I`, but not every behaviour of `I` is real. For safety properties this is sound: a clean result holds for the real system. A witness may be infeasible if it uses a completion with no matching intent. Such a witness is marked `environment: unconstrained`, and the matching path property check (PS5.4) is the place to rule it out. A `send` is an intent in `E` like any other: a machine checked alone has no receivers, so the replies its receivers would send are ordinary actions the environment may offer in any state. This over-approximates too, and the configuration check (PS13) is where the receivers' actual behaviour is used (S30).

## PS5. Properties

There are five kinds of property. Each has its own keyword (PT5), and none is called an invariant unless it is one.

- **PS5.1** An **invariant** is a predicate `P` on states. `M ⊨ invariant P` iff `P(s)` holds for every `s ∈ Reach(I)`. The automatic `domain:<field>` properties (PT3.5) are invariants.
- **PS5.2** A **step property** is a predicate `Q(s, a, d, s', E)`, where `E` is the intent sequence of the step's verdict `accepted(E)` (PS3.2). It holds iff `Q` holds for every **accepted** transition from a state in `Reach(I)`. `Q` reads `d` only where `action == A` narrows the action, with the names of PS2.2 (S19). `Q` reads `E` only through `emits(k, f1: v1, …, fn: vn)`, `n ≥ 0`, which is true iff some intent of `E` is an intent of the effect named `k` (an `emit`, PS2.2), recognised by that effect's kind, whose payload field `fi` equals `vi` for every `i`. Each `vi` is a constant of its field's type: an enum constructor, an integer, a boolean, or `none`; `emits` reads no field, parameter or body. `k` is the effect's name, as `emit k(…)` writes it (PT2.2); a `send`, a timer, a spawn or a signal is not an effect, and naming one in `emits` is `PL1001` (S178). An intent, a witness and the journal carry an effect's kind and not its name, so two effects of one kind cannot be told apart: `emits` on either is `PL1201`. A rejected step emits nothing (PS3.2), so reading only accepted steps misses no intent.
- **PS5.2a** **`never emit` (S178).** `never n: emit k(f1: v1, …) while P` declares the step property `n: P(s) implies !emits(k, f1: v1, …)`, where `P` is a predicate on the pre-state alone: it names fields, and neither `post.`, a parameter nor `action`. It holds iff no accepted step from a reachable state that satisfies `P` emits the effect `k` with those field values. Without `while P`, `P` is `true`. `k` must name an effect the machine declares and each `fi` be a payload field of `k` (`PL1001`); a value outside its field's type is `PL1201`. A violation is a finding whose witness is the path to the pre-state and the step that emits. `P` reads the pre-state: a step that sends from a state where `P` holds is a violation whatever it writes, and a step from a state where `P` does not hold is not, whatever it writes. By PS4.4, `I` over-approximates every environment the machine runs in, a configuration included, so a `never` that holds on `I` holds for every instance of the machine in every configuration. A witness that uses a completion or a message nothing sent is marked `environment: unconstrained` (PS4.4); the configuration check evaluates the machine's `never` statements on that instance's global steps, which confirms such a witness or rules it out. A machine's `never` is not a policy's `never` (S149): the policy's is proved over the gate's decision table, and the machine's over `R_M`, before any gate. **Tested, or vacuous (ruled on M8 plan step 10).** A `never` is *tested* where it is judged (the machine's reachable graph, or a configuration's) when some reachable accepted step of the machine, or of its instance, takes an action whose handler can emit `k` (an `emit k` on some path of its body), from a pre-state where `P` holds. A `never` that is not tested holds for no reason the program gives: it is vacuous there, listed with the `never`, the machine or instance, and the reason (`P` holds in no reachable state, or it holds and no action that can emit `k` is taken from such a state), and the verdict is at best `INCONCLUSIVE` (PT12.3, S113), never `CLEAN`.
- **PS5.3** A **reject property** is a predicate `J(s, a, d, v)`. It holds iff `J` holds for **every** transition from a state in `Reach(I)`, whatever its verdict. `rejected(r)` in `J` is true iff `v = rejected(r)`. `J` reads `d` only where `action == A` narrows the action; elsewhere a bare name is a field of `s` (PS2.2, S19).
- **PS5.4** A **path property** is a predicate `Φ(π)` on finite paths. It is evaluated through `emitted(π)`, the concatenation of the intent sequences of the accepted labels of `π`, and `actions(π)`, the sequence of actions. It holds iff `Φ(π)` holds for every path `π` of `I`. Path properties must be **prefix-closed**: if `Φ` holds of a path, it holds of every prefix. The compiler accepts only forms that are prefix-closed by construction: `count(k) <= n`, `count(k) < n` (read as `count(k) <= n - 1`), `before(k1, k2)`, and their conjunctions. `count(k)` is the number of intents of kind `k` in `emitted(π)`, and `before(k1, k2)` holds iff every intent of kind `k2` in `emitted(π)` is preceded by an intent of kind `k1` (S37). Any other form is `PL1701 NOT_PREFIX_CLOSED`. So a path property is a safety property and has a finite witness.
- **PS5.5** A **liveness property** has one of two forms:
  - `eventually P`: every fair behaviour of `I` reaches a state satisfying `P`;
  - `P leads to Q`: in every fair behaviour, every state satisfying `P` is followed by a state satisfying `Q`.

  Fairness is defined in PS6. A liveness property is not a safety property and has no finite witness. Its counterexample is a **lasso**: a path to a cycle that can repeat forever.
- **PS5.6** **Deadlock.** A state `s ∈ Reach(I)` is a **deadlock** iff `¬term(s)` and no action accepts in `s`: for every `a` and every `d ∈ D(a)`, the verdict is not `accepted`. Deadlock freedom is checked for every machine, whether or not it declares a liveness property (`PL3201 DEADLOCK`, with the path to the state).

## PS6. Fairness

- **PS6.1** An action group `g` is a set of actions (written `A | B`). `g` is **enabled** in `s` iff some `a ∈ g` and some `d ∈ D(a)` give an accepted transition from `s`. `A(*)` in a fairness list stands for one group per data value: `{A(d)}` for each `d ∈ D(A)`. So `Send(*)` is fair to each message separately, and a sender that keeps sending one value cannot starve another.
- **PS6.2** A behaviour is **weakly fair for `g`**, written `WF(g)`, iff `g` is not enabled continuously from some point on without an accepted step of `g` being taken infinitely often. In words: an action group that stays enabled is eventually taken.
- **PS6.3** A liveness property is always stated with its fairness assumption: `liveness n: eventually P under fair { g1, g2, … }`. It is checked only over behaviours that are weakly fair for every listed group. Actions not listed carry no assumption: the environment may never offer them. A person's approval, for example, is not listed.
- **PS6.3a** Liveness under fairness is a game. The environment is an adversary that chooses inputs, constrained only by the stated fairness. A liveness property holds when the adversary has no strategy that avoids `P` forever. The lasso of PS6.4 is the adversary's winning strategy.
- **PS6.4** **Check.** Over the finite graph of `Reach(I)`, `eventually P` fails iff there is a strongly connected component `C`, of the states reachable from the initial state through states where `P` does not hold, with all of the following properties (S82):
  1. `C` contains no `P`-state.
  2. `C` contains at least one edge, where rejected and unhandled steps count as edges.
  3. For every listed group `g`, either some edge of `C` is an accepted step of `g`, or `g` is disabled in some state of `C`.

  **What a machine's liveness assumes (S463, ruled 2026-10-10).** In `I` a completion is an ordinary action (PS4.4), offered in any state, so a completion that a handler rejects is still offered afterwards and fairness may take another. At run time an intent is completed once, and a rejected completion consumes it. A liveness property of a machine therefore assumes that no completion of the program's own decisions and effects is rejected. The certificate states this assumption for each machine with a liveness property, with its status, and the finding of PS15.5 (`PL5409`) is what discharges it, in the configuration that models the runtime's one completion of each intent. The status is **discharged** when a generated configuration that covers the machine, one whose application it is, was checked and reported no `PL5409`; it is also **discharged by its form** when no completion handler of the machine can reject: none of the handlers of the actions named by the `ok`, `failed` and `exhausted` outcomes of its own decisions and effects contains a `require` or a `reject`, and the machine declares no `guard`, since a handler that cannot reject, and a machine with nothing that rejects every action, rejects no completion (the kernel's `terminal`, PS11, aside). It is **open** when neither holds: no generated configuration covers the machine and some completion handler can reject, or the configuration that covers it reported `PL5409` and a person accepted it (ruled 2026-10-10). The form is read from the handlers' syntax alone, so a handler whose `require` can in fact never fail is not discharged by it.

  This is the standard component test for weak fairness on a finite graph. `P leads to Q` is checked by the same test on the graph restricted to the part after a `P`-state, until `Q`. The counterexample is the path to `C` followed by a cycle through `C` that visits every edge the third condition names.

## PS7. Composition

Children come in two kinds. The author chooses, and the verdict says which semantics was checked.

- **PS7.1** **Attached children** (the default) form a **joint machine** with their parent. Its state is `(s_P, {k ↦ s_k})`, over the children spawned so far, and with each instance's status (active or terminal) and each child's wiring (its completion and cancel actions). The joint label is the **stimulus** `(target, a, d)`, where the target is the parent or a child key. The stimuli are offered as the kernel delivers them (S45): a terminal instance is offered nothing, and an action wired as the completion of a child is offered to the parent only once that child is terminal, because until then only the kernel delivers it, in the cascade. Inside a cascade, a delivery to a terminal instance is rejected and changes nothing. This rests on kernel assumption K9.
- **PS7.2** A joint step of attached children is the **cascade** of a stimulus: the stimulus's own transition, followed by every transition it causes, applied in order. These are completions to the parent, parent-terminal actions to children and signals, up to depth 8. The joint step is accepted iff the stimulus transition is accepted. A cascade that exceeds depth 8 is `PL5201 CASCADE_DEPTH`.
- **PS7.3** A **compose invariant** is an invariant (PS5.1) of the joint machine.
- **PS7.4** **Attached means co-located.** The cascade semantics is a model of the runtime only under K1 to K3, and K3 (one transaction per cascade) holds only if the parent and all its attached descendants are served by one kernel shard. The runtime shards by the root of each attached tree and refuses to place an attached child elsewhere (`PL5202 ATTACHED_ACROSS_SHARDS`). Every composition guarantee cites K1 to K3 and this rule.
- **PS7.5** **Detached children** (`spawn detached …`) are separate actors. `spawn` creates the instance and returns its address to the parent. From then on, parent and child communicate only by messages (`send`), which may arrive in any order. Their composition is checked as a configuration (PS13), not as a cascade.

## PS8. Policies

- **PS8.0** **Two truth types.** `Bool = {T, F}`. `Tri = {T, F, U}`, which is `Bool` lifted into an option type, with Kleene's rules for the missing case. The inputs a policy reads (the proposal, the action's labels, `machine(…)` fields, history) have **optional types**: any of them may be missing. A comparison or boolean operator applied to an optional operand has type `Tri`. Machine fields are never optional, so every machine expression has type `Bool`. `unknown(x)` has type `Bool`. A machine `require` demands `Bool`. A policy `when` or `require` accepts `Tri` and is evaluated by PS8.2. A `Tri` where a `Bool` is expected is a type error (`PL1203 TRI_WHERE_BOOL_EXPECTED`). The two logics are separated by type. One set of operators (`==`, `!=`, `&&`, `||`, `!`) serves both, and its meaning follows the operand types.
- **PS8.1** Policy expressions take values in `{T, F, U}`, where `U` is unknown.
  - `not`, `and` and `or` follow Kleene's strong three-valued logic: `not U = U`; `F and U = F`; `T and U = U`; `T or U = T`; `F or U = U`.
  - A comparison with an unknown operand is `U`.
  - `unknown(x)` is `T` or `F`, never `U`.
- **PS8.2** A `rule` obligation `when W require Q else s on unknown u` is evaluated for a proposal as follows. The severity `s` is `deny`, `warn` or `escalate`. The unknown handling `u` is `escalate`, `deny` or `skip`.

  | `W` | `Q` | Outcome |
  |---|---|---|
  | `F` | any | not applicable |
  | `T` | `T` | satisfied |
  | `T` | `F` or `U` | `s` (an unknown value never satisfies a requirement) |
  | `U` | any | `u` |

  **The default for `u`:**
  - For `s = deny`, the default is `escalate`. A deny rule whose condition cannot be evaluated never passes silently.
  - For `s = warn`, the default is `warn`.
  - `skip` must be written explicitly. It is listed in the certificate under `skippedOnUnknown`.
- **PS8.3** **Combination.** The gate's decision for a proposal is:
  - `deny` if any obligation's outcome is `deny`;
  - otherwise `escalate` if any outcome is `escalate`;
  - otherwise `allow`.

  Warnings are recorded with an `allow`.
- **PS8.4** **Labels.** In a scope where any obligation mentions `effects`, `labels` or `class`, an effect or tool with no labels is **refused at admission** (`PL6302 UNLABELLED_IN_LABELLED_SCOPE`, verdict `REFUSED`). An unlabelled effect cannot make a label-based rule's `when` unknown at runtime.
- **PS8.5** `machine("<module>.<Machine>").f` is the value of `f` in the snapshot under evaluation: the post-state of the step that emitted the effect under decision (PT9.3). It is `U` for a proposal that is not an effect of that machine. **An approved re-proposal (S401)** is evaluated twice, with the approval: against that snapshot, and against the emitting instance's latest post-state when the approval re-proposes it. The gate's decision is `allow` only if both evaluations allow; otherwise it is `deny`, with the reason `stale-approval` when only the later snapshot denies. In **check**, the later snapshot may be any state of `Reach(I)` reachable from the emitting state, since the instance can step while the intent waits; the decision table already gives every machine field every value of its type or check domain, a superset of those states, so the policy stage evaluates every row with the approval as well as without it. The combination only removes allows, so a policy `never` proved over single rows holds of it, and a policy that allows on the emitting snapshot and denies on a later one is not a finding: that is the rule's intended effect.
- **PS8.6** **Consistency of obligations.** Obligations in one scope come from several sources: declared policies, promoted Polyx rules, recalled text and native kernels. Each decision is resolved by PS8.3, but the obligations may still contradict each other as a whole. A mandate `m` is **dischargeable** under a set of obligations `O` iff some path over the scope's **tool alphabet** reaches a discharge state of `m` with no `deny` outcome on the way. The tool alphabet is the set of actions the scope's tools can perform, with their labels. The declared action alphabet is used only when the scope has no tool catalogue, and the certificate records which alphabet was used. This is Polyaxion's admission condition m2, "lawfully dischargeable".
  - **A possibility property.** Dischargeability says that a good path *exists*. Every other property in this document constrains *all* behaviours. It is not a property of behaviours: a system whose behaviours all satisfy every PS5 property may fail it, and the converse. It is checked as reachability on the explored graph of the scope's policy machines, not with the machinery of PS5 and PS6, and diagnostics name it as a possibility property.
  - If `m` is not dischargeable, the finding (`PL6501 UNDISCHARGEABLE_MANDATE`) names **a minimal conflicting subset** `O' ⊆ O`: `m` is not dischargeable under `O'`, and it is dischargeable under `O' \ {o}` for every `o ∈ O'`. It is minimal, not necessarily smallest. Different deletion orders can find different minimal subsets, so the order is fixed for reproducibility: obligations are tried for removal in declaration order, then promoted rules in promotion order.
  - The check runs at admission and again on **every promotion** of a mined rule, because promotion is when rules written from different evidence first meet.

- **PS8.7** **Which messages cross the gate.** Every instance has a **trust scope**: the scope of its module's policy, or the scope its configuration assigns to it.
  - A `send` whose sender and receiver are in **different** trust scopes is proposed to the gate, exactly like an effect. A send within one scope is not.
  - Effects to capability addresses are always proposed, as before (PT9).
  - **A denied send** is not delivered. Instead, the message `SendDenied(to, action, reason)` is delivered to the sender itself, as an ordinary message. The sender may handle it; if it has no handler, it is an unhandled step, journaled like any other. A denied send is therefore visible in the sender's behaviour and in the checked configuration, where the gate's decision is an environment choice among allow, deny and escalate (PS4.4).
  - Governance thus sees every message that leaves a trust scope. "One mechanism" holds for control as well as for execution.
- **PS8.8** **The age of claims (PD6.1, S195, S196, ruled for M9).** The verifier adapter may give, beside a step's claims, the time it checked the presentation (`verifiedAt`) and the time of the status information it used (`statusAt`); they are kept with the step and bound into its ledger event. A policy reads `age(step.claims)` and `statusAge(step.claims)`, integers in milliseconds: the decision time minus `verifiedAt`, and minus `statusAt`. The decision time is the runtime's clock when the gate decides, and the ages it gave are recorded in the `verdict` event, so replay uses the recorded ages and never reads a clock (PS11). An age is unknown (`U`) when its time is missing, or lies after the decision time; it is never taken as fresh, and `on unknown` decides (PS8.2).
  - **Checking.** Each age is explored by the intervals the policies' thresholds cut (PT20.3): for a scope whose rules compare an age with thresholds `t1 < … < tn`, the values `0`, each `ti` and `ti + 1`, and unknown. The decision-table check (S149) covers them, so a `never` over ages is proved or refuted with a witness like any other.
  - **Stale claims are denied, never refreshed (S198, as amended by the owner's ruling).** A rule over an age denies: its severity is `deny`, and a rule over an age written `escalate` or `warn` is refused (`PL1201`); an escalation may still be raised on other grounds, and an unknown age follows `on unknown`. A proposal a rule over an age denies is denied with the reason `stale-claims`, journaled. The runtime does not refresh the claims: the host dispatches the action again with a fresh presentation, which is a new step and a new intent, checked by the gate like any other, and is bounded by the host's own logic.
- **PS8.9** **Mandates that only narrow (PD6.2, S195, S197, ruled for M9).** A **mandate** is evidence the verifier adapter may give beside a step's claims: `{ id, delegator, delegate, scope, expires }`, with its chain of parent mandates, outermost first. A **scope** is a conjunction of: a finite set of allowed actions (effect kinds); per payload field, a finite set of allowed values or an upper bound on an integer; and the expiry. `scope(c) ⊆ scope(p)` iff each constraint of `p` is present in `c` and at least as tight: every allowed action of `c` is allowed by `p`, every allowed value of a field in `c` is allowed by `p` for that field, every upper bound of `c` is at most `p`'s, and `expires(c) ≤ expires(p)`. Subset is decided field by field.
  - **The narrowing rule (K12).** For each hop of a chain, the child's scope is within its parent's (`⊆`), and the child's delegator is the parent's delegate. A chain that widens anywhere, or that holds a revoked mandate, is refused before any step: the dispatch is refused `mandate-widened` (or `mandate-revoked`), written to the audit log, and no instance changes, as an input outside its type is (S140).
  - **Every action, not the first.** Each proposal for an effect of a step that carries a mandate is checked against the innermost mandate's scope at the decision time: its kind among the allowed actions, each constrained payload field within its values or bound, and the decision time before the expiry. Otherwise the proposal is denied `outside-mandate` before any policy runs (S199), on the tenth action as on the first. Policies read `step.claims` for the principal and `step.mandate.delegate` and `step.mandate.delegator` for the agent and the person it acts for; the agent is never the delegator.
  - **Revocation.** Revoking a mandate revokes every mandate beneath it: a chain that holds it is refused at the next dispatch, and a proposal from a step whose chain holds it is denied `outside-mandate`.

## PS9. Lowering correctness

- **PS9.1** Let `L(M)` be the lowered module. Let `R_L` be its transition relation under the SAM v2 strict profile. For each `(s, a, d)`:
  - an acceptor rejecting with `r` gives `rejected(r)`;
  - writes to `next`, with the declared `unchanged`, give the next state;
  - the effects mapper applied to the step gives `E`.
- **PS9.1a** Rows 1, 2, 4 and 5 of the table in PS3.2 (terminal states, strict check domains, claims and content) are applied by the runtime before it calls the module: the lowered module's first acceptors apply them, before any guard. `R_L` is therefore the module's relation with those rules applied first, exactly as the runtime applies them. An action with no handler is not in the module's action surface (S35), so the runtime answers it without calling the module: row 1, `rejected("terminal")`, in a terminal state, and row 3, `unhandled`, elsewhere (row 2 never applies: a parameter is `strict` by default only when its action has a handler, PT3.4a and S400, and an explicit `strict` on a parameter of an action with no handler is `PL1302 STRICT_ON_UNHANDLED_ACTION`, S53). Those steps are part of `R_L` and are compared like any other.
- **PS9.1b** **Flattening unions.** A union field `f` lowers to a tag field `f` plus one nullable field `f_<payload>` per payload name of any constructor, because the SAM sealed shape is flat. Below the top of a field, where no flat key exists (a map's value, a payload, a parameter), a union with payloads lowers to one object `{ "$": "C", p: v, … }` with exactly its constructor's payloads, recursively, and `α` reads it back; a union with no payload is its constructor's name (S65). Constructors that share a payload name share its field, which requires the same type (`PL1601 PAYLOAD_TYPE_CONFLICT` otherwise). The abstraction function `α` maps a flat state back to a structured one. The lowering adds one automatic invariant per union field (`shape:f`): the payload fields of the current constructor are present, and all others are null. PS9.2 compares `R_M` with `R_L` through `α`.
- **PS9.2** **The lowering is correct for `M` on `I`** iff `R_L` and `R_M` agree on every `(s, a, d)` with `s ∈ Reach(I)` and `d ∈ D(a)`. They must give the same verdict kind, the same reason, the same next state and the same intent sequence. The lowered property modules must also agree with PS5 on every reachable state and transition.
- **PS9.3** **Translation validation on every check.** `poly check` runs `poly-ref`, poly's own model checker and reference interpreter, written directly from this document and sharing no code with the compiler. It explores `I` and compares every transition with the lowered module's. A difference is `PL2501 LOWERING_MISMATCH`. The verdict is `REFUSED`, and the diagnostic is addressed to the toolchain, not to the author. This makes the lowering's correctness a checked fact for each program, not a claim about the compiler.

### Runtime obligations

A kernel assumption is something the semantics relies on. A runtime obligation is something the semantics *defines*, and which the runtime must implement. When an obligation is not met, the runtime is at fault, not the program or the specification.

| Id | Obligation | How it is watched |
|---|---|---|
| R1 | **Delivery (PS14).** While the runtime is up, every message in transit is eventually delivered, every intent is eventually completed or refused, and every due timer eventually fires. | Queue-age and timer-lag monitors, with an alarm when an age exceeds its declared bound. The ledger records every delivery, so a missing one is visible after the fact. |

## PS11. The gate and replay

- **PS11.0** **The gate is an actor.** It has its own state (Σ per session), it processes one proposal or settle at a time per session, and its only inputs are messages. The order that determines its decisions is its own **arrival order**, recorded as `sseq`. No global order exists, and none is needed. It follows that:
  - a session is a serialisation point: all proposals of a session queue at one actor, and throughput is measured per session (PT9.6);
  - the gate can be sharded along sessions, and only along sessions;
  - a policy that needs state across sessions needs another actor, reached by messages. It cannot share a variable.

- **PS11.1** Each gate session has a **session sequence** `sseq`. The gate assigns it on receipt of every proposal and every settle. Each ledger event carries its `sseq` and the digest of Σ before the event.
- **PS11.2** **Replay of a session** re-applies its events in `sseq` order. It must reproduce every decision and every Σ digest. By K6, this reproduces the gate's behaviour exactly.
- **PS11.3** **Replay of a run** reproduces every post-state from the run's own chain (K1, PS2.5). It reproduces gate decisions when the sessions the run touched are replayed with it.
- **PS11.3a** **Forgotten steps (M10, S306).** A step whose data names a body that a `forget` erased (PS17.7) is **forgotten** on replay: replay reports it with the `forget` event that erased the body, takes the step's recorded post-state, and goes on. A forgotten step is not a divergence, and the replay report lists it.
- **PS11.4** **Replay is a fold.** A run's state after `n` steps is `foldl δ init [l0 … ln-1]`, where `δ(s, (a, d, _))` is the next state given by `R_M`. The replay theorem is then one line: `δ` is a function (PS2.5), so the same journal gives the same fold. The runtime stores the journal, and the state is the fold's cache (the snapshot). A snapshot that disagrees with the fold is a kernel fault, not a program fault. **Replay takes what the checker admits (ruled 2026-10-10).** `δ` on replay is the `δ` the checker explored: a step's data is read as its handler read it, an `Items` as the value whose `count` the handler reads (PS1.4b), its reference opaque. A program the checker admits replays every run the runtime ran: a step the runtime took and replay refuses is a fault of replay, never of the program.

## PS12. Expression syntax: precedence

From tightest to loosest binding:

| Level | Operators | Associativity |
|---|---|---|
| 1 | field access, indexing `m[k]`, calls `count(…)`, `before(…)` | left |
| 2 | `!` `-` (unary) | right |
| 3 | `*` `/` `%` | left |
| 4 | `+` `-` | left |
| 5 | `<` `<=` `>` `>=` `in` | none |
| 6 | `==` `!=` | none |
| 7 | `&&` | left |
| 8 | `\|\|` | left |
| 9 | `implies` | right |

The canonical formatter inserts parentheses whenever `implies` is mixed with `&&` or `||` in one expression. So `executed implies (decisions <= 1 || approved)` is the only printed form of that invariant, and neither the author nor a reader has to remember level 9. `e is C` (constructor test, type `Bool`) binds at level 5. Policies use the same operators; their meaning follows the operand types (PS8.0).

## PS13. Configurations

- **PS13.1** A **configuration** `C` is a finite set of named instances. Each instance has a machine, an initial state (including initial addresses) and a flag telling whether the machine is a service. `C` also declares:
  - its **inputs**: the actions the environment may inject, at which instances;
  - its **bounds**: the maximum number of messages in transit `B`, and the maximum number of instances `N` (detached spawns create instances).
- **PS13.2** A **global state** is a pair `(σ, μ)`:
  - `σ` maps each instance to its state;
  - `μ` is the **set of identified messages** in transit. Each message is `(id, target, action, data)`. Its identity is `id = (sender, sender's step number, position among that step's intents)`, the model's image of the runtime's idempotency key.
- **PS13.2a** **Copies are indistinguishable to the receiver.** Two messages with the same `(target, action, data)` produce the same step at the receiver, whatever their identities. The explorer therefore keeps `μ` as a multiset of values, and a delivery of a value consumes its **oldest** copy. This quotient loses no behaviour: every delivery sequence of identified messages maps to one with the same states and labels. So it is exact for safety.
- **PS13.2b** **Fairness per identified message.** In the quotient, weak fairness of each value's delivery, together with oldest-copy delivery, implies that every identified message is eventually delivered. Proof: while a value `v` is in transit, its deliveries are enabled. Weak fairness makes them happen repeatedly. Each delivery removes the oldest copy. A given copy has at most `B - 1` copies ahead of it (PS13.5), so it is delivered after at most `B` deliveries of `v`. ∎ Liveness checks use this fairness (PS14.2).
- **PS13.3** A **global step** is one of:
  - **input**: the environment injects a declared input `(i, a, d)`;
  - **delivery**: any one message in `μ` is removed and delivered to its target.

  In either case the target takes its step by `R_M` (PS3.2). The intents of an accepted step are handled as follows:
  - its `send` messages are added to `μ`; a send to `none` adds nothing and is a finding (`PL5404 SEND_TO_NONE`, S29);
  - its detached `spawn` intents create new instances, each at the address `<parent address>/<k>`, in its machine's initial state, with its creation action as its first message; instances spawned from `M` join the group `M`, and `N` counts every instance (S60). A spawn of a key whose instance already exists creates nothing and is `PL5101 CHILDKEY_COLLISION`, checked before the instance bound (S83);
  - its other effects and its timers are completed by the environment only through the configuration's declared inputs: a completion action not listed there is never offered (S61).

  A delivery to an instance that rejects the message is a rejected step: the message is consumed and the state is unchanged.
- **PS13.4** **Arrival order is nondeterministic.** Any message in transit may be delivered next, whatever order the messages were sent in. This is the only order a configuration assumes. Two messages from one sender to one receiver are not assumed to arrive in order unless the configuration declares `fifo` for that pair.
- **PS13.5** **Bounds are reported, never silently applied.** A step that would exceed `B` messages in transit or `N` instances is not explored. The verdict is then at best `INCONCLUSIVE`, with `PL5301 TRANSIT_BOUND_HIT` or `PL5302 INSTANCE_BOUND_HIT` and the bound. It is never `CLEAN`.
- **PS13.6** **Properties of a configuration.**
  - A **configuration invariant** is a predicate on `σ`.
  - **Instance groups and quantifiers.** `g[*]` may appear only as the argument of an aggregate: `count`, `sum`, `all` or `any`. Everywhere else a group must be quantified explicitly: `forall i in g: P(g[i])` or `exists i in g: P(g[i])`. An unquantified `g[*]` outside an aggregate is `PL5403 UNQUANTIFIED_GROUP`. In a liveness property, the quantifier scopes over the whole `leads to`: `forall i in order: order[i] is Asked leads to order[i] is Done | Refused` means that each asked order is eventually settled.
  - **Instance fields (S32).** `x.f` and `g[i].f` denote field `f` of an instance in `σ`. `g[i] is C` denotes `g[i].f is C` for the one field `f` of the machine whose type has the constructor `C`; with none or several such fields it is `PL1005`. Only configuration properties read instances' fields (PS1.6).
  - **`init(e)`** is the value of `e` in the configuration's initial state. Properties refer to initial quantities through `init`, never through constants explained in comments.
  - A **quiescent** global state has `μ` empty and no declared input accepted.
  - A **stuck** state is a quiescent state in which some non-service instance is not terminal. It is reported as `PL5402 STUCK`, the configuration's form of deadlock.
  - **A message its receiver refuses outside its domain (F4 of the probe review of V1 to V5).** Since S400 a receiver's parameters are `strict` by default, so a message whose data lies outside the receiving action's strict check domain is rejected `outside-check-domain` when it is delivered, and the sender is not told. Such a delivery is `PL5408 MESSAGE_OUTSIDE_DOMAIN`, a finding, with the path to it as its witness, in every configuration that reaches it. On a machine alone, an accepted step whose `send`, `spawn` creation or `signal` carries, to a machine whose action it names is known (a `Ref<M>` field or parameter, a spawn, an attached child), data outside that action's strict check domain is `PL5408` too, with the path to the step: the sender's exploration offers the values it can send, and the receiver's domain is read from its declaration. A value the receiver declares `disclosed` is not reported. No silent clean: a send the receiver would refuse is a finding wherever it is judged.
  - Liveness properties (`P leads to Q`) are checked under the delivery guarantee (PS14) and any stated fairness. In a configuration the fairness clause may be left out: delivery is fair by PS14.2, and an input is fair only if the clause names it (S56).
- **PS13.7** **Interpretations.** The three interpretations of PS4.1a apply to configurations unchanged:
  - **check** explores every input and every arrival order within the bounds;
  - **simulate** samples them (a Polytrion world, v2);
  - **run** is the deployed system.

  The theorem of PS4.1b extends: every run of the deployed instances, whose inputs are in their domains and which stays within the bounds, is a path of the check interpretation, up to the choice of linearisation.
- **PS13.8** **The happens-before argument.** A deployed configuration does not execute a sequence of global steps. Instances step concurrently on different workers, and no one observes a global state. A run is a partial order of events under the causal relation `→`: a step precedes the next step of the same instance, and a send precedes the delivery of that message. The proof of PS13.7 is:
  1. **Commutation.** Every step touches one instance's state and adds messages to `μ`. So two steps of different instances that are unordered by `→` commute: applying them in either order gives the same global state.
  2. **Linear extensions.** Every linear extension of a run's partial order is therefore a sequence of global steps. It is a path of **check**, because **check** delivers any message in transit in any order (PS13.4).
  3. **Coverage.** A configuration invariant that holds on every path of **check** holds in every state of every linear extension, however the run is linearised. ∎
- **PS13.9** **Monitoring.** A configuration invariant is a statement about global states, which no participant observes. It constrains the system's behaviour, but no runtime monitor can check it directly. It is monitored either by taking a consistent snapshot of the instances (a cut closed under `→`) or offline, over the ledger, by replaying one linear extension of the recorded partial order.

## PS14. Delivery

- **PS14.1** **Every message sent is eventually received.** This is part of the meaning of `send`, not an assumption about a kernel. In a behaviour of a configuration, every message added to `μ` is eventually delivered. Every intent is eventually completed or refused. Every due timer eventually fires.
- **PS14.2** In the check interpretation, this is **weak fairness of each identified message's delivery**, realised in the explorer as weak fairness per value with oldest-copy delivery (PS13.2b). A message in transit stays deliverable until it is delivered, so weak fairness is enough. Liveness checks (PS6.4) include these fairness constraints automatically, so an author states only the fairness of the machines' own actions.
- **PS14.3** At runtime, delivery is obligation R1 (PS10). Delivery is at-least-once through the outbox, and the receiver deduplicates on the message's idempotency key (K4 with its lifetime). The claim that each message takes **exactly one step at its receiver** is a property of the delivery protocol. That protocol is modelled as the `Delivery` machine (PT9.8) and checked: at most one step per message always, at least one under fairness, and in-order delivery for the in-order worker. The runtime's conformance to that model is kernel assumption K8, checked by trace replay at M4.

## PS15. Channels

- **PS15.0** **A channel adds no step, verdict or property of its own (M8b).** `channel c: k { … }` in module `m` means the program obtained by the expansion of PS15.1 to PS15.5, and every other section reads the expanded program. `k` names the module `std.channels.k`. It declares the machine `Conversation`; its peer machine `Peer`, an interface whose actions are the messages the conversation sends to the application, with no state and no handler; and the conversation's actions `Open(app: Ref<Peer>)`, `Inbound(…)`, `Reply(…)`, `Template(…)` and `Ack()`. Of the `Peer` actions, `Delivered`, `Rejected` and `Failed` are the conversation's **receipts**; `Ack()` is the application's acknowledgement of one. The checker and poly-ref each expand a channel from this text, and neither is given the other's expansion.
- **PS15.0a** **A channel's recipients (M10, S305).** `audience c` in a channel declares the class of its recipients, which the flow rule reads for its provider effect `channel.c.send` (PS17.3). A channel with none has recipients of the lowest class. **The thread's principal (S450).** Without `principal from`, the thread's recipient has no principal a module names, so an owned item reaches a channel's recipient only by class. A channel that declares `principal from f`, `f` a field of type `Principal` of its kind's `Sender` claims, gives each thread a principal: the value of `f` in the verified claims of the first `Inbound` of the thread that names one, fixed from then on. The claims come from the verifier (K11), never from a message's content or a parameter. The recipient of the thread's provider effect `channel.c.send` has the thread's principal (PS17.3), and a body received on the thread is owned by it (PS17.4). A thread whose principal is not fixed has a recipient with no principal, so a reply that carries owned content is refused at run time (fail closed). In **check**, a channel configuration (PS15.5) records each conversation's thread principal in its global state: the first `Inbound` fixes it to the principal its claims carry, and the environment offers a later `Inbound` only with claims that name the same principal, since the runtime refuses any other (PS15.4). **One value for a principal nothing reads (b6318b4c, confirmed 2026-10-09).** A `Principal` field of an action's claims is explored by one value only when nothing reads it: its handler never reads the field; no policy reads it, since a policy reads no `Principal` field of claims (PT8: `step.claims.f` and `lineage.origin.f`); and no `principal from` reads it, so the action is not the `Inbound` of the conversation of a channel that declares `principal from`; and the machine's claims carry no `Audience` field, which the flow rule reads with its claimant (S324). Every value then gives the same step by PS4.1c's renaming invariance, and **check** explores it by its first value. Otherwise **check** offers every representative for it, on the machine alone and in every configuration: a conversation whose channel declares `principal from` is explored with every representative of the Sender's principal, alone and in its channel's configuration. In a channel configuration the Sender's principal is also explored with every representative when the application's bound actions take claims, which pass it to the application's handlers (PS15.4). A std conversation never reads it, so a channel without either explores what it explored before S450.
- **PS15.1** **The conversation of a channel.** The channel instantiates `Conversation` as the machine `m.c.Conversation`. Its peer type becomes `Ref<A>`, `A` being the application machine the channel names. Each message it sends its peer under a name `N` is renamed to the action of `A` the channel maps `N` to, and its provider effect `send` takes the kind `channel.c.send`, one kind per channel, so a policy tells channels apart. The binding is checked: it is total, every `Peer` action mapped (`PL6813`); one-to-one, no two `Peer` actions mapped to one action of `A` (`PL6814`); and typed, each mapped action of `A` having the `Peer` action's parameters, by name and type (`PL6815`). The instance keeps the conversation's states, handlers and properties.
- **PS15.2** **The link.** The handler of the action `starts` names gains, as its last statement, `spawn detached m.c.Conversation as c -> Open(app: self)`. The child key is the channel's name, fixed by the compiler (S177), so the conversation of the application instance at address `p` is at `p/c`. `self` is legal as a whole argument of a detached spawn's creation action, as it is of a `send` (S58, S177). A key `c` used otherwise in `A` is `PL1002`.
- **PS15.3** **The rewrite.** In `A`'s handlers, `emit c.reply(args)` is `send c <- Reply(args)` and `emit c.template(args)` is `send c <- Template(args)`, `c` reading the address of the child spawned under that key (PS7.5). Only the conversation emits the provider effect `channel.c.send`. Since `c.reply` is a message after the rewrite, `never … emit c.reply` or `emits(c.reply)` in `A` is `PL1001`, and the rule is stated on the conversation (S178). Each handler of `A` bound to a receipt gains, as its last statement, `send c <- Ack()`: an accepted receipt step acknowledges the receipt, so the conversation can hold its slot until its receipt is consumed and count it in `pending`, and every message between the two is then bounded by `pending`'s bound. A rejected receipt step sends nothing (PS3.2), so its receipt stays unacknowledged. `Ack` is the expansion's alone: an author neither writes nor binds it, and it is outside the binding and its checks (PS15.1, `PL6813` to `PL6815`).
- **PS15.4** **Inbound.** A message from the provider is the action `Inbound` of the conversation at `p/c`, `p` being the application instance its thread key names. The thread key is a checked string computed from the message's fields by the channel's template (PT21.1b), and is used only to name the instance. When no instance has the key:
  - if the channel declares that inbound creates the application (`starts A.S on inbound`), the runtime creates it, takes the `starts` step with its spawn of the conversation, and then delivers the message to the conversation, in that order, each journaled. A `starts` step that is rejected refuses the message, with the reserved reason `thread-not-started`;
  - otherwise the message is refused with the reserved reason `unknown-thread`.
  - while the runtime's kernel cannot create an instance by a detached spawn (polyrun before E13), a message that would create the application is refused with the reserved reason `creation-unavailable`, before any instance is created.

  On a thread whose principal is fixed (PS15.0a, S450), a message whose verified claims name another principal is refused with the reserved reason `principal-mismatch`, before it reaches the conversation, and the thread keeps its principal.

  **Addresses (S191, S205).** A thread key, and each message field its template reads, is an address (a phone number, an email address, a Slack channel id). At run time no address enters the journal or the ledger: before the message is delivered, each field the template reads is replaced by its keyed digest, an HMAC under the store's own key, and `p` is `c:` followed by the keyed digest of the thread key. Each address is kept in the erasable content store under its keyed digest, and the send of `channel.c.send` reads its recipient from there; a send whose recipient was erased fails permanently, journaled, and the conversation is told as of any failed send. The sender a channel's adapter verifies (K11) is journaled by its keyed digest too. One address gives one digest in one store, so the replacement is a renaming of the field's values: a conversation that reads a thread-key field only to compare it for equality, or not at all, takes the same steps, and the conversations of `std/channels` do not read one. So PS4.1b carries over to the renamed values as it does to `Content` (PS4.1f).

  Every refusal is journaled on the runtime's own `runtime:ingress` run. An `unknown-thread` refusal creates no instance. A `thread-not-started` refusal follows the creation and its rejected `starts` step, both journaled: the application exists in its initial state with no conversation, and each later message on its thread is refused the same way: such a thread stays dead. Until its conversation is spawned, `c` names no instance, and a send to it is refused as one to an address that names no instance: dead-lettered and journaled on the sender's run (S89), and `PL5404` in a configuration, as a send to none is. The conversation sends the message to its peer, which the renaming of PS15.1 makes `A`'s mapped action. **Claims on the bound action (S450).** An action of `A` that the binding maps a `Peer` action to may declare `by c: C`, where each field of the claims type `C` is a field of the kind's `Sender` claims of the same name and type (`PL6815` otherwise). Delivered from the conversation, it takes as its claims the claims of the step that started the message's chain (PD5.2.2a), the verified claims of the `Inbound` that caused it, restricted to `C`'s fields; a message whose chain started with no claims gives it none, and PS3.2's claims row rejects the step `claims-unverified`. In a configuration a delivered message carries its origin's claims the same way, so `A` reads the principal its conversation's thread was fixed to; on `A` alone the action is an input with every value of `C`, as any action with claims is. A provider's report that a rule of the conversation reads (an email bounce, a failed webhook delivery, a Slack channel found archived) reaches the conversation as a **provider event**: an `Inbound` of that event on the thread, with the action id `<channel>:<provider's id>`, or the completion of the `send` the report concerns. A report no rule reads is recorded on `runtime:ingress` and reaches no instance.
- **PS15.5** **The checked configuration.** Each channel gives the configuration `c` (PS13), named after the channel in every report so a finding can be traced to it: the instance `app: A`; its conversation, the detached child `c` that `starts` spawns; the inputs `A`'s `starts`, the conversation's `Inbound`, and the completions the conversation's provider effect is wired to (the provider's receipts); the transit bound the conversation's declared `pending` bound, `N` for its field `pending: 0..N`, plus one for each other channel `A` is bound to, `N + n - 1` for `n` channels; and the instance bound one plus the number of channels `A` is bound to: the application and every conversation its `starts` handler spawns (ruled on the review of M8b, A-F2). Another channel's conversation is an instance of `c`, and `c` offers none of its inputs, arms none of its timers and checks none of its `never` statements, which its own channel's configuration checks. Having no inputs, each of those `n - 1` conversations holds at most its creation message `Open(app)` in transit beside the `N` of `c`'s own conversation, hence the transit bound (ruled on the review of M8b, A-F2). The report lists, per configuration, the instances whose `never` statements it checked and those it left to their own configuration. **The provider's clock (ruled on M8 plan step 10).** The inputs of the configuration `c` also include the completion of each of the conversation's timers (`after d -> X() as k`), which may fire an armed timer at any time. The global state of `c` records which of the conversation's timers are armed, with the action and data each will deliver: an `after` arms its key, and an `after` on a key that is already armed re-arms it, so a key has at most one pending firing, as at run time; a `cancel` disarms it; the environment offers `X` only while `k` is armed, and the firing disarms `k` before the step it starts. Durations are not compared: any armed timer may fire before or after any other step (PS4.4). **The application's completions (S456, ruled 2026-10-08).** The inputs of the configuration `c` also include the completions of the application's pending decisions and effects, each offered only while its intent is pending, as an armed timer's firing is. The global state of `c` records, for the instance `app`, the kind of each intent of a decision or an effect that an accepted step of `app` emitted and whose completion has not been delivered: its **pending intents**, a multiset. While an intent of kind `e` is pending, the environment offers each completion that `e`'s declaration names, over every value of its data: a decision's `ok` over every answer and every interval of its confidence and margin (PD1.4b), its `failed`, and a routed decision's `exhausted`; an effect's `ok` and `failed`. A step of that completion, whatever its verdict, takes one pending intent of `e` off, so each intent is completed at most once and a completion arrives only for an intent in flight, as at run time. An intent whose declaration names no completion is never pending, and a completion of a kind with no pending intent is not offered. **A rejected completion is a finding (S463, ruled 2026-10-10).** A reachable step of `app` that is one of these completions, of an intent pending in its pre-state, and that its handler rejects, is `PL5409 COMPLETION_REJECTED`, with the path to it as its witness, as a receipt the application rejects is `PL5406`: the rejected step leaves the application where it was and takes the intent off, so nothing completes that intent again and the application may wait for it for ever. It is reported once per action of the application, at its first step in breadth-first order, whatever the reason, except `terminal`: a completion that reaches an application that has ended leaves nothing waiting. The finding holds the configuration to the assumption of PS6.4. A handler that handles every completion it is offered, with an `if` and not a `require`, has none. A step that would hold more than 3 pending intents of one kind is not explored: it is `PL3901 BOUND_HIT`, and the configuration's verdict is at best `INCONCLUSIVE`, as for pending taints (PS17.2). In the flow rule's exploration such a completion also takes one pending taint of its kind, one choice per distinct taint (PS17.2, PS17.3). A declared configuration is unchanged: it offers a completion only as a declared input (S61). The joint configuration offers the application's completions in the same way. **Timers in every configuration (S206, ruled 2026-10-06).** Every configuration, generated or declared, keeps every instance's armed timers in its global state in the same way, and the environment may fire one while it is armed; a declared input on a timer's target stays an input like any other (it replaces S61's rule that a declared configuration completes timers through its declared inputs alone). Any declared configuration that includes `A` also gets the conversation of each of its instances, with the same inputs and the instance bound raised to count them. The conversation's `never` statements are checked on it alone (PS5.2a) and in these configurations; an application that leaves a message unhandled gets `PL5102` or `PL5402` with its witness, as any configuration does. Each `never` of the conversation that these configurations check is judged tested or vacuous by PS5.2a, per configuration. **The joint configuration (S207, ruled 2026-10-06).** An application `A` bound to `n > 1` channels whose handler of a message from one channel (an action the binding of channel `c` maps a `Peer` action to) sends on another channel `c'` (`emit c'.reply` or `emit c'.template`) gets, beside the configuration of each channel, one more, named after `A`: the instance `app: A`; every conversation its `starts` handler spawns, each live, with its `Inbound`, its provider's completions and its timers, and the application's pending completions (S456); the instance bound `1 + n`; and the transit bound the sum of the conversations' `pending` bounds. It is the model of the run for a reply across channels. Its exploration is capped at 10,000 global states; a check that reaches the cap is `PL3901` and `INCONCLUSIVE`, never `CLEAN`. A finding in it, as in any configuration, is the program's: in the cross-channel application of the M8b review, the email conversation refuses, `busy`, a reply that answers no waiting message while its slot is held (`PL5407`). In each of these configurations two kinds of global step are findings, reported once per action with the path to the first in breadth-first order as the witness: a delivery of a receipt that `A` rejects, `PL5406 RECEIPT_REJECTED`, since a rejected step sends no `Ack` (PS3.2) and the conversation's slot is then never freed; and a delivery of `Reply` or `Template` from `A` that the conversation rejects, `PL5407 REPLY_REFUSED`, since `A` is not told and its message is lost.

## PS16. Credentials

- **PS16.0** **A credential adds no step of its own (M9, S203, S209).** `credential c: oauth2 { … }` in module `m` declares what the vault holds by reference; an effect's `uses c { s… } for p` names it, or `uses c { s… }` when `c` names no holder (PT10e). Its meaning is the module `m.c`: the module `std.credentials` instantiated for `c`. `std.credentials` declares the record `ScopeSet` and the machine `Grant`, whose lifecycle (requested, granted, refreshing within a bounded number of attempts, expired, revoked) is written from RFC 6749 and RFC 7009, and is checked alone with two scopes.
- **PS16.1** **The scope set of a credential.** In `m.c`, `ScopeSet` is the record with one `bool` field per scope `c` declares, in declaration order, each named by its scope with every `.` written `_`; two scopes of one credential that give one field name are `PL1002`. Every record literal of `std.credentials` whose fields are `ScopeSet`'s is read with the new fields, each `false`. Every other declaration is `std.credentials`'s, as written. So the scope sets `m.c.Grant` explores are exactly the subsets of `c`'s declared scopes (PT22.2b): a grant with fewer scopes than requested is a reachable state, and `m.c.ScopeSet` and `m.c'.ScopeSet` are different types for two credentials.
- **PS16.2** **One grant per credential and holder.** At run time each pair of a credential `c` and a holder (a `Principal`, or none for `client_credentials`) has its own instance of `m.c.Grant`, keyed by both (PT22.2a). **A person's grant with no holder named (S457, ruled 2026-10-09).** A credential granted by a person (`authorization_code`) may declare no `holder`. It then has one instance of `m.c.Grant` at a time, as a `client_credentials` credential does, and an effect that uses it names no `for`. Its holder is the person named by the first signed grant request taken for that instance (PT10g): the runtime keeps the holder by its keyed digest beside the instance, and no program, policy or proposal reads it. A later signed request that names another holder is refused while the instance is not `Revoked`. After a revocation (PS16.4) the next request creates the next instance, and the first signed request taken for it fixes its holder again; so replacing the holder needs a revocation. A credential that declares `holder Principal` keeps its meaning: one instance per holder, named by the effect's `for p`. A scope granted on one credential is a field of that credential's instance only, so it never satisfies an effect that uses another credential. The check and the runtime each instantiate `m.c` from this text; poly-ref is given the source as written, as for a channel (PS15.0).
- **PS16.3** **The grant check (PT22.4, S199).** For an intent of an effect with `uses c { s… } for p`, before any policy and before the mandate (PS8.9), the runtime reads the instance `G` of `m.c.Grant` for `c` and the value of the payload field `p` (for `client_credentials`, and for a person's credential that names no holder, the one instance of `c`, S457), as of the proposal. If there is no such instance, no vault for `c`, or `G.g` is not `Granted`, the intent is denied `credential-unavailable`; if some scope of `s` is not among `G`'s scopes, it is denied `insufficient-scope`. Both refusals are final whatever a policy says (fail closed), and are journaled with `G`'s sequence number. An intent the check passes is proposed with the field `credential`: the credential's name, `G`'s state and the scopes granted; the holder is never readable. An allow reads `G` as it reads a singleton (S147): when `G` takes a step before the intent starts, the allow is stale, and the intent is proposed again, so a grant revoked or expired before the start denies it.
- **PS16.4** **Revocation (PT22.6).** `Revoke()` reaches `G` from four sources: the provider's notice that the holder withdrew the grant, a person's signed revocation (a record of the kind `revocation`, by a key of the `people` ring, PT12.5), a security signal on the holder (PD5.3), and a person's signed forget of the holder when a source names the credential and its grant is the holder's own (PS17.7, ruled 2026-10-10). From the step that records `Revoked`, every intent using `G` is denied `credential-unavailable` (PS16.3). **The provider's revocation (ruled 2026-10-10).** The local revocation comes first and unconditionally: `Revoke()` makes `G` `Revoked` in its own step. The request that revokes the token at the provider (RFC 7009, the effect `credential.revoke` that step emits) is then an intent like any other, retried within its effect's bound and journaled with each attempt. Its failure, a refusal or a timeout, never undoes the local revocation and never blocks what revoked the grant: a forget completes whatever the provider answers. A token therefore stays valid at the provider until that revocation succeeds or the token expires. **A revocation made at the provider is not seen (ruled 2026-10-11).** A grant revoked in the provider's own account settings, a Google account's say, is not known to the runtime: its `Grant` stays `Granted` and its intents are still allowed, until a provider signal reaches the runtime or the owner signs a revocation. The owner's signed revocation is the way to take the grant to `Revoked` in the runtime, and it takes the path above, the local revocation first. An intent already started finishes, since the provider has already accepted its request, and its step is journaled before the revocation's.

## PS17. Memory

M10 (PT23, S300 to S310). A program declares where facts come from (`source`), who may read them (`audience`), and gets them only by reference (`Items`). Every `Content` and `Items` value carries a taint; the checker follows it on every path, and the runtime enforces it on every send.

- **PS17.0** **Sources.** `source s: k { adapter "a"  audience c [owned]  freshness d [stale escalate | stale deny]  [keys { k1, …, kn }] }` declares a source of kind `k` (`records`, `documents` or `memory`) whose items all have class `c`. `keys` names the item keys the adapter supplies with each item (S451): a value of type `Key` per key, the same item always giving the same value. `owned` means each item has one owner, a `Principal` the source's adapter supplies (K14). A class `audience` does not declare is `PL6833 AUDIENCE_UNDECLARED`. A `records` or `documents` source names an adapter poly-io makes, otherwise `PL6834 SOURCE_ADAPTER_UNKNOWN`; a `memory` source is the runtime's own store and names none. A source adds no instance, state or step: retrieval effects read it, and `remember` writes it (PS17.5). **Envelopes (S459, ruled 2026-10-09).** `envelope k` in a source, `k` one of its keys, declares that its adapter gives, for a value of `k`, the envelope of a reply to the newest item with that key: its recipient, its subject, and its threading headers `In-Reply-To` and `References`. An envelope comes from the source only, never from a module, a decision or a message. **A source's credential (S460, ruled 2026-10-09).** `credential c` in a source of kind `records` or `documents` names a credential of the module that names no holder, or one that names `holder Principal` when the source is `owned` (S461) (`PL1001` for no such credential, `PL1201` for one with a holder on a source that is not owned, or for a `memory` source): the source's adapter reaches its provider under `c`'s one grant. The build certifies `c`'s vault as it certifies an effect's credential (PT10f), and `c`'s `Grant` instance tracks the grant (PS16.2). The adapter never holds a token: it is built with the runtime's handle for `c`, which sends each request through the vault, only under the provider's base addresses, and only while the grant is `Granted`. So revoking the grant (PS16.4) stops every request of the source, its sync included, from the step that records `Revoked`. A source names at most one credential, and adds no step, state or verdict by naming it. **Per owner (S461, ruled 2026-10-10).** When an owned source's credential names `holder Principal`, each owner of the source's items has a grant of its own: the instance of `m.c.Grant` for `c` and that owner (PS16.2), keyed by the owner's principal, the value the source's adapter gives as an item's owner (K14) and the verifier gives as a thread's principal (S450). A retrieval from such a source names its owner, `where owner == p` (`PL1201` otherwise), and its requests run under the grant of `p`'s value only: the request of one owner's retrieval through another owner's grant is refused, so one account's grant never reaches another's items. Revoking one owner's grant (PS16.4) stops that owner's requests, its sync included, and no other owner's. **check** explores `m.c.Grant` alone, as for any credential with a holder (M9): every owner's grant is an instance of that one machine, and the instance line says so, one `Grant` per owner.
- **PS17.1** **Taint (S300).** A taint is a pair `(c, O)`: a class `c` of `Audience` and a finite set `O` of principals, the owners. `⊥ = (a1, ∅)`. The join is `(c1, O1) ⊔ (c2, O2) = (max(c1, c2), O1 ∪ O2)`. Every `Content` value and every `Items` value carries a taint. It is a **ghost component** of the value: part of it as the checker and the runtime see it, and invisible to every handler, guard and property, which neither read nor write it. Equality of two `Content` values ignores their taints. A value keeps its taint wherever it goes: stored in a field or a map, passed as an argument, carried by a message, an intent or a timer. So a value's taint never decreases on a path (PT23.3b). A timer's firing keeps the taint of the step that set it (S322): on a machine alone as in a configuration, each `Content` and `Items` of its data carries the join of the taints of the values the timer was set with, until the timer fires or is cancelled. `none`, and every `Content` or `Items` that enters as data from outside the program (an input of the environment, a message from ingress), carries `⊥` in **check**. At run time a body received on a channel is owned by its sender (S327, PS17.4), which only narrows its audience. A program that declares no source has no taint but `⊥`, and the ghost changes nothing.
- **PS17.2** **Where taint comes from.** Two kinds of intent taint the data of their completions:
  - **A retrieval.** An effect whose body holds `retrieve s where owner == p limit n` (or `retrieve s limit n`) is an effect of kind `source.s.retrieve` (PT23.1c), labelled `read:private` when `s` is owned or its class is above `a1`, and `read:store` otherwise; its ok outcome binds `r.items`, an `Items`. Its intent's taint is `(c_s, {v})` when `s` is owned and the predicate names `p`, `v` being `p`'s value in the intent's payload (`∅` when `v` is `none`); `(c_s, Ω)` when `s` is owned and there is no owner predicate, `Ω` being every principal (in **check**, every representative; at run time a mark no principal reads alone, PS17.4, S326); and `(c_s, ∅)` when `s` is not owned. `owner == p` is the only predicate the taint reads, `p` a `Principal` parameter of the effect; `where owner == p` on a source that is not owned is `PL6835 OWNER_ON_UNOWNED` (S303). **A key predicate (S451).** A retrieval may add one equality on a key its source declares, `where owner == p and k == x` or `where k == x`, `x` a `Key` parameter of the effect: the items returned are those whose key `k` is `x`'s value. It narrows the items and never their taint, which the owner predicate alone decides as above; a key the source does not declare is `PL1001`, and `x` of another type is `PL1201`. A key is compared only for equality, so PS4.1g holds of a retrieval by key, and the checker explores its completions as any retrieval's. **An envelope retrieval (S459).** An effect whose body holds `retrieve s envelope where k == x` (or `where owner == p and k == x`) is an envelope retrieval, of kind `source.s.envelope` and labelled as a retrieval of `s`; `s` declares `envelope k` and the key predicate names that `k` (`PL1201` otherwise). Its ok outcome binds `r.envelope`, a `Content`: the body of the envelope, which the runtime stores with the taint a retrieval of `s` with the same owner predicate has, and records as an envelope of `s`. Its intent taints its completion as a retrieval's does, and only the runtime delivers its completion (K10). **One retrieval per machine and kind (S41 with S451, ruled 2026-10-09).** Every retrieval of a source `s` has the kind `source.s.retrieve`, and every envelope retrieval the kind `source.s.envelope`, whatever machine declares it. Each intent of such a kind is run with the retrieval its own machine declares: its owner predicate, its key predicate and its limit. So two machines may retrieve from one source differently, by message with limit 1 in one and by thread with limit 5 in the other, and each runs its own. Two effects of one machine whose retrievals from one source differ in their owner predicate, their key predicate or their limit are `PL1002`, since a machine holds one retrieval per kind; so are two remembers of one source in one machine whose provenance or subject differ.
  - **A decision.** A decision's intent's taint is the join of the taints of the `Content` and `Items` values of its payload. A decision's answer may be a `Content`. A decision with `cites x` gives an answer whose taint is that of the items it cites, a subset of `x`'s (PT23.3a); a subset's taint is at most the set's, so the join covers every subset. *Limit (S323):* only a `Content` answer carries the decision's taint. An answer of a finite type (a `bool`, an enum, a range) carries none: a decision with a finite answer is a declassification point, giving at most `log2` of the number of its answers in bits per call to whoever its answer reaches. Tainting finite values would mean following implicit flows through the state, which v1 does not do. The certificate lists every decision that reads a tainted `Content` or `Items` and answers a finite type, with the highest class it reads and the number of its answers, and a policy may deny such a decision by `effect.taint.class` as any effect. The certificate's list of counts (PS1.4b) names each count read of an `Items` from a retrieval whose owner predicate is absent, or names a value other than the requesting step's claimant's principal.

  Each instance holds, as ghost state, its **pending taints**: for each retrieval effect and each decision of its machine, the multiset of the taints of its intents not yet completed. An accepted step adds the taint of each such intent it emits. A step of an action that an outcome of such an effect or decision names (its completion), whatever its verdict, takes one pending taint `t` of it and removes it, and every `Content` and `Items` value in its data carries `t`. When none is pending, the step is a completion nothing asked for (PS4.4), and its data carries `⊥`; the runtime never takes such a step, since only the runtime delivers a retrieval's or a decision's completion (PS17.4, K10). **check** explores each pending taint as a choice of its own. A step that would hold more than 3 pending taints for one effect or decision of one instance is not explored: it is `PL3901 BOUND_HIT`, and the flow rule's verdict is at best `INCONCLUSIVE`.
- **PS17.3** **The flow rule (S301, S305).** The **recipient** of an intent of an effect `e` has a principal and a class. Its principal is the value of the payload field that `e`'s clause `to p` names, or none without one. Its class is the value of the step's claims field of type `Audience`, when the action's claims type has exactly one and the recipient is the claimant: `e` has no `to`, or `to p` names the value of the claims' one field of type `Principal` (S324); otherwise the class `e` declares with `audience c`; for the provider effect `channel.c.send` of a channel's conversation, the class the channel declares (PS15.0a), and, when the channel declares `principal from`, the thread's principal (S450); and otherwise `a1`, the most restricted reader (S305). A recipient `r` **may read** a taint `(c, O)` iff `class(r) > c`, or `class(r) ≥ c` and `O = ∅`, or `O = { principal(r) }` with a principal (PT23.3c). The flow rule is the step property: on every accepted step, for every intent of an effect other than a retrieval, a decision or a `remember`, the recipient may read the taint of every `Content` value of the payload. It is checked on every machine alone, over its pending taints, and in every configuration, over every instance's (PS13): a message keeps the taints of its values, so a value tainted in one instance and emitted by another is judged where it leaves. While a taint of an instance's retrieval or decision is pending, the completions of that retrieval or decision are inputs of that instance in the flow rule's exploration, as an armed timer's firing is (PS15.5), even where the configuration does not declare them (S61): otherwise a value tainted by a completion could never leave in a channel's configuration, and the rule would hold for no reason the program gives. A violation is `PL6831 AUDIENCE_LEAK`, a finding, with the shortest path to the step as its witness. A message between machines that no configuration follows is judged nowhere (S322): on a machine alone, an accepted step that sends, spawns or signals with a `Content` or `Items` whose taint is not `⊥`, to a machine that no configuration of the program holds together with the sender's, is `PL6838 FLOW_NOT_FOLLOWED`, inconclusive, naming the message; the flow rule's verdict is then at best `INCONCLUSIVE`, never a silent clean. A configuration holds the instances it declares and the conversations PS15.5 adds to it (S456, ruled 2026-10-09): a channel's generated configuration, and the joint one, hold each conversation the application's `starts` spawns, and a declared configuration that includes `A` holds the conversation of each instance of `A`. So a message between a channel's application and its conversation is always followed. On a machine alone the ghost adds no behaviour: each step's taints are a function of its path, so the paths of **check** with taints project onto its paths without them. In a configuration the flow rule's exploration adds only the pending completions above. Either way no other verdict and no state count changes, since the flow rule is explored apart. The flow rule is explored apart, and its report gives the number of states with their taints.
- **PS17.3a** **The envelope rule (S459, ruled 2026-10-09).** `envelope e` in an effect, `e` a `Content` parameter of the effect, says that what the effect sends goes to the recipient of `e`'s envelope and carries its subject and threading headers. The rule is static. In every `emit` of the effect, the argument for `e` is either a parameter of the emitting action that the ok outcome of an envelope retrieval binds from `r.envelope`, passed unchanged, or a field whose every write is such a parameter, passed unchanged, or `none`. Any other origin is `PL6830 ENVELOPE_NOT_FROM_SOURCE`, an error: a decision's answer, a body received on a channel, a parameter of an input, or a value computed from any of these. So no model answer and no message chooses where a reply goes. At run time, before the memory check, an intent of such an effect is denied `envelope-origin` when its `e` is `none`, is not the digest of a body the runtime stored as an envelope, or names an envelope erased since (PS17.7), final whatever a policy says (fail closed). An erased envelope is refused here, before any handler, so no recipient survives an erasure (ruled 2026-10-09). The handler takes the recipient and the headers from `e`'s body, which it reads by PS17.4a, and from nothing else; it is the host's code, held to that as every handler is held to its effect.
- **PS17.4** **Representatives and run.** When a program declares an owned source, the number of principal representatives is one more than PS4.1c's. *Lemma:* if a path of **run** breaks the flow rule at a step, its renaming onto the representatives breaks it at that step. The violation names an owner `o` that is not the recipient, or none when only classes decide. Give `o` a representative of its own, and the other principals the remaining ones, which are as many as PS4.1c requires to keep every equality the program tests; `o` stays distinct from the recipient, so the renamed step breaks the rule too. ∎ The verdict prints the count. **At run time** the runtime keeps each body's taint in the content store's metadata, keyed by its digest, as the join of every taint it was stored with. That is at least the taint **check** gives each occurrence of the body, so the runtime refuses every send the flow rule refuses, and may refuse more, never fewer. Before the grant check (PS16.3) and before the policy, it applies PS17.3 to each `Content` of an intent's payload: a recipient that may not read it denies the intent `audience`, and so does a body with no taint record (fail closed); either refusal is final whatever the policy says (S302). A retrieval with no owner predicate from an owned source records the owners `Ω` for the flow rule, a mark that no principal reads alone, so only a class above the source's reads its items; beside it, the taint record keeps the owners of the items it actually returned, which only a forget reads (S326, PS17.7). A body received on a channel is owned by its sender: its taint at ingress is `(c, {s})`, `c` the channel's declared class or `a1`, `s` the sender's principal, the address the adapter verified, by its keyed digest; and the recipient of the channel's provider effect `channel.c.send` on that thread has that principal (S327). The proposal carries `taint: { class, owners }`, the join over its payload, the owners by their keyed digests and `Ω` as itself (PT25.1). A retrieval's and a decision's completions are delivered by the runtime only: an outside dispatch of one is refused before any step, as K10 refuses a decision's.
- **PS17.4a** **A handler reads its own payload's bodies (S459, ruled 2026-10-09).** The handler of an intent receives the capability `content.read(d)`, which gives the body of `d` when `d` is the digest of a `Content` value of that intent's own payload, and refuses any other digest before reading anything (`PL6406`, audited). So a handler reads the bodies of its own intent and of nothing else. An intent reaches its handler only once the memory check (PS17.3, PS17.6), the grant check and the policy have allowed it, so a handler never reads a body the flow rule refuses to send. Each read is recorded by its digest, with the intent, on the runtime's content record; the body is never journaled. A body erased since (PS17.7) is refused `content-missing`.
- **PS17.4b** **A handler reads its own payload's item sets, and one item (S462, ruled 2026-10-10).** The handler of an intent whose payload holds an `Items` receives the capability `items.read(x)`, which gives, when `x` is an `Items` value of that intent's own payload, the list of its items, each `{ id, owner, keys }`: the item's id at its source, its owner (`none` on a source that is not owned), and the values of the source's declared keys the adapter gave for it. Any other value, a reference the runtime did not store or an `Items` of another intent's payload, is refused before anything is read (`PL6406`, audited). As for `content.read` (PS17.4a), an intent reaches its handler only once the memory check, the grant check and the policy have allowed it. Each read is recorded on the runtime's content record by the set's reference and the digest of what it gave, with the intent; no id, owner or key is journaled. The module itself still reads only `x.count` (PS1.4b): an item's id, owner and keys reach the host's code, never the state, so PS1.4c holds. **Exactly one item.** `one p` in an effect, `p` an `Items` parameter of the effect, says the effect acts on exactly one item. **check** narrows `p`'s count domain to `{1}`: an accepted step that emits the effect with a `p` whose count is any other is `PL6847 ONE_ITEM_COUNT`, a finding with its witness, so the module guards the emit (with `require x.count == 1`, for one). At run time, as the second layer, an intent of such an effect whose `p` is not an item set the runtime stored with exactly one item is denied `items-count`, before the memory check and final whatever a policy says, so it never reaches its handler. The `Items` type check (PT10j) still refuses a forged or unstored reference in a step's data, before any step.
- **PS17.5** **Remembering (S309).** `remember s as k about p` in an effect writes each `Content` of its payload to the source `s`, of kind `memory`, as an item owned by `p`'s value, with the provenance `k` (`observed` or `derived`; `as verified` is `PL6837 VERIFIED_BY_PERSON`, refused, since only a person's signed record makes an item verified, S320) and the taint `(c_s, {p})` (`(c_s, ∅)` when `s` is not owned). It is an effect of kind `source.s.remember`, labelled `write:store`. The flow rule does not apply to it. Instead, an item may not be written with a wider audience than its content: every recipient, of any class and principal, that may read the item's taint may read the content's. A step whose `remember` breaks this is `PL6832 TAINT_DOWNGRADE`, a finding with its witness. A memory item is retrieved like any other, with its source's taint.
- **PS17.6** **Citations and freshness (S304, S307).** `cites x` in a decision makes its ok outcome bind `r.cites`, an `Items`, a subset of the references `x` held. The runtime checks it before the completion: an answer citing a reference it was not given is refused with the reserved reason `uncited`. The refusal is recorded on the run, the ok outcome is not delivered, and the decision's `failed` outcome is delivered in its place, as for a provider that failed. **A citation is required (ruled 2026-10-10).** A decision with `cites x` must cite: an answer whose citation list is empty, or that gives none, is refused `uncited` by the same check that refuses an item the decision was not given, such as an item of another thread's retrieval. **check** offers every completion of either outcome in any state (PS4.4), so the refusal adds no behaviour there. Each item has an `asOf`; an `Items` value's age is the runtime's clock at the decision minus its oldest `asOf`, recorded in the `verdict` event and never read on replay (PS8.8). A decision with an `Items` argument older than its source's `freshness` is escalated (`stale escalate`, the default) or denied `stale-items` (`stale deny`), before the policy. A policy reads `items.age` as it reads `age(step.claims)`, and the decision table explores it by the intervals the freshness bounds and the policies' thresholds cut (PT20.3).
- **PS17.7** **Forgetting (S306).** `poly forget <subject> --by <person>`, a record of the kind `forget` signed by a key of the `people` ring, names a principal or a whole source. The record is bound to the project's anchor (S321): its subject names the anchor's id, and a record bound to another anchor is refused `wrong-project` before it is taken. It erases (PS3.2, S205) every body in the content store whose taint names the subject among its owners or among the owners its record keeps (a retrieval's real owners under `Ω`, S326), derived ones included (Q4), and every body received from the subject on a channel (S327); or, for a source, every body read from it. Erasure follows the facts; audience follows the worst case. It calls each source adapter's `forget(subject)`; and writes a `forget` event with the subject's digest and the erased digests. The journal and the ledger hold only digests, so every chain still verifies, and replay reports the steps that named an erased body as forgotten (PS11.3a). **A forget uses no grant (ruled 2026-10-10).** A forget erases what the runtime holds for the subject: its items and item sets, its bodies, its envelopes and its taint records, as above. It never sends a request under a grant. Each source adapter's `forget(subject)` runs with no credential: a request it makes through a credential handle (PS17.0) is refused before anything is sent, and the refusal does not cut the forget short. So an adapter over a credential's provider clears only what it holds itself, its cursor and its cache, while an adapter that reaches a store with no credential (a `postgres` table, an OpenSearch index over the host's transport) removes the subject's items there as before. When the subject is an owner of a source whose credential has a grant per owner (S461), the forget first revokes that owner's grant (PS16.4), so no later sync can bring the subject's items back; every other owner's grant is untouched. A forget of a subject that holds no such grant, a channel's sender for one, revokes nothing. The provider's own copy of the subject's data, the person's mailbox for one, is not poly's to erase.

## PS18. Routes and budgets

- **PS18.0** **A route and a budget add no step of their own (M11, S351, S352).** `route r { … }` and `budget b { … }` in module `m` are top-level declarations. Their meaning is two modules, written from `std.routing`, which declares the machines `Route` and `Budget` and is checked alone: `m.r`, holding `std.routing`'s declarations with `Route` instantiated for `r` (PS18.1) and `Budget` left out; and `m.b`, holding them with `Route` left out. The checker and poly-ref each write these modules from this text, and neither is given the other's.
- **PS18.1** **The route's machine.** A route has tiers `t0 … t(T-1)` in the order written, each naming a provider, a price table, a calibration map or none, an input token limit and an output token limit (S360); an escalation clause `escalate when e1 or … or ek`, each `ei` being `conf < c`, `margin < c` or `failed`; and at most one budget. In `m.r`:
  - the type `Tier` is `0..T-1`, and `Route`'s field `left` starts at `T-1`;
  - every occurrence in `std.routing` of the expression `conf < 0.8 || margin < 0.1` is the route's condition: the `||` of its `conf < c` and `margin < c` terms in the order written, or `false` when it has none;
  - when the clause does not name `failed`, every `left > 0` in the handler of `Fail` is `false`;
  - the effect `call` has the kind `route.r.call`, the labels of the decision that names the route, and a retry of one attempt within that decision's timeout;
  - when the clause has no `conf` or `margin` term, the rules of `Route` whose trigger is an answer below the thresholds, `below-thresholds-escalates` and `exhausted-after-the-last`, are left out: a rule whose trigger the route does not declare is not instantiated for it (ruled on the review of M11). A rule that is instantiated and never exercised is still vacuous.

  `Route` starts `Ready`. `Start()` makes it `Trying` and emits `call(0)`. Each `call(t)` completes with `Answer(conf, margin)` or `Fail()`. An answer that meets the condition's thresholds makes it `Answered`; an answer below them, or a failure the clause names, emits `call(t + 1)` while a tier is left, and makes it `Exhausted` after the last. A failure the clause does not name makes it `Exhausted`. `conf` and `margin` are completion parameters of type `Conf`, explored by the intervals the condition's constants cut (PD1.4b). **Checked:** every path from `Trying` reaches `Answered` or `Exhausted`, under the fairness of `Answer` and `Fail` (the provider's completion, PS6).
- **PS18.2** **A routed decision (PT24.1c, S351).** A decision names its route with `route r` and then names no `provider`. A route serves one decision, since its maps are fitted for that decision (PD1.6a). A routed decision has no `Content` result and no `cites`: no tier's answer is kept with its taint and no tier's citations are checked, so a routed decision that would answer a body, or cite, is `PL6839 ROUTED_DECISION_MATERIALS`, refused (F1 of the review of the M10 and M11 merge). **It may read `Content` and `Items` (S402).** Each tier's call is given the decision's materials as an unrouted decision's provider is (PS17.2): the bodies of its `Content` arguments and the items of its `Items` arguments, read from the decision's payload when the call runs, while the question recorded holds digests only (S310). Each tier's call is proposed with the decision's taint and items, as the decision is (S323, PS17.6): the join of the taints of its `Content` and `Items`, their count, class, age and provenance, so a policy of the route's scope may deny or escalate a tier by `effect.taint.class`, and freshness is judged on each call. The answer stays in the decision's finite result type, so it carries no taint, and PS17.2's stated limit on a finite answer applies to it as to any decision. In the decision's machine nothing changes: its completion is an input explored over every answer and every interval, as for any decision (PD1.4). At run time, the decision's intent crosses the gate as before; once started, it runs no provider. The runtime creates the instance `route:<intent>` of `m.r.Route` and dispatches `Start()` to it, both journaled, and the intent waits for that instance's end. Each `call(t)` is an intent of its own: it crosses the gate under the trust scope `m.r` (PS8.7), its provider is tier `t`'s, and its answer is calibrated by tier `t`'s map. When the instance reaches `Answered`, the decision's `ok` completion receives the answering tier's answer, `conf` and `margin`; when it reaches `Exhausted`, the decision's `failed` completion runs with the reason `route-exhausted`. The decision's intent then takes its terminal transition, once. Every tier choice is a step of the route's instance, so replay reproduces it from the journal by PS11.4, with no provider called (K10).
- **PS18.3** **Money (S350).** An amount is an integer of micro-units, one millionth of a currency unit. A price table gives a provider's model, a currency and, per token class, the price of a million tokens in micro-units, with the source it was read from and the date it was read. A tier's **reservation** is `ceil((I × P_in + N × P_out) / 10^6)`, `I` its input token limit at the table's price of the class `input`, and `N` its output token limit at the table's highest price of any other class (S360, ruled on the review of M11). A call's **cost** is `ceil(Σ n_k × P_k / 10^6)` over the token classes `k` its provider reports, a class the table does not price taking the table's highest price. The provider is given `I` and `N` as its limits (K15), so a call within both costs no more than its reservation, and an overrun is a provider reporting more than one of its limits. **A report poly cannot price (S361, ruled).** A call that answers with no usage report, or with a count that is not a whole number of tokens, is charged its full reservation, and the violation is recorded with its `decision` event (`usage-missing` or `usage-invalid`); its counts are not recorded. Such a call is never released.
- **PS18.4** **Budgets and reservations (PT24.3, S352, S353, S354).** Each cap of a budget has its own instances of `m.b.Budget`, one per address: `budget:b:run:<i>` for a cap per run, `i` the decision's instance; `budget:b:scope:<s>` for a cap per scope, `s` that instance's trust scope (PS8.7); `budget:b:<p>:<k>` for a cap per period, `p` one of `hour`, `day` or `month` and `k` the period that holds the runtime's clock, in UTC; and `budget:b:scope:<s>:<p>:<k>` for both. The runtime creates an instance with `Open(cap)` on its first use. These are the runtime's own inputs, never dispatched from outside, and each is journaled.
  - **Reserve.** Before the policy decides on a tier's intent, the runtime reads every instance of the route's budget for it. If some instance has `spent + reserved + r > cap`, `r` the tier's reservation, the intent is denied `budget` (`on exhausted deny`, the default) or escalated with the reason `budget` (`on exhausted escalate`); the refusal is final whatever a policy says. An approval does not raise a cap: an approved intent is read again, and is denied `budget` when its reservation still does not fit. Otherwise the intent is proposed, and when the gate allows it, `Reserve(r)` is dispatched to every instance in the transaction that records the allow, so the reservation and the allow commit together. A `Reserve` that one instance rejects aborts that transaction, and the intent is read again. An instance that is missing and cannot be created, or that cannot be read, refuses the call, fail closed.
  - **Settle.** A call whose provider answered is settled: `Settle(r, actual)` is dispatched to every instance it reserved on, `actual` the call's cost, in the transaction of the intent's terminal transition, which is the completion step's when the completion is taken. The call's record is kept when the provider answers, so a call whose intent ends otherwise (its completion lost to a crash, its settle refused, its completion outside its type) is settled with the same cost, and its `decision` event is written then (review of M11, B2). When `actual > r`, `Budget` counts the overrun, and every later reservation sees the corrected `spent`.
  - **Release.** An intent that ends after its reservation with no answer (its call failed, its allow went stale and was denied, or an escalation of its recheck timed out) dispatches `Release(r)` to each instance, in the transaction of its terminal transition.
  - **Once.** Each `Reserve`, `Settle` and `Release` of an intent has an action id derived from the intent, so a step repeated after a crash is deduplicated (K4), and an intent's reservation is settled or released exactly once. A runtime stopped between the reservation and the call's completion restarts with the reservation held.
  - **Checked.** `Budget` satisfies `spent + reserved <= cap + overrun` in every reachable state. It is checked alone, with its cap, reservations and costs in check domains small enough to explore and wide enough to put a reservation below, at and above the remainder and a cost below, at and above its reservation; the verdict prints that instance, and a value beyond it at run time is accepted and disclosed (PT3.4). A `Budget` instance is one actor (K2), so the reservations of concurrent runs are serialized at it.
- **PS18.4a** **A budget on an unrouted decision (S454).** A decision that names a provider, not a route, may name a budget with `budget b`, and then names its price table and both token limits, as a tier does: `prices "f" max input tokens I max tokens N`. Its call is the decision's own intent, and it reserves, settles and releases as a tier's call does (PS18.4), with the reservation of PS18.3 from its table and limits, the provider given `I` and `N` as its limits (K15), and S361 unchanged: a call that answers with no usage, or one poly cannot price, is charged its full reservation. The budget's addresses read the decision's instance as a tier's call reads its decision's. Its proposal carries `budget` as a tier's does, and its `decision` event records the call's usage and cost. A decision with no budget reserves nothing, as before. In the decision's machine nothing changes: the budget's refusal is a deny or an escalation of the decision's intent, which **check** already explores, since the gate may deny any intent (PS4.4).
- **PS18.5** **Reasons.** `route-exhausted` is reserved (PS3.2). `budget` is a gate deny reason, as `credential-unavailable` is.
- **PS18.6** **What a record holds (S358).** The `decision` event of each answered tier's call is written on the route's instance, in its completion's transaction (K1), with the tier, the model, the usage by token class (or the violation of S361), the cost, the reservation, the price table's digest and the decision's instance. The decision's own `decision` event repeats the answering tier's and links its hash. No prompt, completion body or key enters the journal, the ledger or a certificate: a question and its inputs are kept by digest (PD2.2a). A tier's answer outside the decision's type, which may be a provider's free text, is recorded by its digest only, in the answer and the distribution alike (S310); the decision's completion still fails outside its type.

## PS19. Traces

A trace corpus is the journal made into evidence for other tools: replay, the version gate, grading and mining (PF10.1). It is a projection of the journals of one certified build. It adds no fact the journals and the build do not hold, and it carries no body.

- **PS19.1** **An episode** is the steps of one run of an instance, in `seq` order, with the run's decision outcomes. Its run id and every digest in it are replaced by tokens (PS19.4). An interaction, for a miner, is a run.
- **PS19.2** **A step in a trace** gives its action, its step kind (`accepted`, `rejected`, `unhandled`) and reject reason, its pre-state, its data and its post-state, the effects it emitted (each with its kind, its labels and its **consequence**), the gate decision recorded for each of those effects, and the parameters it was `outsideCheckDomain` for.
  - **Consequence.** The consequence of an effect is its declared `class` (`none`, `reversible`, `compensable`, `irreversible`, PT6.1). An effect with no declared class has the consequence `unknown`, never a default.
  - **Outside the check domain (S504).** A parameter is `outsideCheckDomain` for a step when its mode is `disclosed` (PT3.4) and its journaled value is not in the check domain that PS4.2 gives it in the certified source. A `strict` parameter is never outside, since dispatch rejects such a value (PT3.4a).
- **PS19.3** **Replay property.** For each episode, take the steps whose `seq` values are consecutive. In such a run of steps, the post-state of a step is the pre-state of the next, and an accepted step whose data and states are all declared values (PS19.4) has, as its post-state, `δ` (PS11.4) of its pre-state and its data. A trace therefore *replays*: the chain of states is the fold of the journal, as far as the trace holds values. A step with a token in place of a value is checked only by the chain.
- **PS19.4** **What leaves, and how (S501).** A value leaves as a value when its declared type has a check domain (PS4.2): a `bool`, a range, an enum, a union or a record or a map of such, and an `int` or a `string` with a `check` clause. Every other value leaves as a token: a `Principal`, `Ref`, `Key`, `Content` or `Items`, any type holding one, and any digest the journal holds. The token of a digest is a keyed hash of it under a salt drawn at random for each export and never written anywhere, so two tokens in one export are equal exactly when their digests are, and no token of one export can be linked to a token of another, or to a journal. Names declared in the certified source (actions, constructors, fields, machines), reject reasons, effect kinds, labels and the fixed words of PS19.2 are the only strings that appear as themselves. No time of day appears.
- **PS19.5** **Erasure (S502).** A step whose data, pre-state or post-state names a body that a `forget` erased (PS17.7, PS11.3a) is **left out**. A run that has lost a step is **gapped**: PS19.3 holds on each run of consecutive steps and says nothing across the gap. The **creation row** of a run (the kernel's `$create`) names no body and is not a step for this purpose: a run all of whose steps after its creation row are erased, and which has at least one, is **erased**, and is not exported at all. The corpus reports how many steps, gapped runs and erased runs were left out, and never which. (Amended 2026-10-11 on the reviewer's ruling: a creation row can name no body, so without this no run could be erased.)
- **PS19.6** **What a trace omits, and counts.** Advice events (PT16), the runtime's own runs (`runtime:` runs and the `OutboxIntent` instances it hosts), and runs whose journal is gone (archived) are omitted. The corpus reports how many of each. A trace never says that a run was complete when it was gapped, nor that a consequence was known when it was not: both are reported, as `gapped` and `unknown`.

## PS20. Mined rules and their promotion

A mined rule is a statement about how a program has been run. It becomes part of a program only through a person's verdict and the program's own checks (PF10.2, PF4.4, PF4.5). Nothing in this section lets a tool, an agent or a model add an obligation.

- **PS20.1** **A candidate** is a rule a miner proposed from a trace corpus (PS19), with its support, its counter-evidence and the source that would carry it. It is not part of any program. Its **digest** is the SHA-256 of its canonical form without the digest field, so a changed candidate is another candidate.
- **PS20.2** **What a candidate may become (S509, S510).** Let `X` and `Y` be effect kinds emitted by one machine `M`, or the effect kinds a candidate names:

  | Mined pattern | Promoted as | Where |
  |---|---|---|
  | `no-X-without-prior-Y`, `X-implies-prior-Y` | the path property `before("Y", "X")` (PS5.4) | in `M` |
  | `at-most-one-X` | the path property `count("X") <= 1` (PS5.4) | in `M` |
  | `no-X-unless-state`, over fields `f` of `M` and a set of values `A` | the rule obligation `when effect.kind == "X" require machine("M").f in A else deny on unknown escalate` | in a policy of the scope |

  A path property holds of every path of the machine's instance, so a promoted `before` or `count` is a statement about each run. A rule over actions that emit no effect is promoted as an invariant over the machine with a ghost flag (PS20.6). `exactly-one-Y-per-X` and `no-X-without-prior-Y-same-S` are **not promotable in M7**: the candidate says so and names the pattern, and it is listed, never dropped. An eligibility candidate whose state is unknown escalates (`on unknown escalate`), as PS8.2's default for a deny rule.
- **PS20.3** **An adjudication** is a person's verdict on one candidate: `real`, `spurious` or `defer`. It is a signed record of the kind `adjudication` (PT12.5), whose subject binds the project's anchor, the candidate's digest and the verdict. An agent's key never signs it (PF9.6, PT12.5); a verdict `narrowed` is no verdict in M7. Only `real` proceeds. A `spurious` or `defer` candidate reaches no program, and its record is kept with the project.
- **PS20.4** **Promotion** adds the candidate's source to the program, at the place PS20.2 names, with a marker line that names the candidate and the record, and appends the promotion to the project's **promotion list**, whose order is the order of promotion. A promotion is refused, and the program left as it was, when it makes a mandate undischargeable (`PL6501`, PS8.6), with the minimal conflicting subset, in which the promoted rule is named by its candidate id and its record. A promotion whose adjudication is not a verified record of a person, whose candidate digest is not the adjudicated one, or whose corpus is synthetic (PS20.5) outside a test certificate, is refused.
- **PS20.5** **Synthetic corpora (S514).** A candidate says whether its corpus is `recorded` or `synthetic`. A certificate that cites a promotion from a synthetic corpus is a certificate of `source: "test"`; any other certificate refuses it.
- **PS20.6** **Actions without effects (ruled 2026-10-11).** A candidate over actions `X` and `Y` of one machine that emit no effect is promoted as: a ghost field `seen_Y : bool = false` and `did_X : bool = false` added to the machine, `seen_Y' = true` set in each handler of `Y` and `did_X' = true` in each handler of `X`, and the invariant `did_X implies seen_Y` (for `at-most-one-X`, a counter field with its bound). The ordinary checks then say whether the machine keeps it.
- **PS20.7** **Admission (PS8.6).** The consistency of obligations includes the promoted rules, in promotion order, and the check runs again on every promotion. The certificate of a program with promotions lists each one: its candidate, the digest of its adjudication record, its corpus kind and the miner that proposed it. The promoted text is read back from the sources against that list at admission, and a promotion whose text is not in the sources, or whose record does not verify against the certified people ring, is refused.

## Conclusion

A poly program denotes a deterministic, labelled transition relation over a finite checked instance. Checking, simulation and running are three interpretations of one environment interface over that same relation, and the claim that the checked program is the running program is a theorem about two of them. States may be tagged unions, so invalid states are unrepresentable rather than merely unreachable. Policy logic has its own type. Machines talk to each other only by messages sent to addresses. A configuration of machines is checked with messages arriving in any order, within declared bounds. Delivery is part of what sending means, and the runtime is obliged to implement it. Attached children are co-located, and detached children are actors like any other. Obligations from all sources are checked together for a way to discharge each mandate; that check is a possibility property, named as such. Messages have identities, so fairness is per message, and the delivery protocol that makes a message take exactly one step is itself a checked machine. Rejections are labelled stuttering steps. Properties come in five kinds with distinct meanings. Liveness is stated only with its fairness assumptions. Policies have a total three-valued evaluation in which an unknown deny condition escalates. The lowering is correct when its transition relation equals this one, and every `poly check` verifies that for the program at hand. Every guarantee about a running program names the kernel assumptions it depends on. Facts carry a taint as a ghost that no handler reads: the checker follows it on every path, and a send that could reach a reader outside its audience is a finding with its shortest witness.
